# The run-to-run loop

Change one line, rerun, compare: baselines, code-change capture, run adoption, and the deltas every run reports.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **Run-vs-run loop (change → break → fix → rerun → compare)**: exptrack's headline workflow is iterating on one or two lines at a time, so the loop is first-class end to end. **(1) Broken runs self-identify**: a notebook cell that raises is detected in `notebook_hooks._post_run_cell` (`_detect_cell_error` → `_nb_state["last_error"]`, read+cleared by `consume_cell_error`); the automatic finish paths (`notebook._finish_active(auto=True)` — kernel-shutdown atexit, a new-run boundary) mark that run `failed` with its traceback instead of silently `done`, while an explicit `%exp_done`/`done()` (`auto=False`) always declares success. `Experiment.finish()` honors `auto_trash_failed` (config, default off) to Trash a failed run at finish. The dashboard hides `failed` runs behind a **Show failed (N)** toggle (`showFailed` state, `getFilteredExperiments`). **(2) Every run reports its delta**: `core/queries.py:get_previous_run` (next-older run of the same script, ordered by **`(created_at, rowid)`** — two runs launched inside the same clock tick tie on the timestamp and the tie-break was whatever order SQLite returned, so "previous" could resolve to the run that started *after* this one; `rowid` is insertion order, i.e. launch order, so the chain always runs backwards in time. `find_previous_by_script` uses the same row-value comparison). **Which runs can be a baseline is one shared rule** (`_BASELINE_WHERE`, applied by both lookups so the strip, the card and the finish-time summary never disagree): trashed runs are excluded — they're gone from every list, so a delta against one names a baseline the user can't open or verify, and deleting a run between two attempts would silently change the numbers with no visible cause; instead "previous" walks back to the next surviving run, matching the list. `running` runs are excluded too — their metrics are still moving, so a delta against one doesn't reproduce a minute later and a parallel sweep would compare each run against a half-finished sibling (a row left `running` by a killed process is what `exptrack stale`/`finish` are for). But a **`failed` run is kept** as a baseline: "it broke, I fixed it, what changed?" is the loop this whole affordance exists for, and skipping the failure would hide exactly the comparison wanted — its `status` is carried through on both payloads instead, so `format_run_delta` prints `prev (name, failed)` and the dashboard marks the baseline `failed` (`_baselineFailedTag` on both the card header and the strip's baseline chip) with a note that the metric values are wherever it crashed, not a finished result (params and code are exact either way)) + `diff_runs` (`{param_changes, metric_changes, code_changed, source_changed}`, skips `_`-prefixed params; a **metric present on only one run is not a change** — a key missing on one side is "not measured", not a `None→value` move, so it's skipped, killing the flood when comparing against a metrics-less/phantom or pre-metrics run; and **float noise is not a change** — `_metric_moved(a, b)` gates every metric on a relative epsilon (`_METRIC_EPS_REL` = 1e-12, mirrored client-side as `metricMoved` in `js/core.py`), because `0.9 + 0.03` and `0.85 + 0.04 * 2` are both 0.93 yet differ by 1.1e-16, which surfaced as a change rendering `▼ -0.0000 (-0.0%)` — a delta reading as zero on a row that exists only because something supposedly moved). **Two code-change facts, kept separate**: `code_changed` is the repository-wide `_run_code_signature` (commit + the *entire* working-tree diff + `_script_hash`), while `source_changed` compares `_run_source_identity` — the run's own content-addressed script-snapshot hash, else its ordered `cell_exec` cell hashes, i.e. exactly what `compare_run_code` diffs (`None` when either run captured no code, so "same" is distinguishable from "unknown"). Collapsing them into one flag made an edit to *any other tracked file* stamp a byte-identical rerun with an amber `code changed` chip, directly contradicting the Code-changes panel beneath it; the strip now renders `code changed` only for `source_changed`, and a muted `repo changed elsewhere` chip (`.vs-chip-repo`, via `_vsCodeChip`) for the wider signal, with `format_run_delta` making the same distinction. **Deltas never round a real move to zero**: `fmtDeltaNum` drops to exponential below 1e-4, `fmtDeltaPct` prints `<0.1%` instead of `0.0%`, and `fmtMetricPair(before, after)` (plus `_vsFmtPair` for the strip's chips) widens precision until the two sides differ, since at a fixed 4dp a genuine 1e-7 move printed the same string twice + `format_run_delta` produce a one-line finish summary (`Experiment._print_delta_vs_previous`) and the dashboard detail "vs previous" strip (`GET /api/run-delta/<id>`; its baseline chip states how much **earlier** the baseline ran (`relEarlier`, e.g. "2 days earlier" / "just before", with the absolute timestamp in the tooltip and `current_created_at` added to the payload to compute it) and `_VS_PREV_LABEL` spells out "the last run of this script started before this one" — an absolute time can't carry that: `fmtDt` resolves only to the minute, so two runs launched seconds apart print the same string — "previous" alone is ambiguous when the run list is newest-first, so the run being compared against sits *below* the current row and reads as the next one). **(3) Every run stays re-runnable**: the real launch command is captured into `experiments.command` — for shell pipelines via `run-start`/`run-finish --cmd` (`_capture_pipeline_command`, so a run wrapped in a bash/SLURM script records the true command, not a truncated wrapper argv), and for the `exptrack run` / `python -m exptrack` **runpy** path via `__main__.main`, which builds a plain runnable `python <absolute-script-path> <args>` *before* mutating `sys.argv` and threads it through the new `Experiment(command=…)` param (falling back to `_build_command()` from `sys.argv` when not supplied). Without this, `cmd_run` left the script as `argv[0]` and `_build_command()` basenamed it — the reproduce box showed just `basic_script.py`, no interpreter, not runnable. **`_build_command()` returns `""` when `sys.argv` isn't a runnable command** (`_NON_COMMAND_ARGV0`: `ipykernel_launcher.py`, `ipython`, `jupyter-*`, `-c`, `""`). Under IPython `sys.argv` is the *kernel's* launch line, so every notebook run recorded a Reproduce command like `ipykernel_launcher.py -f /tmp/kernel-1a2b.json` — a connection file deleted when the kernel stopped, unrunnable, and carrying no `python`/`exptrack` prefix so the box couldn't even offer its toggle. A blank command is better than a false one: the box falls back to its "double-click to add command" prompt, and both `notebook.start`/`_auto_start` pass `command=nb_file` — the notebook's **path**, not a launcher: reproducing a notebook run means opening the notebook, and exptrack cannot know whether that is lab, notebook, nbclassic or an editor, so naming one would be a guess printed as an instruction. The dashboard **Reproduce box** can toggle the shown command between this plain `python …` form and the tracked `exptrack run …` form (interpreter-prefix swap, lossless; `_preferredReproForm`/`_reproFormAlt`/`toggleReproduceForm` in `js/core.py`, pref in localStorage `exptrack-reproduce-tracked`). Also, the full script/shell-script source is snapshotted content-addressed into `code_snapshots` (`capture_script_snapshot` → `store_code_snapshot`, deduped by hash, `.ipynb` never stored, capped by `snapshot_max_kb`) and referenced from the `_code_snapshot` param. **(4) A notebook attempt = a run with zero ceremony**: `%exp_new` (and `start(new=True)`) closes the current run and opens a fresh comparable one without a kernel restart — put `%exp_new` at the top of the notebook to make every Run-All a separate attempt. **(5) "See what's best" is one click**: the experiment table's **Sort by metric** selector orders runs by a chosen metric's latest value (`setMetricSort`/`updateMetricSortOptions`, `getFilteredExperiments` `metric:` sort). **(6) Compare shows the edit**: `compare_run_code(conn, base_id, new_id)` returns the code diff between two runs — paired `cell_exec` cell-source diffs for notebooks (notebook JSON is excluded from git diffs, so the cell edit only lives in `cell_lineage`), or the `_code_snapshot` script-source diff for scripts — surfaced on `/api/compare` (`code_diff`) and rendered in the Compare view's **Code changes** panel via the shared word-level diff renderer (`_renderCompareCodeDiff(cd, expA, expB)` → `_lineDiffRows`/`_renderDiffRows`). **It compares each run's *own* source, which is not the only way one run differs from the last**: run `train.py` and tweak `helper.py` and the edit is real and captured (it is in each run's working-tree diff) but belongs to neither run's script — so the panel found no cells and rendered "no code change between these runs", the opposite of what happened, on the one screen built to answer the question. `_cmpWorkingTreeFiles(expA, expB)` (js/compare.js) closes that: both runs' `git_diff` bodies are already on the `/api/compare` payload, so with no extra request it parses each with the shared `_parseDiff`, keys every file by its hunks to find the ones that differ *between* the runs, and reconstructs each file's post-image (context + added lines) so the two can be line-diffed into the actual moved line. Bracketed sentinels are skipped — two runs carrying different `[compacted…]` markers are not two runs whose code differed. The reconstruction covers the changed *regions* of the file, not the whole file, and the panel says so

- **A code-change summary must not hide the change**: `_code_changes` is the param behind the detail view's **Script diff vs. last commit** panel. Both were capped by a bare slice — `[:1000]` and `[:500]` — over the **whole** `git diff HEAD` of the script, and that is the wrong thing to truncate blindly: the diff is against the last *commit*, not the last *run*, so a working tree that has drifted spends the entire budget on lines the user isn't asking about, and the one edit the run exists to test (`warmup = 100` → `200`, `if i >= 1000` → `if i == -1`) falls past the cut. Nothing marked the cut, so the panel rendered identically to "nothing changed" — the single failure mode a code-change summary must not have. **`core/utils.summarize_changed_lines(fragments, max_chars=None)` is the one implementation**, shared by `core/script_snapshot.py` and `capture/notebook_hooks.py` (they had two different caps for the same job). Three properties are load-bearing: **(1)** the cut lands on a fragment boundary, so a summary never ends mid-line; **(2)** truncation is **stated** — `… [truncated — N of M changed lines shown]` names how much was dropped, so an omission is visible and countable rather than inferred from a summary that merely stops; **(3)** an unusable cap (`0`, negative, a hand-edited string) degrades to the default, since a config typo must never be the reason a run records no code changes at all. The cap is `code_change_max_chars` (default 20000). **There is now one git-vs-`HEAD` panel, not two.** The run detail used to carry a script-scoped **Script diff vs. last commit** panel directly above a repository-wide **Uncommitted Changes** panel: same baseline, same file in any single-script project, so the identical edit rendered twice — the upper one a lossier *summary* of the lower one's full diff. Naming each panel for its baseline (the previous fix) made the duplication legible without making it any less duplicated. `_buildCodeSection(codeChanges, exp, diffData)` is now the single **Uncommitted changes** panel, and `highlight.js:_splitDiffByScript(diffText, script)` is what makes one panel able to do both jobs: it splits the working-tree diff into the run's own script and everything else (matching by path suffix on a separator boundary — a bare `endsWith` makes `train.py` match `retrain.py`), each rendered as labelled per-file groups with `+N −M`. Per-file grouping is itself new — `_renderUnifiedDiff` drops every `diff --git` header, so a multi-file tree was one wall of hunks that never said which file any of them came from. **Merging must not cost the script-scoped answer**, which is the trap here: a run whose own script was clean or untracked normally sits in a repo that is dirty *somewhere*, so a naive merge shows a wall of unrelated files and never says the one thing the run was asked about. `_scriptStatusNote` leads the panel in exactly that case (`train.py had no uncommitted changes — it matched commit abc1234`, or the untracked/no-git note), and `_otherFilesHtml` folds the rest behind *Other files in the working tree (N)*. **The fold is collapsed only when the run's own script is itself in the diff**; whenever the script contributed nothing, those files *are* the changes — you ran `train.py` and tweaked `helper.py`, and that tweak is the whole reason the run differs from the last one. The panel this replaced rendered every file expanded, so folding them unconditionally made the one edit that mattered *less* visible than before the merge. `_parseDiff`/`_shortFileLabel` moved from `sessions.js` into `highlight.js` to back this, so the Sessions split-diff and the run detail share one diff parser. Guarded by `tests/test_dashboard_js_integrity.py` (the working-tree diff is emitted exactly once; the script-scoped note survives the merge). The remaining code view is the **What changed** card (this run vs. the previous one, snapshot-based, no git dependency), which stays separate because it is a genuinely different baseline and renders nothing until asked. The two routinely disagree, correctly: a clean tree with two differently-committed runs leaves this panel with nothing of the script's to show while "What changed" shows the real edit. **Its three empty cases are not interchangeable and none of them means "no changes"**, so each one says which it is rather than rendering nothing — an absent panel read as "clean" for a script git cannot even see. `git diff HEAD -- untracked.py` exits 0 with no output, *byte-identical to a clean tree*, so the empty diff alone can't tell them apart: `_script_facts` records a `code_status` (`changed` / `clean` / `untracked` / `no_git`, the untracked check being one extra `git ls-files` run **only** on the empty-diff path and memoized with the rest of the facts), and `capture_script_snapshot` logs it as the `_code_status` param **only** for `untracked`/`no_git`. A clean tree deliberately writes nothing — no `_code_changes` plus a captured commit already means "matched that commit", and a row on every clean run is pure noise on the commonest path there is. **That last inference is why the panel must first establish there *was* a script**, and why the check is ordered ahead of the clean-tree branch in `_buildCodeSection`: `git_commit` is captured for every run inside a repo, script or not, so a notebook run — which has no script and no `_code_status` — fell straight through to "this script matched commit `abc1234`", a confident claim about a file the run never had, in a repo where the notebook might not even be tracked. It reintroduced the exact failure the empty states exist to kill, one case over. The server states it as **`has_script_capture`** on the detail payload (computed from `_script_hash`, which `capture_script_snapshot` writes and nothing else does — `script` itself cannot answer it, since a notebook carries its `.ipynb` there and a pipeline run carries a label), so the client consults a stated fact rather than inferring one from which internal param keys happen to be present (a notebook carries its `.ipynb` in `script` and a pipeline run carries a label, so `script` itself can't answer it); with no captured script the panel does not render at all. Guarded on both sides — `tests/test_code_panel_scope.py` asserts a notebook run writes none of those params whether or not the notebook is committed, and `tests/test_dashboard_js_integrity.py` asserts the clean-tree branch stays gated. **Notebook cells are not in this panel and are no longer stored as params at all**: `_emit_timeline_events` already puts the cell's edit on the `cell_exec` event's `source_diff` as the structured op/line list the Timeline renders with the word-level renderer, so the old `_code_change/cell_N` param was a second, lossier copy of the same edit in the same database — one edit rendered in two places, and a row per edited cell per run that nothing could reclaim (`compact --code-changes` is snapshot-gated and a notebook run has no script snapshot). Runs captured before this keep theirs; the panel ignores them, and `get_export_data` still reads them while now also exporting the script summary under `code_changes["script"]`, which no export had ever included. Guarded by `tests/test_code_change_summary.py` and `tests/test_code_panel_scope.py`. **Reclaimable after the fact**: because the snapshot is the durable record and the summary is derived, `core/storage.compact_code_changes` / `preview_code_change_compact` (surfaced as `exptrack compact --code-changes` and `POST /api/compact` `mode: "code-changes"`) strip the summary to a `[compacted…]` marker — but **only for runs `_runs_with_snapshot` confirms are recoverable** (the `_code_snapshot` param must name a hash whose row is still present; a dangling reference is not a backstop). A notebook-only or pre-snapshot run keeps its summary, and the skipped count is always reported rather than silently implying everything was compacted. It is deliberately excluded from `--deep`, and its marker test matches both the bare and the JSON-encoded (`"[compacted…`) form since param values are JSON-encoded — matching only the bare form silently re-compacted the same row forever. The marker's byte count is stamped **per row in SQL** (`LENGTH(value)`, the same basis the preview sums) — a single aggregate figure stamped into every row named the wrong number on each — and `skipped_no_snapshot` only names runs that actually hold a summary. **`compact`'s git-diff mode must sweep the bodies it orphans**: diffs are content-addressed into `git_diffs` and a run holds a ~45-byte `[ref:sha256:…]` pointer, so replacing the pointer frees nothing on its own — on a project whose diffs were 90% of the database, `compact` reported success and reclaimed **zero** while the bodies sat unreferenced (`clean`'s default path never sweeps them). It now calls `_sweep_blobs` after the UPDATE, which deletes strictly unreferenced bodies so one still held by a run outside the selection or by a session node survives, and its freed figure counts what left the database (inline diffs free their column; a deduplicated body is counted once, not once per run sharing it). `_reclaimable_diff_bytes` gives the dry-run the same number — it used to sum the *column* length, i.e. the pointer, promising ~1 KB where 1.6 MB would go. **`_code_change_selection(conn, exp_ids)` is the one selection**, returning `(stats, eligible)` to both the preview and the compact — `stats["run_ids"]` names the runs actually written, since `eligible` means "recoverable from a snapshot" and a snapshot-backed run may hold no summary at all (the CLI dry-run reported the wider set, announcing "Would compact 50 experiment(s)" beside "1 row(s) in 1 run(s)"): the eligibility scan is the expensive half, and two independent computations can only *happen* to agree, where the shared one makes "the dry-run describes the write" structural (the rule `prune_metrics` already follows). Guarded by `tests/test_compact_code_changes.py`. **Source-loss guard on delete**: `sole_source_holder(conn, exp_id)` / the batch `sole_source_holders(conn, exp_ids)` (one implementation — the single-run form delegates) report whether a permanent delete destroys the last copy of a snapshot blob; the batch form exists because per-run "does anyone else hold this hash?" sees the other runs *in the same doomed batch* as holders, so bulk-deleting the only sharers warned on none of them. Carried on `get_delete_preview["source_only_copy"]` and the bulk-preview payload, rendered through the one `_sourceWarnBox` shell in `trash.js` (`_sourceLossHtml` / `_sourceLossBulkHtml` supply only a headline and an action — the wording of a safety warning maintained in duplicate is what drifts). The check is **best-effort inside `sole_source_holders` itself** — one guard, one fallback shape (`{sole: False, …}`, logged via `debug_log`) for every caller, rather than a divergent try/except per route — so an advisory warning can never break a delete dialog. `get_delete_preview(..., source_check=False)` skips it for the bulk loop, which answers the question batch-aware once instead of paying N discarded full param scans. Both it and `_runs_with_snapshot` read hashes through `_snapshot_refs`, the one generous hash-token scan (mirroring `db._referenced_snapshot_hashes`), so the compaction guard and the sole-holder warning stay superset-compatible with the sweep. **`source_code_storage(conn)`** is the storage-report gatherer (exact bytes: snapshots + un-compacted summaries, split by what reclaims each), surfaced as a "source code" line in `exptrack storage` and a **Source code** section in the Settings storage panel (`/api/storage-info` `source_code`)

- **Logging the numbers after the run is over**: the notebook loop routinely produces the result *after* the run has finished — you run the notebook, close it out, then evaluate and only then have test/train accuracy. Every other logging path needed either a live run (`metric()`) or a run id you had to go find (`exptrack log-metric <id>`), so the numbers most worth keeping were the most awkward to attach. `notebook.log_last(**metrics)` — surfaced as **`%exp_log test_acc=0.93 train_acc=0.98`** — logs onto the active run when there is one, and otherwise resolves the most recent surviving run of *this notebook* via `queries.find_latest_by_script`, resumes it, logs, and finishes it again so it is handed back in the state it was found (not left `running` forever). Three properties are load-bearing: **(1)** the chosen run is always printed, because attaching a number to the wrong run *silently* is worse than not attaching it; **(2)** trashed runs are excluded from the lookup for exactly the reason they can't be a baseline — a run deleted from every list would file the number where the user cannot see it; **(3)** `_parse_metric_assignments` reports a malformed or non-finite token instead of dropping it, since a metric that looks logged but isn't is the worst outcome of the three (non-finite is refused here for the same reason `json_dumps` scrubs it on the way out — `Infinity`/`NaN` are not parseable JSON).

- **A run can name its own baseline (`variant_of`)**: every delta exptrack shows — the "vs previous" strip, the "What changed" card — resolves its baseline *chronologically*, and that is wrong for the commonest loop in the product: re-run one notebook with a different model and "the previous run of this script" is whatever happened to run last, not the run you mean to compare against. A run may therefore declare the run it is a variant of, and that target wins over chronology in **both** resolvers (`queries.get_previous_run` and `find_previous_by_script`, via the shared `_explicit_baseline`) so the strip and the card can never name different baselines. It is stored as the **`_variant_of` param, not a column**: the `_` prefix already keeps it out of run naming, the params table and the param diff, and it needs no migration or `_SCHEMA_VERSION` bump. `_explicit_baseline` re-applies `_BASELINE_WHERE` to the target rather than trusting the link, so a **stale link degrades to chronological** — a trashed or still-running target must not leave the run with no comparison at all, which is strictly worse than the default it replaced. `set_variant_of` refuses a self-link, an unknown target and a one-step cycle (A→B while B→A, after which neither run has a stable baseline). Surfaced as `exptrack variant-of <id> [baseline]` (omit the baseline to clear it), `POST /api/experiment/<id>/set-variant-of`, and a `variant_of` field on the detail payload.

- **Run adoption (no phantom run under `exptrack run`)**: `exptrack run script.py` (`__main__.main`) must create its wrapper `Experiment` *before* the script runs (argparse/savefig/TensorBoard patching + stdout capture all need a live run up front) and injects it as the script's `__exptrack__` global. A cooperative script logs onto that global → one run. But a script written for plain `python script.py` — which does `from exptrack.core import Experiment; with Experiment() as exp:` and ignores `__exptrack__` — would create a *second* run for the same script: the wrapper gets the code snapshot but no metrics, the script's own run gets the metrics, and the same-script diff then floods with `None→value` changes. To prevent that, `__main__.main` calls `experiment.publish_run_wrapper(exp)` to register the wrapper as adoptable; `Experiment.__new__` claims it (once, via `_claim_run_wrapper`, which sets `_adopted=True`) and returns the wrapper instead of a fresh instance, and `__init__` short-circuits when `self._adopted` so the wrapper isn't re-created. Adoption is deliberately narrow: **only a bare `Experiment()` (no args/kwargs) adopts** — a script passing its own `name`/`params`/… clearly wants its own run and is never silently merged (a sweep loop keeps independent rows) — and **only the first** construction adopts (the wrapper is claimed once). `Experiment.resume` uses `object.__new__` so it bypasses adoption; notebooks and plain `python` never publish a wrapper, so both are unaffected. Because an adopted `with Experiment()` block finishes the wrapper itself, `__main__`'s post-run finish/fail calls are all guarded by `if not exp._finished:` (a second `finish()` raises "Cannot finish twice"). **The arg-passing-sweep case is handled by trashing, not adoption**: a script that constructs Experiments with explicit args (a sweep) deliberately does *not* adopt — merging would silently drop each run's distinct name/params — so those runs get their own rows, but the wrapper is then left metrics-less. `Experiment.__init__` flags this: while the wrapper is still published (`_run_wrapper` non-None), any *non-adopted* construction of a different `Experiment` sets `_run_wrapper._had_foreign_child = True` (the wrapper's own `__init__` runs *before* `publish_run_wrapper()`, so it never flags itself). At finish, `__main__._maybe_trash_phantom_wrapper(exp, resume)` soft-deletes the wrapper (`trash_experiment` → Trash, recoverable) when it saw a foreign-built run **and** logged no metrics of its own — so an explicit-args sweep under `exptrack run` no longer leaves an empty phantom row. **The "no data of its own" test counts artifacts as well as metrics**, because savefig/auto-output capture stays pointed at the wrapper for the whole script: a sweep that plots per iteration without logging a metric leaves its only artifact rows there, and trashing on the metric count alone took the plots out of the Images tab with no hint. The rows every wrapper gets for free are excluded from that test — the `output_dir` row and the `[log] stdout.log`/`[log] stderr.log` rows the stream tee registers — since counting those means no wrapper is ever a phantom and the trashing silently stops happening at all. Guarded: a resumed run (`--resume`) and a hybrid wrapper that logged its own metrics are never trashed. `Experiment.resume` uses `object.__new__` so it bypasses adoption; notebooks and plain `python` never publish a wrapper, so both are unaffected

- **Every run snapshots its own source, however it was started**: `capture_script_snapshot` used to be called only from `__main__`, i.e. only under `exptrack run`. A script run as plain `python train.py` building its own `Experiment()` — a fully supported pattern, and the one the **Run adoption** pattern exists to serve — therefore recorded no source at all. The symptom was a contradiction on screen: the "vs previous run" strip reported `code changed`, since that comes from the repository-wide `_run_code_signature` and needs no snapshot, while the Code-changes panel directly beneath it had nothing to diff and said no code was captured. So two runs that had each diverged from the committed file *and from each other* could not be diffed against each other — exactly the run-to-run comparison the panel exists for. `Experiment.__init__` now calls `_maybe_snapshot_script()` whenever the run has a real script file, so the source is captured however the run started; label scripts (`run-start --script pipeline`) and notebooks are skipped, having no file and their own capture paths. **`Experiment._maybe_snapshot_script` is the single entry point** and `Experiment` owns the idempotence flag (`_script_snapshotted`, a class-level default so the `object.__new__` resume path is safe): `__main__` calls that method rather than reaching past it into the capture layer, because `Experiment.resume` bypasses `__init__` and cannot know the path this invocation resolved. Whichever call runs first wins, and the second no longer writes a duplicate `cell_exec` timeline event and a second set of params. The module itself lives in **`core/script_snapshot.py`**, not `capture/` — `core.experiment` calling it on every run made the old `core → capture` import a real, permanent runtime dependency, the same layering inversion moving `dataset.py` into `core/` was meant to end, and a function-local import only hides that from the import graph. Its expensive work is memoized on `(path, mtime, size)` so a param sweep does it once, not once per run

- **"What changed" card (Overview tab)**: sits at the top of every run's Overview, before the params/metrics grid — auto-diffs this run's params (and, now, metrics) against the previous experiment that used the **same script** (chronologically prior, `find_previous_by_script(conn, exp_id)` in `core/queries.py`, exposed via `GET /api/experiment/<id>/prev-by-script` → `api_prev_by_script`), so the "tweak one line, rerun" loop shows what actually differs — and what it did to the numbers — without the user ever renaming a run (the `name_is_auto` pattern above helps after the fact; this helps at a glance, every time). Only **changed** params are listed (`key | previous → this run`, reusing the `.diff-added`/`.diff-removed` styling from Compare); if nothing differs, a note says so explicitly ("same config, different attempt") — itself a useful signal that a rerun didn't change what was tested. A second table below it lists **changed metrics** (`key | previous → this run | delta`, delta colored/arrowed via the shared `metricDelta(before, after, key)` helper in `js/core.py` — also used by Compare's metrics table so the two never drift; the colour is polarity-aware, see the **Polarity-aware metric deltas** pattern), built from `get_metrics_last(conn, exp_id)` (last-logged value per key, across sources) called for both the previous and current run and returned on the same payload as `metrics`/`cur_metrics`; unchanged metric keys are omitted, and the table is simply absent when nothing changed. A **Compare** button opens the full pair-Compare view pre-populated with the previous run and this one (`compareWithPrevious`, mirrors `compareSelected`'s dropdown-populate-then-`doCompare()` sequence). No card renders for a script's first run (no earlier experiment to diff against). Below the two tables sits a lazy **Code changes** section (`loadWhatChangedCode(prevId, curId, btn)` → `GET /api/compare?id1=&id2=`, rendered with Compare's own `_renderCompareCodeDiff`, so the word-level diff renderer and its collapsed/empty states are shared, not reimplemented): params and metrics answered only half of "what did I do differently?", since the most common edit in the tweak-one-line loop is to the code. It's fetched on click rather than with the card (a script snapshot can be hundreds of KB and most visits don't open it), and when neither run captured code it says so instead of rendering an empty box. The internal-param filter is shared with Compare via **`isUserParamKey`** in `js/core.py`, and the rule is the **`_` prefix**, not a list of known keys — every internal param exptrack writes is `_`-prefixed, so an enumeration silently misses each new one. It did: `_code_snapshot` (a JSON blob naming the snapshot hash and the script's absolute path) wasn't on the list, so any run whose script had been edited showed that blob as the *headline row* of "What changed", burying the hyperparameter the user actually changed. The same fix removes it from the Overview's Params table (`regularParams` now ends in an `isUserParamKey` branch) and from the Compare pickers' option labels

- **Every way a run can end is an outcome, including Ctrl-C**: `__main__` caught `SystemExit` and `Exception`, and `KeyboardInterrupt` is neither — so interrupting training (one of the commonest ways a run ends) fell through both handlers and left the run `running` with no duration, no error and its log files unclosed. A run stuck `running` is excluded from every baseline by `_BASELINE_WHERE`, so it vanished from the comparison loop entirely until `stale` swept it 24 hours later. The wrapper now catches it, restores the streams, records the run and exits **130** (the conventional SIGINT status, so a job script can tell "I stopped this" from "it crashed"). A deliberate interrupt and a crash are different facts, but they are both "this produced no result", so the **status stays `failed`** and the distinction is a `_interrupted` param beside it — a fourth status would have to be understood by ~50 call sites, every filter and every cleanup path, to express something only the *reason* line needs to say. The outcome is recorded by **`Experiment.__exit__`** as well as the wrapper — `KeyboardInterrupt` is a `BaseException`, but `with` still calls `__exit__` for it, so a `with Experiment()` block under a plain `python train.py` was recording a crash with an empty message. `__main__` keeps only the exit code

- **The mtime window is not ownership**: `_auto_detect_outputs` filtered files by "modified since this run started", which is true of every *other* run in flight at the same moment. Verified with two concurrent runs: whichever finished first registered the other's weights *and* its stdout/stderr logs as its own artifacts — so a SLURM array or two terminals cross-contaminated silently. It also defeated the phantom-wrapper trash, because a sweep wrapper looked like it had "data of its own" once the scan had swept its children's checkpoints onto it. The scan now skips paths registered to another run and anything under another run's claimed output directory (`claimed_output_paths(exclude_id=…)` — the same ownership rule the delete path uses, so "protected from deletion" and "not mine to claim" can never disagree)

- **Zero-friction means whichever way the script was launched**: the capture patches were installed only by `exptrack run` and the notebook extension, so a plain `python train.py` containing `exp = Experiment()` captured **no parameters at all** — and moving one script between the two launchers made every parameter appear as a change in the "What changed" card, because one side had them and the other didn't. The run object arms them itself (`_install_capture_patches`), which is also the right place: the patches exist to feed *a run* — `exptrack run` calls the same method with `force=True` rather than keeping a second copy of the list, since the only case the constructor cannot cover is a resumed run (`Experiment.resume` bypasses `__init__`). The auto-**naming** policy moved for the same reason: `Experiment.refresh_auto_name` owns both guards (a resumed run keeps its name and output dir; a user-named run keeps its name), which the notebook path had copied only half of. Two guards. Raw-argv capture only fires when `sys.argv[0]` resolves to this run's own script, because `sys.argv` is process-global and a run created inside a test runner, a REPL or any host program would otherwise record that host's flags as hyperparameters. And the shell pipeline opts out (`auto_capture=False`): it parses its own `--key value` args, so argv capture there would store `--resume` and `--study` as user parameters

- **A run's `script` is its identity, so it must not vary with its inputs**: `run-start` set `script` to `"exptrack run-start --lr 0.5"` — the whole invocation, param values included — so two runs of the same pipeline never shared a script and vs-previous, the "What changed" card, `--resume latest` and duplicate detection silently never fired for interactively launched pipeline runs. Identity is now the calling shell script, else the stable `--script` hint, else a bare `exptrack run-start`; the full invocation still lives in `command`, which is what it is for. Relatedly, `name=` is what marks a run *user-named*, so passing a generated name into it (as `run-start` did) made every pipeline run register as deliberately named and dropped it out of the auto-name badge, the bulk-rename filter and the un-renamed count — `naming_hint=` names the run without making that claim

- **`duration_s` means one thing, whichever path finished the run**: `Experiment.finish` recorded `time.time() - self._start`, which on a resumed run is the *final session's* wall time and silently discards every earlier session; `run-finish` recorded elapsed-since-creation, which for a job resumed the next morning counts the night as compute time. Both now accumulate: the definition is "wall time this run was actually running, summed across resumes", and a resumed finish adds this session to whatever is already stored. **`core/db.accumulated_duration` is the one implementation**, because there are five writers, not two — `queries.finish_experiment` (the dashboard's "mark done"), `exptrack finish` and the `stale` sweep each had their own elapsed-since-creation copy, so how long a run took depended on which surface ended it

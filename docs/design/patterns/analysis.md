# Analysis over a set of runs

The parameter matrix, rankings, effect summaries, duplicate detection, the primary metric and the pinned reference run.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **What varies is a property of the set, not of a stored grouping**: the experiment list answers "what did I run?"; `core/param_study.py` answers what comes after twenty runs exist — which parameters I actually varied, what values I tried, and whether I have already run this configuration. It works over an **explicit list of run ids**, posted by the client, rather than a study name: filter to last week's runs and `lr` may be constant, widen to the project and it varies, so deriving it from a stored grouping would answer a different question from the one on screen. That is also why the endpoint is `POST /api/param-study` despite being a read — the id set is the input, and a query string would cap it well below the list's 1000-run page. Three rules are load-bearing. **(1) A parameter missing from a run is a variation, not a blank** — run A passing `--dropout 0.1` while run B never passed it is a real difference in what was tested, and adding a flag partway through a sweep is the commonest way that happens; it is represented by the `MISSING` singleton rather than `None`, because `None` is a value a run can genuinely log and collapsing the two would report "I tried None and 0.1" for a parameter half the runs never had. **(2) Values are compared after normalization and displayed as captured** — the same `lr=0.01` arrives as a float through argparse and as the string `"0.01"` through the shell-pipeline CLI, so comparing raw would report two values for one setting and, worse, make the duplicate detection built on the same `_norm` actively misleading by calling two identical configurations different. `_norm` collapses numeric spellings and `true`/`True`, normalizes lists/dicts recursively (order-preserving — a list param is ordered data, not a set), and keeps **bools distinct from 0/1**, since `epochs=1` and `epochs=True` are not the same intent even though `--flag 1` and `--flag True` are. **(3) Internal params never surface**, by the `_`-prefix rule (`is_user_param_key`, mirroring `isUserParamKey` in `js/core.js`) rather than an enumeration — an enumeration silently misses each new internal key, which is exactly how `_code_snapshot` once became the headline row of the "What changed" card. It matters twice here: `_code_snapshot` names a per-file hash and always differs, so counting internals in `config_fingerprint` would mean no two runs are ever duplicates. Counts always sum to the run count (every run contributes exactly one entry, `MISSING` included) so a value's share of the set reads straight off `count`, and `varying` is ordered most-distinct-values first since that is the parameter the sweep was actually over. The route resolves id prefixes and **reports unknown ids rather than dropping them** — an analysis quietly computed over fewer runs than were selected would misreport what varies, which is the one thing these views exist to answer. **`utils.LEGACY_INTERNAL_PARAM_KEYS` is the one exception to the prefix rule and it exists because one key predates the convention**: `Experiment.fail()` writes the failure message as the un-prefixed `error` param (backward compat — `_error_traceback` got the prefix when it was added later), so every failed run in a set contributed an `error` *column* to the matrix, and since each message differs, two runs that failed the same way were not detected as the same configuration. It lives in `core/utils.py` beside `is_user_param_key` rather than in whichever module noticed it — which keys are exptrack's own is knowledge about the param namespace, not about parameter-study analysis. **Every reader that surfaces params to a user now goes through the shared predicate** — `queries.py` (compare, detail, export/CSV), `cli/inspect_cmds.py` (`show`, `compare`) and the JS `isUserParamKey`, which carries the same legacy exception (`tests/test_primary_metric.py`-style mirroring: the constant is spelled in both and the comment in each names the other). The readers that deliberately keep a bare prefix check are the ones filtering exptrack's *own* namespace rather than a user-facing list — `naming.py` (never name a run after a bookkeeping key), `dataset.py`, `capture/*`, and `write_routes/params.py`'s write guard, where `error` is a key the user may legitimately edit. **`build_matrix`** is the view on top: one row per run, one column per varying parameter, the primary metric pinned, the best row marked, and duplicate configurations flagged per row (`classify=False` skips that classification — it costs a fingerprint per run and `parameter_effects` reads none of it). **The ranking rule lives server-side only**: both `best_row_id_final` and `best_row_id_best` ride on the payload, so switching the basis is a client-side lookup rather than a second implementation of the rule in JS, where a tie-break could silently disagree about which run is best. **`code_fingerprint` answers from the caller's already-loaded params** when it can — the snapshot is in `_code_snapshot`, and re-querying for it was a round trip per run (200-400 on a matrix request); only a notebook run, which has no snapshot, falls through to the cell-hash query. Its exclusions follow `_BASELINE_WHERE`'s reasoning and are **stated, never silent** (an `excluded` count per reason) — `running` runs are hidden by default (metrics still moving, so a rank against them doesn't reproduce), `failed` runs are **shown** by default and marked (a config that failed is a result of the search; hiding it invites re-running the thing that already broke), and a run with no value for the primary metric is kept — it is still a configuration that was tested — but can never be the best row. `rank_by` (`final` | `best`) is on the payload and **both numbers ride on every row**, so switching is a re-render rather than another request. Client side, `_matrixIds()` calls `getFilteredExperiments({includeFailed: true})`: the matrix carries its own *Show failed* control, and the experiment list's `showFailed` toggle would otherwise strip those runs out upstream, leaving the matrix's own checkbox checked and doing nothing

- **Ranking a search, and knowing when it stopped paying**: the parameter matrix marks the best row, which is right for reading a sweep row by row and wrong for the two questions that follow — "what are my best five configurations" (sorting and counting by eye) and "am I still making progress" (nothing in a table says it at all). `core/leaderboard.py` answers both, and both are **views over `build_matrix`** rather than parallel implementations: which runs are eligible, how exclusions are counted, which metric the set is judged by and how ties break must have one answer across every ranking surface, since a "best run" panel that disagreed with the matrix's own best row over the same runs would make both untrustworthy. The cost — both load the set's parameters — is deliberate: what a top run *is* is its configuration, and the point of the progress view is seeing what changed at each improvement. **`consensus_metric` is the shared "which metric is this set judged by" rule** and it lives in `param_study` beside the analysis that needs it. The **most common** key wins, not the first one seen: rows arrive newest-first, so a project that switched from `loss` to `val_acc` could have one legacy straggler define the axis and exclude every other run from the ranking. Ties break toward the key that sorts first so the answer is stable rather than dict-order dependent, and a `min` goal wins a disagreement (ranking a loss as if larger were better is the more damaging way to be wrong). `scored_values` then drops runs judged by a *different* key — two numbers measuring different things share no ranking, axis or best row — which is a real fix to the matrix, whose `_best_on` used to rank across every run regardless of key. `off_metric_runs` counts them so the exclusion is stated. `top_runs` returns **`unscored` separately rather than dropping it**, and the client counts "logged nothing" apart from "measures something else" (`off_metric` per row) because the two call for different responses and both render as a blank. `best_so_far` is ordered by `(created_at, id)` **ascending regardless of how the client sorted** — a best-so-far computed over a metric-sorted list is monotonic by construction and means nothing — keeps unscored runs in place carrying the record forward (dropping them compresses the x-axis and makes a 30-run search look like it converged in 12), and attaches to every improving run the parameter diff against the run that previously held the record, since which edit moved the number is the reason to open the view. `since_improvement` counts every run that followed, scored or not. Client side the three sections below the matrix (Top runs, Progress, Effects) share one lazy-section mechanism (`MX_SECTIONS` + `_mxSection`/`toggleMxSection`/`loadMxSection` in `js/matrix.js`) — collapsed by default and fetched on open, since each needs a second server pass over every run's metric points and most visits want the table.  **The client half of the rule is one function**: `consensusMetricKey` in `js/core.js`, used by both the Result column's sort and the filmstrip's badge — it must be derived client-side (the set is whatever the list is filtered to, which the server never sees), but two copies of it would let the two surfaces label the same list with different metrics. **`build_matrix(primaries=False)`** is the escape hatch for the trade-off view: it names both of its own axes, so resolving the set's primary metric would be a config read, a `resolve_spec` per run and a windowed pass over that metric's points, all discarded. The cheap DISTINCT scan of which keys each run logged still runs and comes back as `metric_keys`, because that view *does* need it for its axis pickers — reading the same map is also what keeps the picker offering keys over exactly the run set the frontier was computed on. `top_runs`/`best_so_far` read `matrix["metric"]` rather than recomputing the consensus, which is what makes "the top run" and "the matrix's best row" the same run by construction. Client side, only the sections the server orders by the rank basis reload when it changes (`rankDependent` in `MX_SECTIONS`) — each request re-runs the whole matrix build, and `parameter_effects` always scores on the final value, so reloading it returned byte-identical data for a full param-load-and-analysis pass. The progress chart is a **stepped** line: the record genuinely holds flat between improvements, and interpolating it would draw a climb that never happened, with every run's own value plotted behind it so the spread of what was tried stays visible (a record line alone reads as steady progress)

- **Descriptive means descriptive: the effect summaries name what they cannot separate**: `parameter_effects` reports, per varying parameter, the values tried, the runs per value, and the best/median primary metric, plus the points for a scatter (numeric) or strip plot (categorical). The runs were not randomized, the parameters were usually not varied independently, and the sample per value is a handful — so the module's whole job is delivering that summary *without* it reading as importance. Three mechanisms do that, and the first is the one that matters. **`_aliased_params` finds parameters that split the runs identically** (`_partition` compares the set-of-sets of run ids, so it catches exact co-variation regardless of the values themselves) and a confounded parameter is **not charted at all** — the panel renders a note naming the partner and saying which one to vary alone. Captioning it was not enough: a scatter titled "lr vs val_acc" is read as an answer whatever sits underneath it, so the chart has to be absent, not annotated. Only *exact* co-variation is reported; quantifying partial correlation would start making the causal claims this deliberately avoids. **`single_run_per_value`** marks a parameter whose every value was tried once — "best" and "median" of one run are that run, and presenting them as a summary invents a distribution nobody measured (the client renders those medians dotted and hover-explained rather than as plain numbers). And **a run with no value for the metric still counts** toward `count` while being excluded from `n_scored`, so "6 runs tried lr=0.1" and "4 of them produced a number" stay separate facts. Runs whose primary metric resolved to a *different key* are excluded from scoring entirely rather than mixed in — two numbers measuring different things do not share an axis. `group_by` adds a second parameter's value to each point for colouring, validated against the varying keys (an unknown key is ignored, never silently applied) and never the axis parameter itself. Surfaced as `POST /api/param-effects` and a collapsed, lazily-fetched section under the matrix — the summaries need a second pass over every run's metric points and most visits want the table

- **Three answers to "I already ran this", and they lead to opposite actions**: a duplicate flag that says only "you ran this before" is worse than none, because the three cases it merges want different responses — an **identical** rerun is wasted compute, **same params / different code** is the change-one-line loop working correctly (calling that waste is actively wrong), and **same params and code / different dataset** is the one that silently invalidates a comparison. `classify_duplicates` groups by the normalized parameter fingerprint (`config_fingerprint`, built on the same `_norm` as everything else, so a config captured through argparse and through the pipeline CLI is one configuration) and then splits each group by two facts that were **already captured** — `code_fingerprint` (delegating to `queries._run_source_identity`, the run's own snapshot or cell hashes, *not* the repository-wide `_run_code_signature`, which moves when any tracked file changes and would report "different code" for a byte-identical rerun) and `dataset_fingerprint` (the `_dataset_manifest` param `Experiment.finish()` already writes). Nothing new is collected. **`_agreement` has four outcomes, not three**, and the fourth is what makes the feature usable: `same` / `differs` / `unknown` (*some* member lacks the fact — so the group can only be shown to agree on what was captured; it never outranks `differs`, since two members that demonstrably differ differ whatever a third failed to record) and **`absent`** (*no* member recorded it). `_duplicate_kind` then treats `absent` as "nothing to differ on" for the **dataset** and as missing evidence for the **code**, and that asymmetry is deliberate: a run may genuinely read no data files, so "neither recorded a dataset" is a complete answer, but every run executes *some* code, so "neither captured source" is not. Without it, a project whose scripts take no data path saw every duplicate degrade to `params_only` and the one verdict the feature exists to deliver never appeared. `find_equivalent_runs` backs the finish-time notice (`Experiment._warn_if_duplicate`) and is deliberately bounded — the most recent 200 surviving runs of the same script — because it sits on the run path and a sweep that has run 5000 times needs no exhaustive scan to be told the config is a repeat. The notice is **one stderr line, never a prompt and never a refusal**: re-running a configuration is frequently deliberate (a seed check, a flaky result, a new machine), so blocking on a heuristic would be wrong; it is skipped for resumed runs, gated by `warn_duplicate_runs` (default true), and wrapped so an advisory can never break a finish

- **One primary metric, four levels of saying so**: every surface that ranks, summarizes or compares a run needs one answer to "what is *the* metric here?", and each one used to improvise — the filmstrip took the first metric present on any run, Charts rendered every key, the table had a sort selector. `core/primary_metric.py` is the single answer, resolved **run override → study override → project default → heuristic**. The first three are *configured*; the heuristic is a guess and runs only when nothing has been said, picking from the run's own keys with a `result_types` match preferred and `sorted()` as the tie-break (a guess that changes between requests is worse than an arbitrary one). Two rules are load-bearing and each has a test. **(1) A configured metric is never silently substituted** — a run that never logged the project's `val_auroc` reports it with `missing=True` and no value, rather than falling back to whatever it did log: a table column whose rows each mean a different metric reads as comparable when it isn't. A *heuristic* key can never be missing (it was chosen from the run's own metrics); a run with no metrics at all gets `key=""` / `source=None`, which is a third distinct state, not a synonym for either. **(2) The answer says where it came from** — `source` is `run`/`study`/`project`/`heuristic`, so the UI can render a guess as a guess and offer to make it explicit. Storage follows the existing conventions rather than adding a table: the run override is the `_primary_metric` param (exactly as `_variant_of` is — the `_` prefix already keeps it out of naming, the params table and the param diff, and it needs no migration or `_SCHEMA_VERSION` bump), while the study and project levels live in `config.json`, because **a study is not a row anywhere** — it is a name inside each run's `studies` JSON list, derived at read time by `get_studies`, so there is no per-study record to hang an override on. `goal` (`max`/`min`) is stated by a configured level or inferred by `goal_for_key`, which **mirrors `metricGoodDirection`/`LOWER_IS_BETTER_RE` in `js/core.js`**; `tests/test_primary_metric.py` parses the JS regex and asserts the two name lists are equal, since a one-sided edit would colour the same metric as an improvement on one end and a regression on the other. Once resolved, `goal` rides on the payload so the client reads it instead of re-deriving it for the primary metric (the localStorage per-key override still governs *other* metrics' deltas). **The run-level override is read in bulk** (`run_primary_metrics`, or straight from a caller-supplied `params_by_exp`): resolving it per run made `list_experiments` issue a query per listed run — up to 1000 per request on the dashboard's polled path — when `get_params_batch` had already loaded `_primary_metric` for every row and thrown it away. `_value_rows` groups its lookup by **`(key, goal)`, not by key** — two runs can resolve one metric with opposite directions (one declares `min`, the other takes the heuristic) and "best" is meaningless for a group that disagrees on which end is best — and computes final and best in one indexed pass per group using two `ROW_NUMBER()` windows, chunked at 400 ids: this runs once per experiment-list request over every listed run's points, so a correlated subquery would be quadratic in points-per-metric exactly where that has already bitten once (`_latest_metric_rows`). "Final" orders by `COALESCE(step,-1) DESC, ts DESC, rowid DESC`, matching `last_metrics`, so a step-less series resolves by insert order rather than tying at NULL; "best" breaks ties toward the **earliest** step, since the first time a run reached its best is the more useful of two equal points. **Surfaced throughout the UI rather than only on the payload**: a sortable **Result** column in the experiment table (`primary` in `ALL_COLUMNS`, on by default, rendered by `_primaryCellHtml`) that keeps the four states distinct — a value, `not logged` for a *configured* metric this run never recorded, `--` for a run with no metrics, and a dotted `primary-guess` underline for a heuristic pick; the run detail's header line (`_primaryMetricSummary`, which states the source and tags a guess); the Charts tab and Overview preview opening on it (`_defaultChartKey`, reading the already-loaded list row rather than adding state or a request); and the filmstrip (`_filmstripMetricKey`), which is the surface the pattern was written about. **Sorting the Result column ranks only the runs on the set's own metric** — `_consensusMetricKey` in `js/table.js` mirrors `param_study.consensus_metric` and off-metric runs sink via `_cmpMissingLast`, because 0.11 of a loss and 0.92 of an accuracy have no order between them and interleaving them yields a ranking that looks authoritative and means nothing. Also `exptrack primary-metric <key> [--goal max|min] [--study NAME] [--run ID]` (the level is chosen explicitly rather than inferred — writing the wrong one leaves a setting that appears to do nothing because a more specific level shadows it), and as `primary_metric` on both `list_experiments` and `get_experiment_detail`

- **Two objectives, and the honesty a frontier needs**: ranking assumes one number, and real choices routinely have two that pull against each other — accuracy against latency, F1 against model size, recall against false positives. No single ranking expresses "these are the runs where you cannot do better on one without giving up the other", so `leaderboard.pareto_front` computes the non-dominated set over two caller-named metrics. **Both axes are named by the caller**: the second objective cannot be guessed, and picking one would invent the trade-off the user is trying to examine. Four things carry it. **(1) The goal is stated and switchable, because getting it wrong inverts the entire frontier.** Each axis defaults to the shared `goal_for_key` name heuristic — which reads `latency_ms` and cannot read `size_mb` — so both resolved goals ride on the payload and render as per-axis selectors rather than being applied invisibly. Internally the min-goal axis is negated for the sweep only; the **values reported are always as recorded**, since flipping the displayed number to simplify an algorithm would put a negated loss on screen. **(2) Domination requires a strict win.** `_dominates` is "at least as good on both, strictly better on one", which keeps two runs that scored *identically* both on the frontier — neither beat the other, so calling either dominated is a claim the data does not make — while a tie on one axis with a strict win on the other is still domination. **(3) A run missing either metric cannot be placed at all**, and comes back as `unplaced` with the keys it lacks: on a chart an absent point and a point that was never measured look identical, and the second is the one that changes what you do next. **(4) The frontier describes the runs, not the space** — a run sits on it when nothing *in this set* beat it on both, which includes being the only run tried in that region, and the caption says so (the same discipline as `parameter_effects`). The sweep is O(n log n): sort best-x first, keep the best y seen, and a point that fails to improve on it is dominated by whichever run set it — which also names *a* dominating run for free, more useful than a bare flag. `frontier` comes back ordered best-x first so the client draws the line without re-sorting. Values come from **`primary_metric.metric_values`**, the public door onto `_value_rows` for callers that know their key: reusing that windowed query rather than writing a second one keeps "final" and "best" meaning exactly what they mean everywhere else. `available_metrics` ranks the pickable keys by how many runs logged each, and rides on the payload even when no axes are chosen, so the empty state is a working chooser rather than a second differently-shaped request

- **A pinned reference is a target, not a lineage**: exptrack already resolves a baseline for every run chronologically — the previous run of the same script, overridable per run by `_variant_of` — which answers "what did I change since last time". That is a question about *lineage*, and it is the wrong answer to the one a parameter search asks constantly: "is this better than the thing I am trying to beat?", where the comparison point is one fixed run (the production model, the published number, the config everything else varies from). `core/reference.py` is that second baseline and it is kept **deliberately separate** from the first — a run declares what it descends from, the project declares what it is measured against — because folding them together would mean pinning a reference silently rewrote every run's "what changed since last time" and clearing it silently rewrote them back (`tests/test_reference.py` asserts `get_previous_run` is untouched by a pin). Three rules carry it. **(1) There is no implicit chain.** Resolution is study level → project level and *stops*; it never continues on to "the best run so far" or "the previous run", because a baseline that moves on its own as data arrives is one you cannot reason about — the user's own constraint on this feature. If nothing is pinned there is no reference, and the strip is absent rather than showing a substitute. **(2) Every surface says where the choice was made.** `source` (`study`/`project`) and `study` ride on every payload and render as "set for this project" / "set for study *sweep-a*" — a delta whose baseline the reader has to guess is the failure the whole feature exists to avoid, so there is no state that renders a bare number. **(3) A broken reference is stated, never silently absent.** `resolve` returns the entry with `stale` = `STALE_MISSING` or `STALE_TRASHED` (kept apart because one is restorable and the other is not) plus the configured id and level, so the message can name what was set and where. This is the opposite of `_explicit_baseline`'s silent degradation, and correctly so: *that* degrades to a chronological baseline that still works, whereas here there is nothing to degrade to, so silence would read as "no reference set" and hide that the comparison the user has been reading stopped happening. `set_reference` refuses an unknown or trashed run for the same reason — a typo'd id stored now surfaces later as a stale reference, which is a worse way to learn about it. Storage mirrors `primary_metric` (`reference_run` / `reference_run_by_study` in `config.json`) because a study is not a row anywhere. Client side the two strips share **`_vsChipsHtml(d)`** — the polarity-aware colouring and the precision-widening are stated-comparison logic that must not exist in two copies — and `delta_vs_reference` reuses `queries.diff_runs`, so the two strips differ *only* in which baseline they name. The header pin (`_referenceBtnHtml`) offers no unpin for a run that is the reference by way of a **study** setting: the button would clear the project level and appear to do nothing, since the study level still shadows it

- **One name for one measurement (`core/metric_alias.py`)**: every surface that matches metrics matches them by *string*, and two models rarely agree on what to call a number — one logs `val_acc`, another `accuracy`, a TensorBoard writer contributes `val/acc`. Matched by name those runs shared no metric at all: the compare table was two rows of `--`, the reference strip reported no overlap, and `consensus_metric` excluded one model wholesale rather than admitting it could not compare them. That is the single biggest obstacle to comparing different models, and it is **not inferable** — only the person who named them knows they are the same thing — so it is configuration (`metric_aliases`, canonical name → the spellings that mean it). Three rules. **(1) Canonicalization is display-level, never storage.** Rows keep the key the run logged; removing an alias gives the original keys back and nothing recorded is rewritten or lost. **(2) Matching is exact after normalization, never fuzzy.** Case, `-`/space → `_`, and the path prefix in `train/loss` are normalized (`utils.normalize_metric_key`, shared with `goal_for_key` rather than copied, so the two agree about what "the metric's name" is — two copies drifting apart would stop aliases resolving while polarity still matched, with nothing failing to say so); a heuristic that guessed `val_acc ≈ val_accuracy` would eventually merge two metrics that are genuinely different and quietly average them, which is worse than not comparing at all. **(3) A merge is reported.** `canonical_groups` gives every surface the spellings it folded, because a merge the user cannot see is indistinguishable from a metric that was silently dropped — `get_multi_compare` returns `merged_metric_keys` for exactly that. An unusable map degrades to no aliasing (the documented config invariant): a hand-edited file must never be the reason a comparison stops working. Applied at **every** read boundary — `get_latest_metrics`, `get_latest_metrics_batch`, `get_latest_metrics_with_source_batch` (and so `list_experiments`), `last_metrics`, `get_multi_compare`, `get_metrics_series`, the session tree's per-node metrics — rather than at each consumer, so a new surface is aliased by construction. **Missing one boundary is not a partial feature, it is an inconsistent screen**: while `get_metrics_series` returned raw keys the Compare table merged `accuracy` into `val_acc` and the training-curve overlay *directly beneath it* silently dropped that model's curve; while `get_latest_metrics_with_source_batch` did, the two models resolved **different primary metrics** (`loss` and `accuracy`), so the effect summaries counted one model's runs as off-metric and scored none of them — the ranking layer still split the models the config had just joined; and while `param_study._metric_keys` did, the matrix printed one model's *accuracy* under a column headed `LOSS`, because that column is the **set's** metric while each cell is the **run's** own. **Canonicalizing a name obliges you to fetch by every spelling of it** (`metric_alias.spellings_for`): the rows carry what the run logged, so a value query on the canonical name alone finds nothing on precisely the runs the alias exists to include, and the metric reads as `missing` — the failure mode is not "no alias" but "the model disappeared from the ranking". Where the value is a whole series, or a value carried with its source, the collision rule differs from `merge_metric_map`'s later-wins: `canonicalize_run_keys` **skips the rename** when two spellings collide inside one run, since dropping one there loses points rather than choosing between two readings of one number

- **Duplicate detection has a model dimension**: `_duplicate_kind` takes `(code, dataset, script)` and `script == differs` outranks both other axes, because `model_a.py --lr 0.01` and `model_b.py --lr 0.01` are not a repeat in any sense the feature exists to report — they are two models that happen to share a hyperparameter configuration, which is the *normal* shape of a cross-model comparison. Reporting it as "you already ran this" told the user to skip the second model. The script is loaded per group (`_scripts_by_exp`, an unrecorded script becoming `None` so it flows through `_agreement` as "not captured" rather than as evidence of a match), and `find_equivalent_runs` requires script equality **in both directions, including the empty case** — dropping the filter when the run had no script made a script-less run a candidate duplicate of every script in the project, so a notebook was told it repeated some unrelated model's configuration

- **A change surface must use the same equality the grouping does**: `diff_runs`, `leaderboard._param_changes` and `cli compare` compared *raw stored* values while `param_study` groups by `_norm`, so the same `lr=0.01` captured as a float through argparse and as the string `"0.01"` through the pipeline CLI read as a change — and `best_so_far` credited a record improvement to an edit that never happened. `param_study.params_differ` is the public form of that equality and all three now use it; `diff_runs` also reports **decoded** values, since it describes settings, not storage (the display used to read `'0.01'` → `'"0.01"'`). The same discipline covers polarity: `cli/inspect_cmds._delta_is_better` is the one rule for `compare` and `watch`, which previously coloured green-when-bigger and green-when-smaller respectively — the same falling loss read as a regression on one surface and an improvement on the other

- **A still-running reference is allowed but stated**: pinning a run whose metrics are still moving is legitimate (a long training run is a real target), but it is exactly what `_BASELINE_WHERE` excludes from *chronological* baselines, so `set_reference` returns a `warning` and the CLI prints it once. The alternative — refusing — would block a real workflow to protect against a fact the user can simply be told

- **A descriptive panel still has to say what it found**: the per-parameter effects panel is the section a sweep is actually run for, and it was the last of four, introduced as "What each value was worth" in 12px muted type — a topic, in the weight of a table caption. It also could not be read on the case it exists for. Hyperparameters are swept multiplicatively (`lr` over 0.0001, 0.001, 0.01), and on a linear axis two of those three values land inside the first 10% of the plot with every point stacked against an edge; log scaling would fix that case and break any sweep containing a zero or a negative. So a numeric parameter with few distinct values (`EFFECT_CATEGORICAL_MAX`, 8) is drawn on **evenly spaced ticks labelled with its actual values** — the same reading the table beneath it gives, where what matters is which of three settings won, not that one is a hundredth of another — and a parameter with many distinct values keeps the linear axis, since there the spacing carries meaning. The ticks come from Chart.js's **category scale**: the hand-rolled version (a linear axis with `min`/`max` at ±0.5 and `stepSize: 1`) generated ticks at -0.5, 0.5, 1.5 …, none of which indexed the label array, so the axis rendered with no value labels at all — a strip plot whose strips were unnamed. A muted line joins the best score at each value, because individual runs scatter and the *shape* of the answer ("it improves to 0.01, then stops") is not readable from the points; it is drawn only on the spaced axis, since on a continuous one it would imply a density of sampling that never happened. Above all of it, one sentence states the finding, and it carries its own caveats rather than leaving them to a caption further up: a "best" drawn from a single run says so, and **a tie is reported as a tie** — two values sharing the best score is a common outcome of a small sweep, and naming one of them claims a difference the data does not show. Ties are decided with `metricMoved`, the same epsilon the compare table's best/worst tint uses, so two values printing the same number are never split into a winner and a loser.

- **A chart point raises a question of identity, and answering it must not cost the analysis**: clicking a dot in an effect chart called `openFromMatrix`, which opened that run's detail view — a full-canvas switch that put the whole parameter matrix down. So the only gesture available for "which run is this?" discarded the comparison it was asked from, and getting back meant reopening Analyze and reassembling the selection. The question a dot raises is *identity*, not "show me everything about this run", so the click now renders a card under that chart naming the run, its varying parameters and its score, and offers **Add to selection** and **Open this run** as two of three things you might then want. The card is repainted on its own (`_renderEffectPick`) rather than through the section's renderer: the panels hold live Chart.js instances, and rebuilding the section's HTML to fill in a card underneath one would destroy and recreate every chart in it. The hover tooltip carries the name for the same reason — `lr=0.01  loss=1.8298` describes a point that is already plotted at those coordinates — and the chart sets `interaction: {mode: 'nearest', intersect: true}`, because the default groups everything near the cursor and produced a tooltip titled with one run's name listing two runs' values underneath it: the exact ambiguity the title was added to remove.

- **Width is a property of the content, not of the window**: the matrix run table wants every pixel it can get (a wide sweep has a column per varying parameter, and the table scrolls in its own container so the page never does). Everything below it does not, and inherited the full canvas anyway: a 280px-tall scatter of six points stretched to 1900px is mostly whitespace, a four-row summary table beside it is worse, and prose at that measure is unreadable regardless of what it says. The analyses are capped and the per-parameter panels are laid out `repeat(auto-fit, minmax(480px, 1fr))`, so two of them sit side by side on a wide screen — which is also the comparison the section exists for, and previously took a screenful of scrolling per parameter.

- **Point → run was the only direction, and it was the harder one**: hover names the run under the cursor, and that was the whole of the effects charts' interactivity. The reverse question — *where is this run on these charts?* — had no gesture at all, and hover is a poor substitute for it: a sweep's points overlap (four runs sharing an `lr` land within a few pixels of each other), so locating one specific run meant hovering each of them in turn and reading a long auto-generated name off a tooltip that changes as the cursor moves. The **selection** drives a highlight instead — the gesture that already exists, and the one the compare actions read. Ticking a run enlarges its point and dims the rest **in every parameter panel at once**, which also answers the question the panels are laid side by side to ask: this run is best on `lr`, so where does it sit on `epochs`? The point identified by a click joins the same set, so clicking a dot in one panel locates the same run in all of them. Three constraints hold this together. With an empty highlight set nothing is dimmed — an always-on highlight is a filter, and this view already has one. The repaint is a data update (`_refreshEffectHighlights` → `chart.update('none')`) rather than a re-render of the section, because the panels hold live Chart.js instances and rebuilding the HTML to move a highlight would destroy and recreate every chart in it. And per-point colours make `backgroundColor` an *array*, which the legend reads element 0 of — so with a highlight active the swatch took the colour of whichever run sorted first, usually a dimmed grey; `generateLabels` names the series' own base colour instead. Separately, `pointHitRadius` is 14: needing pixel precision to read a tooltip is most of why hovering was the wrong tool for this in the first place.

- **A control has to be able to show its own value**: the effects section's "Colour by" picker is rendered from the server's `groupable` list, and that list was built with the currently selected key *removed* — `[k for k in keys if k != group_by]`. The intent was real ("you cannot colour by the axis itself": colouring the `lr` panel by `lr` just repeats its own x axis) but it is a rule about **one panel**, applied to the **whole section's control**. Since the option did not exist, the `selected` match had nothing to attach to and the `<select>` fell back to its first entry: picking `model` coloured the points correctly and then displayed "—", which reads as the setting not having taken — and made the state unrecoverable to look at, since nothing else on screen named the grouping. `groupable` now carries every key plus the `_script` pseudo-key unconditionally; the per-panel rule moved into `_drawEffectChart` (`groupBy = d.group_by !== p.key ? d.group_by : ''`), and the client also force-includes `group_by` in the option list if a payload ever omits it again. The guard that was supposed to catch this asserted `"opt" not in out["groupable"]` — a string against a list of dicts, which is true whatever the list contains, so it never checked anything; it now compares keys. Related, and the other half of the same report: a grouping where every run lands in one bucket ("colour by script" in a single-script project) recoloured the chart one colour and was indistinguishable from a control that did nothing, so the section states which of the two it is.

# Dashboard: views and selection

Which view owns the canvas, and which surface owns a selection. Read before touching view switching or anything that feeds Compare.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **One canvas, one way to take it (view switching)**: The dashboard's full-screen views — welcome, run detail, Compare, the parameter matrix, the Trash and the Sessions tab — are siblings sharing one canvas, and two of them additionally suppress their neighbours from CSS (`body.sessions-active` and `body.matrix-active` carry `display:none !important` rules). So raising one view means putting *all* the others down, classes included, and no amount of `style.display=''` on the target can win against a leftover `!important` rule. Every switcher used to hide an ad-hoc subset instead, and they had drifted apart: `showCompareView` hid the two oldest (welcome + detail) only, so **Compare (N)** pressed from the sidebar while the Sessions tab, the Trash or the matrix held the canvas ran the whole comparison — request, render, charts — and then displayed it underneath them or not at all. Nothing threw and nothing was reported; the button simply did nothing, which is the one outcome a button must not have. **`releaseCanvas()` (js/sidebar.js) is the single teardown**, driven by the `CANVAS_VIEWS` / `CANVAS_CLASSES` lists so a view added later is covered by adding it to a list rather than by remembering five call sites, and every switcher (`showWelcome`, `showDetailView`, `showCompareView`, `openParamMatrix`, `openTrashView`, `toggleSessionsTab`) calls it first. `CANVAS_VIEWS` carries `#matrix-bar` alongside the six views: it is not a view, but the matrix's floating selection bar is laid out *outside* `#matrix-view`, so hiding the view alone strands it over whatever comes up next — listing it beats special-casing it in the teardown. `closeParamMatrix()` calls `releaseCanvas()` for the same reason rather than repeating the three lines, and the switchers that raise a view of their own no longer call it at all. It is deliberately **not** built out of `closeSessionsTab()`/`closeTrashView()`: those restore whichever view they were opened from (and re-show the welcome screen), which is the opposite of what a switcher about to raise its own view wants — it flashes a view being left, or lands the user back on the one they just left. `openTrashView` still reads `sessions-active` *before* releasing, since that is what its Close returns to. Guarded by `tests/test_dashboard_js_integrity.py`, which asserts every switcher releases first and that the view lists are complete — none of these failures raises, so a static check is the only thing that notices when one comes back.

- **A selection belongs to the surface that owns it**: three surfaces let the user assemble a set to compare — the experiments table/sidebar (`selectedIds`), the parameter matrix (`_matrixSelected`) and the Sessions tree's branch-compare mode (`_compareNodes`) — and each is a different question over a different population, so they are deliberately separate sets rather than one shared one. What they share is the *destination*: **`compareRuns(ids)`** (js/detail.js) opens the one Compare view for any number of runs (it used to route two runs to a separate pair view — see the tab-merge entry below), and `compareSelected()` is the thin table-side caller (`compareRuns([...selectedIds])`). The ids are a parameter for a reason — `compareMatrixSelection` used to pass its picks by *assigning* `selectedIds`, which silently discarded whatever the user had staged in the table (a set possibly assembled for a bulk delete or an export) and left the table's action bar afterwards describing the matrix's runs. `populateMultiCompareSelector(preselect)` takes the set to tick for the same reason, defaulting to `selectedIds` only when the table is what called it. **A selection must not outlive the set it was made in — where the set is knowable.** `_matrixSelected` survives closing the matrix (reopening it should not lose what you were assembling), but the set analysed is whatever the experiment list is filtered to, so `_pruneMatrixSelection(rows)` drops picks the reloaded set no longer contains: the floating bar's count and the ticked boxes in front of the user must agree, and without it a pick could name a run with no row to un-tick it on, still counted and still comparable. **The other two sets deliberately do not do this, and the reasons differ.** `selectedIds` *cannot*: the experiment list is paged, so `allExperiments` is only the loaded window and pruning against it would silently drop legitimate picks for runs scrolled out of the fetched set — the matrix's "rows are the whole analysed set" property is what makes pruning safe there and it does not hold here. `_compareNodes` is only reset on session switch, not on a reload of the same tree, so a pick trashed in another tab does survive in the compare bar's count; `runCompare` catches it at compare time and reports it rather than dropping it silently. That is a genuine gap rather than a design choice — pruning `_compareNodes` at the tree-reload sites would close it and demote `runCompare`'s reporting to the racy case it is actually good for. The **Sessions** mode follows the same discipline from the other direction: `_closeCompareResult()` dismisses the comparison *without* touching the picks that produced it (the result panel's own Close used to call `clearCompare()`, so putting the columns away to look at the tree again meant re-picking every node — the picks are the expensive part), `clearCompare()` still clears and closes, entering the mode hides the single-node detail while leaving it **restores** the node that was open (`_applyCompareMode` re-selects `_selectedNodeId`, where exiting used to hide the detail on the way out too and drop the user on an empty panel), and `runCompare` **states** picks it could not resolve rather than dropping them — four picks rendering three columns while the bar still says four is a comparison quietly missing one of the things being compared.

- **Clearing a selection has to clear what the selection produced — the asymmetry with dismissing a result is the point**: Compare's **Clear** emptied `_multiPicked` and repainted the chips, and stopped there, so the rendered comparison — config table, metric table, training curves, bar charts, image rows — kept standing underneath a control bar now reading "No runs chosen yet". The only thing still on screen was the thing Clear was pressed to get rid of, which is indistinguishable from a button that does nothing. `_discardComparison()` is the single teardown (chips → charts → `_lastComparison` → the result host → the `#compare=` address), and the **token bump belongs in it**: a comparison already in flight otherwise lands after the clear and repaints everything that was just removed, which is the same superseded-answer hazard `doMultiCompare` already guards on its own path. The address goes too — leaving `#compare=…` on a cleared page makes Copy link offer a link to a comparison that is not there and makes Back restore what was just discarded. Note the deliberate asymmetry with the Sessions rule above: **clearing the picks clears the result, dismissing the result does not clear the picks.** The picks are the expensive part, so putting the columns away to look at the tree again must not cost them — but a set that no longer exists cannot keep an answer on screen.

- **The panel that answers "what changed" must not answer by showing nothing**: Multi Compare's Configuration table returned an empty string when no parameter varied and the runs shared a script. That is the one case where "nothing differs" is itself the finding — the numbers below moved because of the code, the data, or run-to-run variance — and rendering nothing is indistinguishable from the panel being missing or from the comparison having failed to load it. The panel now always renders and says which case it is. Three further things it owes the reader: **internal `_`-prefixed params are filtered out** (`_dataset_manifest` and friends differ on nearly every run, so they were the loudest rows in the table while saying nothing about any decision the user made — the matrix has always dropped them, server-side); cells are marked against the **first run as the reading baseline**, so a twelve-column row can be scanned for *where* it changed rather than read value by value, and a key a run never had prints `not set` rather than leaving a blank cell that reads as "not shown"; and the constants are **kept, folded** (`_multiConstantsHtml`) rather than dropped, because "all six ran at `batch_size=64`" is routinely what explains the result, and it is the background the differences are read against.

- **One answer to "how do these N runs differ"**: `get_multi_compare` is the payload behind Multi Compare *and* behind `exptrack compare a b c` — the CLI had its own assembly of the same table (script row, varying params, best per metric row), and the two had already diverged: the server reported which metric spellings an alias merged and the CLI reported nothing, breaking `metric_alias`'s own "every merge is reported" rule, while `rank_by=best` existed only on the dashboard. The CLI keeps the terminal formatting and nothing else. **What varies is decided there too**, by `varying_param_keys` over the shared `params_differ`: computed in the browser with JSON equality, `0.01` and `"0.01"` — the same setting captured by argparse and by the pipeline CLI — showed as a differing row in the one surface built for cross-launcher comparison, while the matrix one click away called it constant

- **Searchable Compare pickers**: The pair (`cmp-id1`/`cmp-id2`) and multi (`cmp-multi-select`) pickers listed ~100 runs as native `<option>`s labelled `id | name(35 chars) | status | date`. With auto-named runs that is a hundred visually identical lines — the name's distinguishing tail was exactly what the 35-char slice cut off — and a native `<select>` has no way to search. Now **one** cached run list feeds all three pickers: `_loadCmpExps(force, limit)` fetches once per Compare visit (so switching tabs no longer refetches; `loadExperiments` clears `_cmpExps` so a mutation can't leave a stale set) and stores entries as `{id, lbl, hay}` — the option label built once by `_cmpOptionLabel(e)` plus a lowercased copy for matching, so filtering and rendering never rebuild it. The label keeps the **full** name and appends the run's first three user params (`lr=0.01 batch_size=128 …`, filtered by the shared `isUserParamKey`) so options differ visibly where the runs differ. A single `#cmp-filter` box calls `onCompareFilter` — `debounce(filterCompareOptions, 150)`, the same treatment the main search box gets, since each keystroke otherwise rebuilds three option lists over up to `EXP_PAGE_SIZE` runs — which re-narrows every picker by substring over `hay` (so `lr=0.1`, a status, an id prefix or a date all work) and shows an `(N of M shown)` count in the placeholder. **`_cmpOptsHtml(q, placeholder, selectedSet, keepId)` is the only place an `<option>` is emitted**; `keepId` force-includes the current pick so narrowing the filter never silently drops it (the earlier version re-appended a second, separately-built option for that case — two markup paths that would drift). And because this cache is capped like the table's, it carries **the same honesty guarantee**: `_renderCmpTruncNotice()` shows a `.cmp-trunc` strip ("Filtering the N most recent runs of M" + **Load all runs** → `loadAllCompareRuns()`) whenever runs went unfetched — without it, a filter box searching a partial set would render "no match" for a run that exists, which is precisely the failure the main table's notice exists to prevent.

- **One way to answer "which runs?", and it must not depend on knowing a name**: three surfaces ask the user to name a set of runs — Pair Compare (two single `<select>`s), Multi Compare (a `<select multiple>`) and the parameter matrix (which did not ask at all: it analysed whatever the experiment list happened to be filtered to). All three failures were the same failure. A native `<select>` shows **one line of text per run**, and the runs that most need picking are auto-named — `Aug12_basic_script__lr0.01_epochs10_batch_si64_modelmlp__53a73952` — so a list of them is a wall of identical prefixes distinguished by a tail the option cuts off. The searchable-picker work above widened that line to carry three parameters and put a filter box over it, which helped the two pair selects and could not help the multi list at all: a `<select multiple>` still needs **Ctrl/Cmd-click** to hold a second run (the page said so in fine print underneath, and a plain click silently *replaced* the whole selection), and the matrix still had no control of its own — narrowing the analysed set meant leaving the view, rewriting the list's search box, and coming back, which also meant "these five runs" was inexpressible unless their names shared a substring. **`openRunPicker(opts)` (js/run_picker.js) is the one picker**: a modal on the shared `.dc-overlay`/`.dc-dialog`/`.dc-button` shell (a third modal look on one page is its own drift), whose rows are two lines — status, name and id prefix above, **every user parameter as a chip** plus the date below. `mode: 'single'` confirms on the row click (a Confirm press for a choice that cannot be ambiguous is a step with no decision in it) and `mode: 'multi'` returns the set. The picks are handed to `onConfirm(ids)` and never written to a global for the caller to read back — the same rule `compareRuns(ids)` follows, and for the same reason: each of the three surfaces owns a different selection, and Multi Compare's `_multiPicked` staging is a **copy** of `selectedIds`, so editing a comparison cannot reach back and change what the experiments table has ticked. The matrix's `_matrixIdSet` overrides `_matrixIds()` and the controls **state which set is being analysed** ("from the current filter" vs "7 chosen runs"), because what varies is a property of the set and a chosen subset reading as the whole search would misreport it; an empty pick returns to the filter rather than analysing nothing, which would be a dead view whose only escape is the control that emptied it.

- **The picker searches the cache the filter box searches, and it searches more of each run than it prints**: the picker reads `_cmpExps` through `_loadCmpExps` rather than fetching its own list — two caches would mean the picker and the Compare filter box beside it could be searching different sets of runs, so "no match" would mean different things in each, and `loadExperiments`' cache-clear would only reach one of them. What did change is `hay`: it was a lowercased copy of the **option label**, so matching was limited to what a dropdown line had room to print — three parameters. A run identified by its fourth parameter, by its script, or by a tag was unfindable, and the picker reported "no match" for a run sitting in the list it had just searched. `_cmpHaystack` now folds in every user param as `key=value`, the script, tags and studies; the label is unchanged, so the pair dropdowns still read the same. **The query is the only thing that decides what is listed.** Selected runs were briefly force-included past the filter, on the reasoning that the dialog is the only place a pick can be taken back — which sounds careful and is not: the matrix opens the picker with its *entire* analysed set preselected, so every row was exempt and typing narrowed nothing at all. A search box that cannot narrow is worse than no search box, because it looks like it worked. Picks the query hides are counted in the footer ("13 selected (9 not matching this search)") instead, so confirming never takes a set larger than the footer admits to. The picker also carries **both** truncation notices, because they call for opposite actions: more rows matched than `RP_MAX_ROWS` paints means *narrow the search*, while `_cmpHasMore` means the cache is one page of the project and offers **Load all runs**. Collapsing them into one strip would tell the user to narrow a search that is already showing everything it has.

- **Leaving a view has to be as reachable as entering it, and comparing should not require leaving at all**: Compare is a full-canvas view that puts down whatever raised it, and its Back was hardwired to `showWelcome()`. So comparing four runs picked in the parameter matrix **cost you the table you had assembled them in**: the only route back was re-opening Analyze and re-ticking every row, and there was no way to hold the comparison and the matrix on screen together at all. Three things now: (1) `_compareOrigin` travels with the request (`compareRuns(ids, 'matrix')`) rather than being a global the matrix writes and Compare reads back, and `closeCompareView()` restores the matrix — with its picks intact, since `_matrixSelected` survives closing the view. It is set **after** `showCompareView()`, which resets it to the experiments list, because that is where the toolbar's Compare button comes from. (2) The browser's own Back button now works, which it never did: the page wrote history **only** with `replaceState`, so no in-app navigation left an entry and Back exited the dashboard — landing on a URL whose `?token=` had been stripped at boot, which works only while localStorage still holds the token and is otherwise the login prompt (see `server.md`). `_pushViewHash(hash, replace)` and the `popstate` handler `_onPopView` give `#matrix` and `#compare=…` a position; returning to a view (Compare's Back going home to the matrix) *replaces* rather than pushes, or Back would bounce between the two. `restoreCompareFromUrl` stays the only parser of the compare vocabulary, so a shared link and the Back button cannot disagree about what a hash means. Run detail and the Sessions/Trash tabs are deliberately not addressed yet — Back from those still leaves the page, as it always did. (3) **Compare n here** renders the config and metric tables *inside* the matrix, under the rows the runs were picked in, so the common case needs no navigation in either direction; the full view keeps the curves, bar charts and images and is one button away. The inline panel carries the same two obligations as every other compare surface: a request token (two quick comparisons interleave and the older answer can land last) and a statement when it renders fewer runs than were picked. Its metric table is `_multiMetricTableHtml`, shared with Multi Compare — a second copy would be a second place for the best/worst tint to come back inverted.

- **A chart series has to be named by what distinguishes it**: every chart in Multi Compare — the training-curve overlay, the bar charts — labelled its series with the run's `name`. For the case these charts exist for, a sweep, those names are auto-generated and differ in a tail, so a five-run legend was five near-identical strings and the chart could not answer the only question it was opened for: *which line is which setting*. Series are now built from the varying params (`lr=0.05 epochs=20 model=cnn`), with a **Label series by** control offering each varying key individually or the run name back. Three things this got wrong on the way, each worth keeping: the compound label was first run through `midEllipsis`, which on a five-parameter sweep produced `batch_size=64 dr….05 model=cnn` — hiding `lr`, the thing being swept, because it happened to sit in the middle alphabetically; so the label caps at `MULTI_LABEL_MAX_KEYS` (3) keys and ellipsizes long *values* rather than the label. Then the keys were ranked by distinct-value count, which picked three two-valued params over `lr` and produced three identical legend entries — a label naming settings that differ *somewhere in the set* rather than the ones that separate these runs. `_multiRankedLabelKeys` is greedy set-cover instead: each step takes the key that maximizes the number of distinct labels, and stops as soon as every run has its own, which is the property a legend actually needs. It returns `{use, all}` rather than one ordered list, because slicing a concatenated list padded a sufficient two-key label with a third key that separated nothing; `all` is what decides whether the label admits (with `…`) to naming fewer settings than the runs differ by. Relabelling repaints from `_lastComparison` — it is a render, not a request, the same rule the polarity toggle follows.

- **A view of everything says nothing**: the parameter matrix opens onto a wide table and four collapsible analyses, and it never stated in words what any of it amounted to — so arriving meant reading a grid to work out which columns mattered and which row won, and the four sections were named (`Progress over the search`, `What each value was worth`) in a way that could only be resolved by opening all of them. Two cheap fixes, both drawn from data already in the payload: `_matrixSummaryHtml` states the answer in one sentence — run count, which params varied, the best value and the run that got it, and how many configurations are repeats — with the winner as a link, because "which one won" was previously carried only by a badge partway down a column; and each section's toggle carries a one-line description of what it will show, so the sections are four questions to choose between rather than four tables to open and read. The second line of the summary is the "what now": it names the ticked count and what Compare-here will do when there is a selection, and how to make one when there isn't.

- **A comparison needs an address**: a built comparison could not be sent to anyone or returned to, and combined with the picker holding only the most recent page there was no path at all to compare two specific *old* runs by id. `#compare=pair:a,b` / `#compare=multi:a,b,c` is written whenever a comparison renders and restored once on load. Deliberately the URL fragment, not a query parameter: it never reaches the server, so a shared link leaks no run ids into logs and it needs no route

- **A picker's cache is not the set of runs that exist**: `_openPairCompare` assigned `select.value = id` against options built from the first page of runs. Assigning a value with no matching `<option>` silently leaves the select empty, so comparing an older run — easy to reach from the filmstrip, from "Load all runs", or now from a shared link — set nothing and `doCompare()` returned without a word: the "button that does nothing" failure this file already documents. Missing ids are injected as options before assignment, and `doCompare` says "select two runs" rather than returning silently

- **Two clicks race, and the loser can land last**: neither compare surface had a staleness guard, so two rapid comparisons interleaved and the older result could paint over the newer one — while leaking the loser's Chart instances. Both now carry a request token checked before every DOM write, the same guard `refreshDetail` applies with `currentDetailId`

- **Chart canvases are identified positionally**: ids built by sanitizing the metric key collided (`val/acc` and `val_acc` both become `val_acc`), and in Multi Compare the keys are the *union* across runs — exactly the different-models case. The second `new Chart` on a canvas that already owns one throws, and the unhandled rejection killed every remaining chart while the table above still looked healthy

- **Two tabs for the same question at different arities is two half-views**: Compare shipped a *Pair* tab and a *Multi* tab, and the split was not along a seam in the problem — it was along a seam in the implementation. Each tab had grown capabilities the other lacked, and neither set was reachable from the other. Only the pair tab could show the **code diff between two attempts** (the run/run/compare loop's whole payoff), the **notebook variable table**, and the **A/B image overlay**; only the multi tab had the **run picker**, the **chip staging**, the **Configuration table** and the **training-curve overlay**. So a three-run comparison could not reach a code diff at all, and a two-run comparison could not reach the picker that makes runs findable — you had to know which tab held what, and re-pick both runs in a different control to cross over. The merge keeps one view whose panels *specialize* at n=2 rather than a second view that owns them: `_fetchPairExtras` runs alongside the comparison POST when the set is exactly two, and `_pairExtrasHtml` renders all parameters (with the differences toggle), the code diff, the variables and the image overlay from it. The **Delta** column is the same rule in the metric table — a delta between three runs is "against which?", so it exists exactly when the set is a pair. Two constraints made this safe rather than lossy: the extras are fetched in `doMultiCompare` and attached to `data._pair`, never fetched in the renderer, because three controls repaint from the cached payload (metric polarity, chart labels, the differences toggle) and any of them re-requesting five endpoints to redraw a table is the cost the repaint path exists to avoid; and `_repaintComparison` is now the single repaint entry point those three share, rather than three copies of the same five lines. `#compare=pair:` links still resolve — the ids are what the address names, and two of them render the pair panels anyway.

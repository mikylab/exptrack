# Dashboard: views and selection

Which view owns the canvas, and which surface owns a selection. Read before touching view switching or anything that feeds Compare.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **One canvas, one way to take it (view switching)**: The dashboard's full-screen views — welcome, run detail, Compare, the parameter matrix, the Trash and the Sessions tab — are siblings sharing one canvas, and two of them additionally suppress their neighbours from CSS (`body.sessions-active` and `body.matrix-active` carry `display:none !important` rules). So raising one view means putting *all* the others down, classes included, and no amount of `style.display=''` on the target can win against a leftover `!important` rule. Every switcher used to hide an ad-hoc subset instead, and they had drifted apart: `showCompareView` hid the two oldest (welcome + detail) only, so **Compare (N)** pressed from the sidebar while the Sessions tab, the Trash or the matrix held the canvas ran the whole comparison — request, render, charts — and then displayed it underneath them or not at all. Nothing threw and nothing was reported; the button simply did nothing, which is the one outcome a button must not have. **`releaseCanvas()` (js/sidebar.js) is the single teardown**, driven by the `CANVAS_VIEWS` / `CANVAS_CLASSES` lists so a view added later is covered by adding it to a list rather than by remembering five call sites, and every switcher (`showWelcome`, `showDetailView`, `showCompareView`, `openParamMatrix`, `openTrashView`, `toggleSessionsTab`) calls it first. `CANVAS_VIEWS` carries `#matrix-bar` alongside the six views: it is not a view, but the matrix's floating selection bar is laid out *outside* `#matrix-view`, so hiding the view alone strands it over whatever comes up next — listing it beats special-casing it in the teardown. `closeParamMatrix()` calls `releaseCanvas()` for the same reason rather than repeating the three lines, and the switchers that raise a view of their own no longer call it at all. It is deliberately **not** built out of `closeSessionsTab()`/`closeTrashView()`: those restore whichever view they were opened from (and re-show the welcome screen), which is the opposite of what a switcher about to raise its own view wants — it flashes a view being left, or lands the user back on the one they just left. `openTrashView` still reads `sessions-active` *before* releasing, since that is what its Close returns to. Guarded by `tests/test_dashboard_js_integrity.py`, which asserts every switcher releases first and that the view lists are complete — none of these failures raises, so a static check is the only thing that notices when one comes back.

- **A selection belongs to the surface that owns it**: three surfaces let the user assemble a set to compare — the experiments table/sidebar (`selectedIds`), the parameter matrix (`_matrixSelected`) and the Sessions tree's branch-compare mode (`_compareNodes`) — and each is a different question over a different population, so they are deliberately separate sets rather than one shared one. What they share is the *destination*: **`compareRuns(ids)`** (js/detail.js) opens the one Compare view for any number of runs (it used to route two runs to a separate pair view — see the tab-merge entry below), and `compareSelected()` is the thin table-side caller (`compareRuns([...selectedIds])`). The ids are a parameter for a reason — `compareMatrixSelection` used to pass its picks by *assigning* `selectedIds`, which silently discarded whatever the user had staged in the table (a set possibly assembled for a bulk delete or an export) and left the table's action bar afterwards describing the matrix's runs. `populateMultiCompareSelector(preselect)` takes the set to tick for the same reason, defaulting to `selectedIds` only when the table is what called it. **A selection must not outlive the set it was made in — where the set is knowable.** `_matrixSelected` survives closing the matrix (reopening it should not lose what you were assembling), but the set analysed is whatever the experiment list is filtered to, so `_pruneMatrixSelection(rows)` drops picks the reloaded set no longer contains: the floating bar's count and the ticked boxes in front of the user must agree, and without it a pick could name a run with no row to un-tick it on, still counted and still comparable. **The other two sets deliberately do not do this, and the reasons differ.** `selectedIds` *cannot*: the experiment list is paged, so `allExperiments` is only the loaded window and pruning against it would silently drop legitimate picks for runs scrolled out of the fetched set — the matrix's "rows are the whole analysed set" property is what makes pruning safe there and it does not hold here. `_compareNodes` is only reset on session switch, not on a reload of the same tree, so a pick trashed in another tab does survive in the compare bar's count; `runCompare` catches it at compare time and reports it rather than dropping it silently. That is a genuine gap rather than a design choice — pruning `_compareNodes` at the tree-reload sites would close it and demote `runCompare`'s reporting to the racy case it is actually good for. The **Sessions** mode follows the same discipline from the other direction: `_closeCompareResult()` dismisses the comparison *without* touching the picks that produced it (the result panel's own Close used to call `clearCompare()`, so putting the columns away to look at the tree again meant re-picking every node — the picks are the expensive part), `clearCompare()` still clears and closes, entering the mode hides the single-node detail while leaving it **restores** the node that was open (`_applyCompareMode` re-selects `_selectedNodeId`, where exiting used to hide the detail on the way out too and drop the user on an empty panel), and `runCompare` **states** picks it could not resolve rather than dropping them — four picks rendering three columns while the bar still says four is a comparison quietly missing one of the things being compared.

- **Clearing a selection has to clear what the selection produced — the asymmetry with dismissing a result is the point**: Compare's **Clear** emptied `_multiPicked` and repainted the chips, and stopped there, so the rendered comparison — config table, metric table, training curves, bar charts, image rows — kept standing underneath a control bar now reading "No runs chosen yet". The only thing still on screen was the thing Clear was pressed to get rid of, which is indistinguishable from a button that does nothing. `_discardComparison()` is the single teardown (chips → charts → `_lastComparison` → the result host → the `#compare=` address), and the **token bump belongs in it**: a comparison already in flight otherwise lands after the clear and repaints everything that was just removed, which is the same superseded-answer hazard `doMultiCompare` already guards on its own path. The address goes too — leaving `#compare=…` on a cleared page makes Copy link offer a link to a comparison that is not there and makes Back restore what was just discarded. Note the deliberate asymmetry with the Sessions rule above: **clearing the picks clears the result, dismissing the result does not clear the picks.** The picks are the expensive part, so putting the columns away to look at the tree again must not cost them — but a set that no longer exists cannot keep an answer on screen.

- **The panel that answers "what changed" must not answer by showing nothing**: Multi Compare's Configuration table returned an empty string when no parameter varied and the runs shared a script. That is the one case where "nothing differs" is itself the finding — the numbers below moved because of the code, the data, or run-to-run variance — and rendering nothing is indistinguishable from the panel being missing or from the comparison having failed to load it. The panel now always renders and says which case it is. Three further things it owes the reader: **internal `_`-prefixed params are filtered out** (`_dataset_manifest` and friends differ on nearly every run, so they were the loudest rows in the table while saying nothing about any decision the user made — the matrix has always dropped them, server-side); cells are marked against the **first run as the reading baseline**, so a twelve-column row can be scanned for *where* it changed rather than read value by value, and a key a run never had prints `not set` rather than leaving a blank cell that reads as "not shown"; and the constants are **kept, folded** (`_multiConstantsHtml`) rather than dropped, because "all six ran at `batch_size=64`" is routinely what explains the result, and it is the background the differences are read against.

- **One answer to "how do these N runs differ"**: `get_multi_compare` is the payload behind Multi Compare *and* behind `exptrack compare a b c` — the CLI had its own assembly of the same table (script row, varying params, best per metric row), and the two had already diverged: the server reported which metric spellings an alias merged and the CLI reported nothing, breaking `metric_alias`'s own "every merge is reported" rule, while `rank_by=best` existed only on the dashboard. The CLI keeps the terminal formatting and nothing else. **What varies is decided there too**, by `varying_param_keys` over the shared `params_differ`: computed in the browser with JSON equality, `0.01` and `"0.01"` — the same setting captured by argparse and by the pipeline CLI — showed as a differing row in the one surface built for cross-launcher comparison, while the matrix one click away called it constant

- **Searchable Compare pickers**: The pair (`cmp-id1`/`cmp-id2`) and multi (`cmp-multi-select`) pickers listed ~100 runs as native `<option>`s labelled `id | name(35 chars) | status | date`. With auto-named runs that is a hundred visually identical lines — the name's distinguishing tail was exactly what the 35-char slice cut off — and a native `<select>` has no way to search. Now **one** cached run list feeds all three pickers: `_loadCmpExps(force, limit)` fetches once per Compare visit (so switching tabs no longer refetches; `loadExperiments` clears `_cmpExps` so a mutation can't leave a stale set) and stores entries as `{id, lbl, hay}` — the option label built once by `_cmpOptionLabel(e)` plus a lowercased copy for matching, so filtering and rendering never rebuild it. The label keeps the **full** name and appends the run's first three user params (`lr=0.01 batch_size=128 …`, filtered by the shared `isUserParamKey`) so options differ visibly where the runs differ. A single `#cmp-filter` box calls `onCompareFilter` — `debounce(filterCompareOptions, 150)`, the same treatment the main search box gets, since each keystroke otherwise rebuilds three option lists over up to `EXP_PAGE_SIZE` runs — which re-narrows every picker by substring over `hay` (so `lr=0.1`, a status, an id prefix or a date all work) and shows an `(N of M shown)` count in the placeholder. **`_cmpOptsHtml(q, placeholder, selectedSet, keepId)` is the only place an `<option>` is emitted**; `keepId` force-includes the current pick so narrowing the filter never silently drops it (the earlier version re-appended a second, separately-built option for that case — two markup paths that would drift). And because this cache is capped like the table's, it carries **the same honesty guarantee**: `_renderCmpTruncNotice()` shows a `.cmp-trunc` strip ("Filtering the N most recent runs of M" + **Load all runs** → `loadAllCompareRuns()`) whenever runs went unfetched — without it, a filter box searching a partial set would render "no match" for a run that exists, which is precisely the failure the main table's notice exists to prevent.

- **One way to answer "which runs?", and it must not depend on knowing a name**: three surfaces ask the user to name a set of runs — Pair Compare (two single `<select>`s), Multi Compare (a `<select multiple>`) and the parameter matrix (which did not ask at all: it analysed whatever the experiment list happened to be filtered to). All three failures were the same failure. A native `<select>` shows **one line of text per run**, and the runs that most need picking are auto-named — `Aug12_basic_script__lr0.01_epochs10_batch_si64_modelmlp__53a73952` — so a list of them is a wall of identical prefixes distinguished by a tail the option cuts off. The searchable-picker work above widened that line to carry three parameters and put a filter box over it, which helped the two pair selects and could not help the multi list at all: a `<select multiple>` still needs **Ctrl/Cmd-click** to hold a second run (the page said so in fine print underneath, and a plain click silently *replaced* the whole selection), and the matrix still had no control of its own — narrowing the analysed set meant leaving the view, rewriting the list's search box, and coming back, which also meant "these five runs" was inexpressible unless their names shared a substring. **`openRunPicker(opts)` (js/run_picker.js) is the one picker**: a modal on the shared `.dc-overlay`/`.dc-dialog`/`.dc-button` shell (a third modal look on one page is its own drift), whose rows are two lines — status, name and id prefix above, **every user parameter as a chip** plus the date below. `mode: 'single'` confirms on the row click (a Confirm press for a choice that cannot be ambiguous is a step with no decision in it) and `mode: 'multi'` returns the set. The picks are handed to `onConfirm(ids)` and never written to a global for the caller to read back — the same rule `compareRuns(ids)` follows, and for the same reason: each of the three surfaces owns a different selection, and Multi Compare's `_multiPicked` staging is a **copy** of `selectedIds`, so editing a comparison cannot reach back and change what the experiments table has ticked. The matrix's `_matrixIdSet` overrides `_matrixIds()` and the controls **state which set is being analysed** ("from the current filter" vs "7 chosen runs"), because what varies is a property of the set and a chosen subset reading as the whole search would misreport it; an empty pick returns to the filter rather than analysing nothing, which would be a dead view whose only escape is the control that emptied it.

- **The picker searches the cache the filter box searches, and it searches more of each run than it prints**: the picker reads `_cmpExps` through `_loadCmpExps` rather than fetching its own list — two caches would mean the picker and the Compare filter box beside it could be searching different sets of runs, so "no match" would mean different things in each, and `loadExperiments`' cache-clear would only reach one of them. What did change is `hay`: it was a lowercased copy of the **option label**, so matching was limited to what a dropdown line had room to print — three parameters. A run identified by its fourth parameter, by its script, or by a tag was unfindable, and the picker reported "no match" for a run sitting in the list it had just searched. `_cmpHaystack` now folds in every user param as `key=value`, the script, tags and studies; the label is unchanged, so the pair dropdowns still read the same. **The query is the only thing that decides what is listed.** Selected runs were briefly force-included past the filter, on the reasoning that the dialog is the only place a pick can be taken back — which sounds careful and is not: the matrix opens the picker with its *entire* analysed set preselected, so every row was exempt and typing narrowed nothing at all. A search box that cannot narrow is worse than no search box, because it looks like it worked. Picks the query hides are counted in the footer ("13 selected (9 not matching this search)") instead, so confirming never takes a set larger than the footer admits to. The picker also carries **both** truncation notices, because they call for opposite actions: more rows matched than `RP_MAX_ROWS` paints means *narrow the search*, while `_cmpHasMore` means the cache is one page of the project and offers **Load all runs**. Collapsing them into one strip would tell the user to narrow a search that is already showing everything it has.

- **Leaving a view has to be as reachable as entering it, and comparing should not require leaving at all**: Compare is a full-canvas view that puts down whatever raised it, and its Back was hardwired to `showWelcome()`. So comparing four runs picked in the parameter matrix **cost you the table you had assembled them in**: the only route back was re-opening Analyze and re-ticking every row, and there was no way to hold the comparison and the matrix on screen together at all. Three things now: (1) `_compareOrigin` travels with the request (`compareRuns(ids, 'matrix')`) rather than being a global the matrix writes and Compare reads back, and `closeCompareView()` restores the matrix — with its picks intact, since `_matrixSelected` survives closing the view. It is set **after** `showCompareView()`, which resets it to the experiments list, because that is where the toolbar's Compare button comes from. (2) The browser's own Back button now works, which it never did: the page wrote history **only** with `replaceState`, so no in-app navigation left an entry and Back exited the dashboard — landing on a URL whose `?token=` had been stripped at boot, which works only while localStorage still holds the token and is otherwise the login prompt (see `server.md`). `_pushViewHash(hash, replace)` and the `popstate` handler `_onPopView` give `#matrix` and `#compare=…` a position; returning to a view (Compare's Back going home to the matrix) *replaces* rather than pushes, or Back would bounce between the two. `restoreCompareFromUrl` stays the only parser of the compare vocabulary, so a shared link and the Back button cannot disagree about what a hash means. **Run detail is addressed too**: `#run=<id>&tab=<tab>` (`_runViewHash`/`_parseRunViewHash`, js/sidebar.js). Without it a reload while reading a run — the commonest thing a reader does to a live run — always landed on the experiments list, and Back out of a comparison opened from a run skipped the run. Entering a run pushes; a lateral move (filmstrip, vs-previous, return from the matrix — the `keepSidebar` callers) replaces, so Back leaves the run view instead of walking every run the filmstrip passed; a tab switch replaces, because a tab is not a place Back returns to. Boot and `popstate` both go through `_restoreViewFromHash`, the one dispatcher for every view hash, so a reload and the Back button cannot disagree — and a reload on `#matrix` now reopens the matrix as well. `showWelcome` drops the hash (`_clearViewHash`), or a reload would reopen a run the reader had left. The Sessions/Trash tabs are still not addressed — they overlay the canvas, so a reload there reopens whatever view they were opened over. (3) **Compare n here** renders the config and metric tables *inside* the matrix, under the rows the runs were picked in, so the common case needs no navigation in either direction; the full view keeps the curves, bar charts and images and is one button away. The inline panel carries the same two obligations as every other compare surface: a request token (two quick comparisons interleave and the older answer can land last) and a statement when it renders fewer runs than were picked. Its metric table is `_multiMetricTableHtml`, shared with Multi Compare — a second copy would be a second place for the best/worst tint to come back inverted.
- **Every full-canvas view has an address, Sessions and Trash included**: `#sessions`, `#sessions=<id>` and `#trash` join `#matrix`, `#compare=` and `#run=`, and `_restoreViewFromHash` stays the one parser. Entering Sessions (`toggleSessionsTab`) or Trash (`openTrashView`) pushes; choosing another session (`selectSession`, and the list load that re-opens the active one) *replaces*, because it is a move inside the view; closing replaces or clears (`closeTrashView` back to Sessions replaces `#trash` with the session's hash, so Back does not bounce between them). A restore or a return passes `{replaceHash: true}` (`toggleSessionsTab(opts)`, `openSessionNode(…, opts)`, as `openParamMatrix` already took it), and `toggleSessionsTab` also skips its write when the hash already starts `#sessions`. `_isViewHash` is the one list of hashes the parser knows, so `_clearViewHash` clears exactly what entering a view can write. Every close path that returns to the list goes through `_showListView()`, which re-renders the rail's selection bar — `closeParamMatrix` used to show the list by hand and left the duplicate bar up. Before this, neither view had an address, so a run opened from a session tree pushed `#run=` on top of the view the reader had left *before* Sessions — Back from the run skipped the tree and landed on an old comparison — and a reload on Sessions dropped the reader on the list.
- **A run's address names its tab, its view and its split: `#run=<id>&tab=<tab>&view=<view>&split=<tab>`.** `_parseRunViewHash` runs every hash through `_resolveDetailTab` and `_resolveSplit`, so a pre-2.1 link (`tab=timeline`, `tab=images`, `tab=logs`) lands on Code › Timeline, Files › Images or Files › Data — those were tabs of their own, and dropping the mapping would send every saved link to Overview without a word. `_currentRunHash(id)` is how every caller builds the address; `view` belongs to the left tab, and a view picked in the right pane of a split is kept in memory only. Tool views (`compare-within`, `confusion`) keep their ids. Tab, view and split changes replace; entering a run pushes.

- **A chart series has to be named by what distinguishes it**: every chart in Multi Compare — the training-curve overlay, the bar charts — labelled its series with the run's `name`. For the case these charts exist for, a sweep, those names are auto-generated and differ in a tail, so a five-run legend was five near-identical strings and the chart could not answer the only question it was opened for: *which line is which setting*. Series are now built from the varying params (`lr=0.05 epochs=20 model=cnn`), with a **Label series by** control offering each varying key individually or the run name back. Three things this got wrong on the way, each worth keeping: the compound label was first run through `midEllipsis`, which on a five-parameter sweep produced `batch_size=64 dr….05 model=cnn` — hiding `lr`, the thing being swept, because it happened to sit in the middle alphabetically; so the label caps at `MULTI_LABEL_MAX_KEYS` (3) keys and ellipsizes long *values* rather than the label. Then the keys were ranked by distinct-value count, which picked three two-valued params over `lr` and produced three identical legend entries — a label naming settings that differ *somewhere in the set* rather than the ones that separate these runs. `_multiRankedLabelKeys` is greedy set-cover instead: each step takes the key that maximizes the number of distinct labels, and stops as soon as every run has its own, which is the property a legend actually needs. It returns `{use, all}` rather than one ordered list, because slicing a concatenated list padded a sufficient two-key label with a third key that separated nothing; `all` is what decides whether the label admits (with `…`) to naming fewer settings than the runs differ by. Relabelling repaints from `_lastComparison` — it is a render, not a request, the same rule the polarity toggle follows.

- **A view of everything says nothing**: the parameter matrix opens onto a wide table and four collapsible analyses, and it never stated in words what any of it amounted to — so arriving meant reading a grid to work out which columns mattered and which row won, and the four sections were named (`Progress over the search`, `What each value was worth`) in a way that could only be resolved by opening all of them. Two cheap fixes, both drawn from data already in the payload: `_matrixSummaryHtml` states the answer in one sentence — run count, which params varied, the best value and the run that got it, and how many configurations are repeats — with the winner as a link, because "which one won" was previously carried only by a badge partway down a column; and each section's toggle carries a one-line description of what it will show, so the sections are four questions to choose between rather than four tables to open and read. The second line of the summary is the "what now": it names the ticked count and what Compare-here will do when there is a selection, and how to make one when there isn't.

- **A comparison needs an address**: a built comparison could not be sent to anyone or returned to, and combined with the picker holding only the most recent page there was no path at all to compare two specific *old* runs by id. `#compare=pair:a,b` / `#compare=multi:a,b,c` is written whenever a comparison renders and restored once on load. Deliberately the URL fragment, not a query parameter: it never reaches the server, so a shared link leaks no run ids into logs and it needs no route

- **A picker's cache is not the set of runs that exist**: `_openPairCompare` assigned `select.value = id` against options built from the first page of runs. Assigning a value with no matching `<option>` silently leaves the select empty, so comparing an older run — easy to reach from the filmstrip, from "Load all runs", or now from a shared link — set nothing and `doCompare()` returned without a word: the "button that does nothing" failure this file already documents. Missing ids are injected as options before assignment, and `doCompare` says "select two runs" rather than returning silently

- **Two clicks race, and the loser can land last**: neither compare surface had a staleness guard, so two rapid comparisons interleaved and the older result could paint over the newer one — while leaking the loser's Chart instances. Both now carry a request token checked before every DOM write, the same guard `refreshDetail` applies with `currentDetailId`

- **Chart canvases are identified positionally**: ids built by sanitizing the metric key collided (`val/acc` and `val_acc` both become `val_acc`), and in Multi Compare the keys are the *union* across runs — exactly the different-models case. The second `new Chart` on a canvas that already owns one throws, and the unhandled rejection killed every remaining chart while the table above still looked healthy

- **Pairing two runs' images is a claim, so it is decided once and stated**: Compare grouped images by `label || basename`, which is exactly right when both runs wrote `loss.png` and useless the moment the filename carries the epoch, the step or a timestamp — `loss_epoch10.png` and `loss_epoch12.png` are the same plot and paired with nothing, so the grid degenerated into one column of images per run. "Sometimes they line up and sometimes they don't" is that one rule meeting two naming habits. The rule now lives server-side in **`queries._assign_image_groups`** (so any future surface pairs identically) and is ordered: an **exact filename two or more runs share always wins** — the rule that already worked must not be weakened by a fuzzier one, and a run holding both `loss.png` and `loss_epoch9.png` must not have them merged — then `normalized_image_stem` (digit runs to `#`, separators and case folded) as a fallback, applied **only where merging cannot hide anything**: if any single run has two images that normalize alike (a per-epoch filmstrip), that family keeps its exact filenames, because the grid renders one cell per (run, group) and would otherwise show one of them and silently drop the rest. Each cell prints its real file name under the image, since the row heading is now the group and may be a normalized family. Separately: because artifacts are tracked **by reference**, two runs pointed at one path share one file, and what the grid shows in both cells is whatever the later run wrote. Rendered unmarked, that row is a picture of two runs agreeing perfectly — the most misleading output this view can produce, and the shape every rerun into a fixed output path takes. `shared` is set server-side, **scoped to the compared set** (a third run writing there says nothing about this pair), and `_sharedImageNote` says it in words above the row


- **One image is one row, however many paths point at it**: the savefig capture copies each figure into `outputs/<run>/` and registers **the copy**, and the finish-time output scan then registers the original the script wrote — two artifact rows for one image. In the Images tab that showed every plot twice. In Compare it did something worse: `_set_image_keys` keys a run's images on their file name *unless the run holds two images with the same name*, in which case both fall back to their full paths — and full paths are unique per run, so rule 1 (an exact filename two runs share) matched nothing, rule 2's `mergeable` test saw two images per run in the family and refused the merge, and every image ended up in a group of its own. The symptom is a very long grid of unpaired singles, reported as *"the images still don't line up, so instead I get a huge page of them by themselves"* — and it is worth noting that the pairing rules were not wrong: they were being fed a run that appeared to hold two `loss.png`s. `queries.drop_protected_copy_duplicates` collapses exactly that shape and no other: rows sharing a `content_hash` where **some sit under the project's `outputs/` dir and some do not** — the copy wins, the original drops. Two genuinely different plots that merely hash alike (`plots/train/loss.png` and `plots/val/loss.png`, both outside `outputs/`) are both kept, because a merge that hides one of a run's images is the one thing this must never do. It is applied on read (Compare and the Images tab), so runs already recorded with both rows are covered; the write side stops making the second row at all — see `run-loop.md`

- **A side-by-side of two runs' images has to say which run is which**: the overlay modal labelled each panel with the image's file name, and the whole reason two runs pair in this view is that they wrote **the same file name** — so the label read `loss.png` against `loss.png` and identified nothing, in the one view that exists to attribute a difference to a run. `openCompareModal` takes `run1`/`run2` (optional: an intra-run comparison has one run and nothing to disambiguate), the header names both, and `_imgCmpPanel` prints an A/B badge with the run name above the file name. The compare grid passes the column's run name through `selectCrossImg`, so the picker bar names the run too — the selection is readable before the modal opens
- **A comparison column is headed by what tells its run apart**: `_cmpRunLabel` returns the charts' own series label (`_multiSeriesLabel` over `_cmpLabelKeys`, the ranked varying keys `_renderMultiComparison` computes before any table), so a column reads `label_smoothing=0.3` rather than `SEP28_TRAIN__…_366A8603`, the table and the legend name each run the same way, and **Label series by** relabels both. The name is the fallback (`_cmpColName`, still middle-ellipsized) when no key separates the runs, and the untruncated name stays on the title. The pair-only panels (all parameters, variables, images) use the same helper.
- **A comparison's conclusion is written where it is reached**: **Write up** (`openCompareNote`, js/notes.js) opens the notes editor under the Compare toolbar, prefilled with the runs (by their label and full name), a link that reopens the comparison and a `**Result:**` line, and appends it to the notes of *every* run compared — through each run's own project (`postApi(…, e.project_id)`), so a cross-project write-up lands in both databases. The run set is snapshotted when the editor opens, so a comparison re-run underneath a draft cannot redirect it. Before this the only place to record a result was one run's notes, reached by leaving the comparison. Every append goes through `core/utils.join_notes`, the one rule `queries.append_note` and `Experiment.add_note` share.


- **A series is one row; a plot is one row per plot**: `_assign_image_groups` had exactly two shapes in mind — a handful of named plots (`loss.png`, `acc.png`) and a short epoch filmstrip — and both are handled by pairing per file name. A run that writes one image *per test sample* is a third shape, and per file it is hundreds of rows: unreadable when they pair, and worse when they don't, because two runs that scored different samples share no file name and every row reads *No image* opposite its one image. `IMAGE_FAMILY_MIN` (4 members of one normalized family in any single run) marks that family a **series**, and it becomes one row whose cell holds that run's strip (`family: true`, `_imageCellHtml`, first `CMP_FAMILY_CELL_LIMIT` shown with the remainder counted, sorted naturally so `x_2` precedes `x_10` and the same index sits at the same position in both runs). This is the one rule that outranks an exact filename match — the exact match is *correct* for a series and still produces a page nobody can read. It is safe only because the client now keeps **every** member per (run, group): it used to keep the first and drop the rest silently, which is precisely why the server had to refuse to merge a multi-member family at all. Below the threshold nothing moved: two named plots are two rows, and a three-epoch filmstrip keeps its exact names

- **Picking one image out of nine hundred is a search problem, not a scrolling problem**: both surfaces that choose images — the Images tab gallery and Compare's two picker columns — take a file-name query (matched against the path too, so `epoch3/` narrows as well as `ISIC_0042`), debounced, and the box keeps focus and caret across the repaint, because a search that makes you retype after each keystroke is not one. Each states its own emptiness (*no file name matches "…"*) rather than rendering a blank column, and the picker's truncation note now says *search to narrow* instead of only counting what it dropped. Compare's columns repaint through `_repaintCmpImageCols` alone — the comparison has not changed, only what is listed, and rebuilding the result would take the reader's scroll position with it (the "a selection change repaints in place" rule in `dashboard-ui.md`)

- **A comparison you can walk**: comparing sample 41 with sample 42 used to mean closing the modal, scrolling the gallery, re-picking both sides. `openCompareModal` takes the candidate list behind each side (`opts.listA` / `listB`, whatever the picker is *currently showing*, so a search narrows the flipping too), and the modal renders a row per side: the run's name, `◀ n / total ▶`, a *jump to name* box, and the current file. The two sides step independently — the usual act is holding one image still and walking the other — with left/right for A and shift+left/right for B. `_setCompareSide` rewrites only the header, body and nav, so the mode you are in (side-by-side, overlay, swipe) survives a step

- **A reserved box must not be a painted box**: the grid reserves 4/3 per image so a dropped decode cannot collapse the row (see the image-grid rule below), but it also filled that box with `--code-bg` and outlined it. A matplotlib plot is rarely 4/3 and is usually white, so the reservation showed up as a slab around every image — reported as *why are there white boxes around the images*. Transparent background, border only on hover, reservation unchanged
- **Two images side by side means adjacent, not one per half-screen**: the A/B side-by-side mode gave each panel `flex: 1` while `img { max-width: 100% }` never upscales, so a 640px matplotlib plot on a 1920px screen sat centred inside a ~950px column and the pair ended up several hundred pixels apart — the exact distance at which two plots can no longer be compared, in the one view whose whole purpose is comparing them. `flex: 0 1 auto` with `min-width: 0` sizes each panel to its image and still lets it shrink when the pair is wider than the window (the body is `overflow: hidden`, so shrinking is what keeps both visible), and the row's `justify-content: center` then places them together in the middle with only the gap between them

- **A crossfade hides the differences it exists to show**: Overlay mode's only control was an opacity slider, and at any setting between the ends *both* images are partly drawn — so the difference a reader is hunting (a boundary that moved, a handful of wrong pixels, a curve that diverges late) is exactly the thing a fade averages away. The tints answer it instead: each side is projected onto its own channels and the top one is **added** (`mix-blend-mode: screen`), so agreement sums back to neutral grey and disagreement leaves one hue standing alone — a coloured patch on a grey plot is found instantly, and it also says *which run* the extra ink belongs to. `Difference` is the strict form (identical pixels cancel to black) for "are these byte-identical?", where a colour cast would be noise. Four details make it trustworthy. (1) **The tints are SVG `feColorMatrix` projections of luminance, not a CSS `grayscale sepia saturate hue-rotate` chain** — the chain only lands *near* a hue, and near-yellow plus near-blue sums to **pink**, so the first implementation painted an identical pair in false colour, which is the worst thing a difference view can do. (2) **A tinted top image is drawn at full opacity and the slider is replaced by the legend**: at 50% the sum is half of each and every colour is muddy, and a slider that ruins the view it sits under is a trap. (3) **The stack paints itself black and isolates while tinted** — `screen` over a light backdrop saturates to white, and without `isolation: isolate` the blend would reach past the stack into whichever backdrop the reader chose. (4) **The legend is part of the feature**: an unexplained colour scheme is just a strangely coloured image, so the active tint's sentence sits under the buttons. Like the backdrop, the choice persists (`exptrack-overlay-tint`), because a reader comparing 40 pairs picks a scheme once

- **The backdrop an image is judged against is a choice, not a constant**: both image modals painted a fixed near-black behind the image, which is the right answer for a matplotlib plot on white and the wrong one for the two kinds of image an ML project actually produces most of — a dark segmentation mask or sample grid (invisible against it) and a light-on-white plot whose margins vanish. `MODAL_BACKDROPS` (js/core.js) is the list, rendered as swatches by `modalBackdropPickerHtml()` into both headers and applied by `applyModalBackdrop()`, which is the only place that knows the `data-backdrop` attribute name. Three things make it an option rather than a second theme to maintain. (1) **Dark stays the default and stays exactly as it was** — the ask was for an extra option, not a new default, and a changed default is a bug report from everyone who liked the old one. (2) **Every piece of modal chrome reads `--modal-fg` / `--modal-fg-dim` / `--modal-line` / `--modal-hover` / `--modal-field`, never a literal**, because the header, the mode buttons, the nav rows, the jump-to-name field and the swipe divider were all hardcoded `#fff` — a light backdrop would have been white text on white, which is the same failure the design-token rule in `dashboard-render.md` records for aliases that exist in only one theme. The A/B badge keeps its literal white: it sits on `--blue` in every preset. (3) **The choice is per reader and persists** (`localStorage`, `exptrack-modal-backdrop`), because it is answered once and then wanted for every image after it; a per-modal toggle that reset on close would have to be re-answered 900 times. The checkerboard earns its place by answering a question no flat colour can: whether a PNG's white is transparent or painted

- **A modal opened to look closer must never show less than the grid behind it**: every image in the dashboard was sized with `max-width`/`max-height`, which only ever *shrink*. The gallery thumbnail stretches its image to the cell (`width: 100%`, ~180px), so a 128x128 sample — a generated image, a patch, a small heatmap — rendered at 184px in the grid and at **128px** inside a full-screen modal opened from it: clicking to enlarge made the picture smaller, reported as *"if I have 128x128 images they are sooooo small... in the images panel they are bigger than when I click on them"*. `fitModalImages(imgs, availW, availH)` (js/core.js) is the one helper, used by `openImageModal` and by the compare modal's `_fitCompareBody`. Four constraints keep it from becoming its own bug. (1) **One scale for every image in the modal**, computed from the largest of them: overlay and swipe stack two images on the same spot, and independently fitted images would stop aligning — which is the entire content of those two modes. (2) **Capped at `MODAL_IMAGE_MAX_UPSCALE` (4x)**, so a 32px icon fills a reasonable square instead of a wall of blur. (3) **Floored at `MODAL_IMAGE_MIN_UPSCALE` (1.25x)** — a 1200px figure in a 1296px slot is not the problem this solves, and stretching it 8% only softens it; below the floor nothing is written and the existing shrink-to-fit rules stand untouched. (4) **`image-rendering: pixelated` past 2x**, because a 128px raster upscaled smoothly reads as *out of focus* — as though the tracker had degraded the image — while nearest-neighbour reads as pixels, which is what they are. The available box comes from the mode (`_imgCmpAvail`: side-by-side splits the window between two panels, overlay and swipe give each the whole width), and the fit waits for every image to decode — a **broken** image counts itself in on `error`, or one failed load would leave the images beside it unscaled forever

- **Two tabs for the same question at different arities is two half-views**: Compare shipped a *Pair* tab and a *Multi* tab, and the split was not along a seam in the problem — it was along a seam in the implementation. Each tab had grown capabilities the other lacked, and neither set was reachable from the other. Only the pair tab could show the **code diff between two attempts** (the run/run/compare loop's whole payoff), the **notebook variable table**, and the **A/B image overlay**; only the multi tab had the **run picker**, the **chip staging**, the **Configuration table** and the **training-curve overlay**. So a three-run comparison could not reach a code diff at all, and a two-run comparison could not reach the picker that makes runs findable — you had to know which tab held what, and re-pick both runs in a different control to cross over. The merge keeps one view whose panels *specialize* at n=2 rather than a second view that owns them: `_fetchPairExtras` runs alongside the comparison POST when the set is exactly two, and `_pairExtrasHtml` renders all parameters (with the differences toggle), the code diff, the variables and the image overlay from it. The **Delta** column is the same rule in the metric table — a delta between three runs is "against which?", so it exists exactly when the set is a pair. Two constraints made this safe rather than lossy: the extras are fetched in `doMultiCompare` and attached to `data._pair`, never fetched in the renderer, because three controls repaint from the cached payload (metric polarity, chart labels, the differences toggle) and any of them re-requesting five endpoints to redraw a table is the cost the repaint path exists to avoid; and `_repaintComparison` is now the single repaint entry point those three share, rather than three copies of the same five lines. `#compare=pair:` links still resolve — the ids are what the address names, and two of them render the pair panels anyway.

- **A search box can only be used by someone who remembers what to type**: the shared picker's one narrowing tool was a substring match over `hay`, which is the right primitive and the wrong only-option. With two dozen runs listed, "the failed cnn runs" is a set the user can describe exactly and cannot type — the query has to be guessed against a haystack whose contents (`paramColLabel(k) + '=' + v`, the script, tags, studies) are not shown anywhere, so a near-miss returns nothing and looks like an empty project. `_rpFacetBarHtml` puts the values the runs *actually hold* above the list as chips: `status`, `script` (basename), `tag`, and up to `RP_FACET_MAX_GROUPS` (6) parameter groups. Five rules make the bar honest rather than decorative. (1) **The groups are derived from the cache, never hardcoded**, so every chip is a value some run holds and clicking one can never empty the list; a key every run shares is dropped outright, because it cannot narrow anything. (2) **Parameter groups are offered fewest-distinct-values first** — `model` with two values halves the list, while a per-run `seed` splits nothing and is exactly what the search box is for. (3) **Values inside a group are an OR, groups are an AND** (`_rpMatchesFacets`): the reading every faceted list uses, and the only one that can narrow to a non-empty set — an AND inside a group would match nothing the moment a second chip went on. (4) **A count says what clicking that chip would leave**, so it is computed over the rows the query and *every other* group leave, with the chip's own group excluded (`_rpMatchesFacets(entry, def.key)`); counting a group against itself makes every unselected value in it read zero, and counting against the whole project promises rows that are not there. A value that is on but now matches nothing stays listed at `0` rather than vanishing — a chip that hid itself would leave an empty list with no visible cause and nothing to click to undo it. (5) **The narrowing in force is stated** (`_rpActiveFacetCount`, "3 filters on") next to its own **Clear filters**, because a list that is short because of a chip scrolled out of the bar is indistinguishable from a project with four runs in it. The picks and the filters are cleared **separately**: one button for both would make dropping a stray chip discard a selection assembled across four searches. The definitions are memoized on the cache size — `_rpMatchesFacets` runs per row, and rebuilding them inside it made narrowing quadratic in the run count, on the one surface that exists because the project is too big to scan. Everything downstream inherits the facets for free, since `_rpFiltered` is the single answer to "what is listed": `rpSelectAllShown` acts on the narrowed rows, and the footer's off-screen-picks count now reads *hidden by the search or filters* rather than naming the query as the only thing that can hide a pick

- **An image grid inside the scroller must reserve its boxes**: `.multi-compare-image-cell img` had `width: 100%` and no height, so each cell's height came entirely from the decoded image's aspect ratio — zero before the load, and zero again any time the browser drops the decode for an offscreen image, which opening a full-size PNG in the modal is a good way to provoke. The grid lives in `#main-content`, and that element clamps its own scrollTop the instant its content becomes shorter than the current offset (the failure the live-run refresh documents in `dashboard-ui.md`), so a collapse there throws the reader to the top of a comparison they were part-way down — read, correctly, as *the page recentred when I clicked an image*. Every other image grid in the dashboard already reserved its box (`.img-thumb` and `.cmp-img-thumb` both carry `aspect-ratio`); this one, the only one inside the page scroller, was the outlier. It now reserves 4/3 — matplotlib's default figure ratio — with `object-fit: contain`, because a reserved box that *cropped* would make a grid whose entire job is pairing plots lie about the plots. Belt and braces on top of that: **`_holdMainScroll()` (js/core.js) is the shared version of the three lines `refreshDetail` has carried by hand**, and both image modals hold the position across open *and* close — restoring immediately and again on the next frame, since layout can settle a frame late and a clamp that happens then would otherwise stand. Consolidating the close paths is what made that possible at all: the modal closed by three routes (backdrop, ×, Escape) and two of them inlined `.remove()`, so a restore-on-close would have had to be written three times — and, relatedly, the Escape listener leaked on those two routes, once per image ever opened. `closeImageModal()` is now the only way it closes

- **Compare is the only surface that may span projects, and a bare id still means the current one**: run ids are qualified as `<project-id>:<run-id>`, and a **bare** id — every id every existing caller, bookmark and saved URL holds — means the project the request is already about. That is the whole compatibility story, and it is why the separator is a colon against ids that are hex and never contain one (`projects.split_qualified_id`; it takes **ids, never paths**, because on Windows `C:\work\p` would split at the drive colon and read as project `C` — not a vulnerability, since a client never sends a path and the returned id is resolved only against the server's own discovered id->path map, but the contract is the defence). Compare and nothing else: every other view reads a *set* whose members must share a parameter space, so a cross-project matrix, leaderboard or merged run list would be ranking columns that mean different things; Compare reads an explicitly chosen handful of runs, which is the one case where "these two, from wherever they live" is a question the user can actually be asking. `api_multi_compare` groups the posted ids by project and serves the **current project's group first, on the connection it was handed**, then scopes into each foreign root with `cfg.project_scope(path)` and a fresh `get_db()`. Three rules keep that safe. (1) **After the last scope exits it calls `get_db()` once more.** `core.db.get_db()` closes the previous connection when the resolved path changes, so from the first switch the `conn` the route was handed is a *closed handle* — and the thread's cached connection is still the foreign project's. Without the reopen, the next thing to touch either (the POST dispatcher's WAL checkpoint, or the next request this pooled thread serves) works through a dead or foreign connection, and neither raises anywhere the user can see. (2) **A foreign project that is unknown, stale or schema-skewed is refused, before a single query runs** — the same two refusals `handler._activate_requested_project` gives a bad `X-Exptrack-Project` header, and for the same reason: a comparison silently narrowed to the projects that happened to resolve looks like success and answers a different question, and opening a schema-skewed database would migrate and re-stamp it behind its owner's back. The root is resolved from discovery, never from client input. (3) **Each returned run says which project it came from** (`project_id`, `project_name`, `qualified_id`) and every compare surface leads its column with the project name when — and only when — the set actually spans projects: two projects can hold runs with the same name, and auto-generated names are drawn from one shared vocabulary, so that is the ordinary case rather than the unlucky one. A request that qualifies nothing gets no stamp at all and runs exactly the code it always did. The picker cache is keyed by project for the mirror-image reason (`_cmpCacheByProject`, js/detail.js): one cache fed all three pickers, and a run list is entirely a property of the project it was paged from, so it would go on offering project A's runs — under bare ids that now resolve against B — while the user browsed B

- **Choosing a run from another project is the only way the cross-project grammar is reachable, and it must not leak into any other surface**: `openRunPicker` takes `crossProject: true`, and **only `openMultiRunPicker` (Compare) passes it** — the parameter matrix's picker deliberately does not, because what varies is a property of a set whose members share a parameter space and a set drawn from two projects does not. The selector lists what `/api/projects` returns, with a stale or schema-skewed project shown *disabled with its status* rather than omitted ("my other project isn't there" is indistinguishable from discovery being broken); a listing that fails leaves the picker working as the single-project list it has always been, because a dialog that refuses to open is worse than one without an optional control. Four rules keep the ids honest. (1) **`_rpQualify` is the single place an id becomes what it will be handed back as** — bare inside the page's project, `<project-id>:<run-id>` outside it — and the *row's* identity is that qualified id, in `data-id`, in the inline handler (via `escJsAttr`) and in `_rpSelected`: keyed on the bare id, a run in project A and a run in project B could tick and un-tick each other. The page's own project is spelled `''` in both the selector's option value and `_activeProjectId`, so it can never end up with two cache slots under two names. (2) **Switching project replaces the list and never the selection**, since a set assembled across two projects is the entire point. (3) The facet definitions are memoized on the row *count*, so the project is part of the memo key — two projects with the same number of runs would otherwise be offered the first one's values and every chip would filter to nothing. (4) An empty list distinguishes *loading* from *this project has no runs*, which with a project selector above it is now a normal place to land; `_rpLoading` is cleared in a `finally`, or the one case where nothing arrives is the one case that never says so.

- **A run's data comes from the run's project, not from the page's**: `api(path, projectId)` and `postApi(path, body, projectId)` take the project as a trailing optional argument, so every existing one-argument call is unchanged and the return contract (`null` on failure) is identical — every existing guard covers a cross-project fetch too. The project rides on the *request*: switching the page's project to fetch one panel would move every other view under the reader. `_renderMultiCurves` passes `e.project_id`, because with the page's project on the request a foreign run's metrics come back empty and an empty series draws as *a run that logged nothing* rather than one we asked the wrong database about. Images are the exception that proves the rule — an `<img src>` carries no headers at all, which is already why the auth token rides in the query for `/api/file/`, so `fileUrl(path, projectId)` sends the project the same way and each image is stamped with its run's project as the groups are built. The pair-only panels (all parameters, the code diff, the notebook variables, the A/B overlay) are served by endpoints that read **one** database per request, so a cross-project pair **states that they are unavailable** (`_pairCrossProjectNoteHtml`) instead of dropping four panels silently — which reads as a comparison that half-failed, with no way to tell which half. **A pair drawn wholly from one *other* project is still a pair, and its panels are fetched with that project** (`_fetchPairExtras(id1, id2, projectId)`, pair images stamped `_project` for `fileUrl`): `_cmpSpansProjects` is false for it, so it took the pair path — and fetched without a project, it asked the page's database about two runs it does not hold, got `not found`, and all four panels vanished with no note, the exact silence the note above exists to prevent. **A picker that cannot act on its selection says so before it is pressed**: `openRunPicker({minPicks, minReason})` greys out the confirm below `minPicks` and prints the reason in the footer (Compare passes 2); a one-run Compare used to confirm, stage the pick and do nothing. Because a cross-project list shows one project at a time, **every pick is listed in the picker's Selected strip** (`_rpRenderPicked`, labelled via `_cmpLabelFor`, removable), and the footer counts a pick from another project as *in another project*, never *hidden by the search or filters*. A comparison that fails renders `_showCompareFailure(reason)` — *Couldn't compare* plus the server's error and the names of `unknown_ids` — in the result area, never a blank. A chip naming a staged run resolves a qualified id in *that* project's cache and leads with the project name (`_cmpLabelFor` → `splitQualifiedRunId` + `projectName`); looking a foreign run up in the page's list finds nothing and falls back to an id prefix, which is the one label that says least.
- **Multi Compare shows a metric as a spread, not a bar chart**: the per-metric bar-chart grid is now **Metric spread** (`_multiSpreadHtml`, js/compare.js): one row per metric with a dot per run placed between that metric's lowest and highest value, the best run (polarity-aware) ringed and named, and a click (`toggleSpreadChart`) for the full horizontal bar chart sorted best first. The grid drew one 400px chart per metric with every bar from zero, so runs that differed in the third decimal differed by a pixel at the top of identical bars, under rotated labels nobody could read — 45 metrics across 39 runs was most of a 15,000px page. Metrics every run agrees on (a dataset size, a base rate) are listed once at the end as **Same for every run** rather than drawn. Canvas ids stay positional (`multiChartId(i)`).
- **Spread dots are grey until you choose what colour means**: a colour per run was 39 colours from a 10-colour palette — no meaning, and the eye hunted for a pattern that was not there. Dots are `--muted` with the best filled `--status-success`; **Colour by** (`setSpreadColorBy`, remembered in `exptrack-spread-colorby`) paints by one setting with at most 8 values (`_spreadColorKeys`), with a legend, which answers the question colour can: do the `model=hgb` runs sit right of the `rf` ones? Hovering a dot (`spreadHover`) lights that run in every row and fades the rest, so one run can be followed down the list.

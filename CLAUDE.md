# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**exptrack** is a local-first, zero-friction Python experiment tracker for ML workflows. It automatically captures parameters, metrics, and git state by monkey-patching argparse and IPython hooks — no code changes required in user scripts. Uses SQLite (WAL mode) for storage with no external dependencies (stdlib only).

## Installation

```bash
pip install -e .
```

Uses `pyproject.toml` with setuptools. The `exptrack` console script entry point maps to `exptrack.cli:main`.

## Running

```bash
# Initialize a project (creates .exptrack/ and patches .gitignore)
exptrack init [project_name]

# Wrap any training script
exptrack run train.py --lr 0.01 --data train
# Or: python -m exptrack train.py --lr 0.01

# Shell/SLURM pipeline integration (single step)
eval $(exptrack run-start --lr 0.01 --epochs 50)
# ... run training ...
exptrack run-finish $EXP_ID --metrics results.json
# or on failure:
exptrack run-fail $EXP_ID "reason"

# Multi-step pipeline (group steps in a study with numbered stages)
# First call sets EXP_STUDY and EXP_STAGE; subsequent calls inherit automatically
eval $(exptrack run-start --study my-run --stage 1 --stage-name train --lr 0.01)
python train.py; exptrack run-finish $EXP_ID
# EXP_STUDY inherited, EXP_STAGE auto-increments to 2
eval $(exptrack run-start --stage-name eval)
./evaluate; exptrack run-finish $EXP_ID

# Resume a previous experiment (auto-detected from script's --resume flag)
# All metrics, artifacts, and params aggregate into the same experiment
exptrack run train.py --output_dir results/ --resume --ckpt results/model.pt

# Shell pipeline resume
eval $(exptrack run-start --resume --lr 0.01)
# or resume a specific experiment:
eval $(exptrack run-start --resume abc123 --lr 0.01)

# Programmatic resume
from exptrack.core import Experiment
exp = Experiment.resume("abc123")    # by ID
exp = Experiment.resume("abc")       # by ID prefix

# Session Trees (notebook only — opt-in, no-op when not started)
#   %exptrack session start "name"        begin a session (must precede other magics)
#   %exptrack checkpoint "label"          mark stable point (snapshots per-checkpoint diff)
#   %exptrack branch "label"              declare intent for the next divergence
#   %%scratch                             cell magic — runs cell, never logged
#   %%setup                               cell magic — recorded-but-secondary prep code (builds a df you reference later): kept on the node's demoted setup store + a muted experiment event, out of cell lineage/diffs
#   %%pin "label"                         cell magic — runs cell, snapshots cell+output as artifact
#   %exptrack promote "label"             link active experiment to current node
#   %exptrack session end                 close session (open branches → abandoned)
#
# Log results after the notebook run has already finished
#   %exp_log test_acc=0.93 train_acc=0.98   attach metrics to this notebook's
#                                           latest run (works post-hoc)
#
# Compare a run against the run you *mean*, not the one that ran last
#   exptrack variant-of <id> <baseline>     declare this run a variant of another
#   exptrack variant-of <id>                clear the link (back to chronological)
#
# CLI commands: ls, show, diff, compare, history, timeline, tag, untag, note,
#   edit-note, rm, clean, finish, delete-tag, study, unstudy, stage, stale,
#   upgrade, storage, prune, export, verify, ui, notebook-guard, variant-of,
#   sessions, session show|nodes|rm|restore|purge|finalize|rm-node|restore-node|
#     purge-node|empty-trash|trash|rename-node|promote-checkpoint|note  Session Trees
```

## Testing & Linting

```bash
pip install -e ".[dev]"
python -m pytest tests/ -x -q

# The capture tests for the monkey-patched libraries SKIP unless these are
# installed. CI has a dedicated job that installs them and fails if they skip.
pip install -e ".[dev,integrations]"    # matplotlib, numpy, pandas

ruff check .                             # enforced in CI
npx eslint exptrack/dashboard/static/js  # enforced in CI
```

Note `tests/run_all.py` (the legacy runner, also in CI) executes each test file
as a script, so it needs exptrack actually installed — `pip install -e .`, not
just pytest's `pythonpath`. Without it every file fails on `ModuleNotFoundError`,
which looks alarming and means nothing.

Key test files: `test_pipeline_shell.py` (53 tests for shell/SLURM pipeline commands),
`test_experiment.py`, `test_cli.py`, `test_db.py`, `test_capture_argparse.py`,
`test_dashboard_routing.py` (GET dispatch characterization + ordering guards),
`test_dashboard_headers.py` (security headers, over a real socket), etc.

## Architecture

```
exptrack/
  __init__.py                 Package init, exports Experiment, load_ipython_extension
  __main__.py                 python -m exptrack entry point (wraps scripts via runpy, auto-resume detection). **Publishes its wrapper run** via `experiment.publish_run_wrapper(exp)` before running the script, so a wrapped script that creates its *own* `Experiment()` (one written for plain `python script.py`) adopts the wrapper instead of spawning a redundant second metrics-less run for the same script (the "phantom run" — see the **Run adoption** pattern). After finishing, it calls `_maybe_trash_phantom_wrapper(exp, resume)`: if the script instead built its *own* Experiment(s) with explicit identity (a param sweep — which correctly does *not* adopt) and the wrapper logged no metrics of its own, the metrics-less wrapper row is soft-deleted (moved to Trash, recoverable) so an explicit-args sweep no longer leaves an empty phantom row (a resumed run or a wrapper that logged its own metrics is never trashed). Its post-run finish is guarded by `if not exp._finished:` on every path (clean exit, `SystemExit(0)`, and the two failure handlers) so an adopted run the script already finished (its own `with`-block, success or failure) is never double-finished (which `Experiment.finish` raises on). On an uncaught exception the crash handler prints the traceback *before* `_restore_streams` (so it tees into `stderr.log`, which the restore closes) and passes the full formatted traceback to `Experiment.fail(error, traceback=…)`. The `SystemExit` handler (non-zero code) surfaces the chained cause (`SystemExit.__context__`) the same way — a script that catches an error and calls `sys.exit(1)` no longer hides the real exception behind `SystemExit(code)`; a bare `sys.exit(code)` with no `__context__` just records the code. `_TeeWriter` (mirrors stdout/stderr to the log files) no-ops writes/flushes once the log is `closed` so a late write during interpreter shutdown can't raise the `I/O operation on closed file` warning
  config.py                   Project-aware config (.exptrack/config.json), root detection, `GITIGNORE_RULES`/`ensure_gitignore_rules()` (the one additive ignore-rule list, shared by `init` and the token write) and the dashboard-token location + writer (`token_file_path()` / `write_token()` — a secret must never land in the committable config.json)
  notebook.py                 Jupyter: %load_ext exptrack magic + explicit API
  core/
    __init__.py               Re-exports Experiment, make_run_name
    experiment.py             Experiment class, lifecycle, param/metric/artifact logging
    db.py                     SQLite schema (9 tables), migrations, WAL mode. **Schema-version gate**: the DB carries a `PRAGMA user_version` stamp (`_SCHEMA_VERSION`); `get_db()` skips both the open-time `PRAGMA quick_check` and `_ensure_schema()` entirely when the stamp matches (steady-state fast path), and `_ensure_schema(conn, force=True)` (used by `exptrack upgrade`) always re-runs the full check. **Bump `_SCHEMA_VERSION` by +1 with any schema change** (new table/column/index or migration helper) or existing DBs never see it. `_ensure_schema()` is a thin orchestrator: `_create_base_schema()` (idempotent CREATE TABLE/INDEX) + one `_migrate_*` helper per table (`_migrate_session_nodes`, `_migrate_experiment_session_link`, `_migrate_artifacts`, `_migrate_metrics`, `_migrate_params`, `_migrate_experiments`), each built on the shared `_add_columns(conn, table, {col: ddl})` primitive (with `_table_columns(conn, table)`) which adds only absent columns and returns the set it actually added — so a helper gates its one-time backfill/index creation on a *real* migration, and an already-migrated DB is a guaranteed no-op (the idempotency the tests assert). The whole thing is idempotent and individually unit-testable
    utils.py                  Shared safety helpers: `debug_enabled()`/`debug_log()` (stderr diagnostics gated by the `EXPTRACK_DEBUG` env var, read fresh each call so it can be toggled mid-notebook-session) and `safe_call(fn, …, default=…, context=…)` — the one-liner replacement for the `try/except: <fallback>` idiom used throughout capture/db. Failures swallowed for run-safety surface here only when `EXPTRACK_DEBUG` is set. The capture/git swallow sites are migrated onto these: the per-cell/per-savefig warning prints in `cell_lineage.py`, `notebook_hooks.py`, `matplotlib_patch.py`, `script_tracking.py`, `session_hooks.py`, and `core/git.py` now go through `debug_log` (quiet by default, no per-cell stderr spam), and `variables.var_summary` builds its `ndarray/DataFrame/Series/Tensor/repr` summaries via `safe_call`. Also **`json_dumps(data, **kw)`** — see the **JSON we emit must be JSON anyone can parse** pattern
    naming.py                 Run name generation (readable: {MonDD}_{script}__{params}__{uid}; legacy "numeric" style via `naming.date_style`) + `looks_auto_named` fingerprint helper. `make_run_name` skips internal `_`-prefixed bookkeeping params (`_var/…`, `_code_change/…`, `_cells_ran`) before picking the top N keys, and path-sanitizes every component (`_path_safe`) so a value with slashes/spaces can never produce a name that breaks the on-disk output-folder rename
    hashing.py                File integrity hashing (SHA-256, partial for large files)
    dataset.py                Dataset/input versioning — `capture_dataset_manifest(exp)` scans captured params for dataset-shaped values (existing data files by extension, or dataset-shaped keys like `--data_dir`/`--train` pointing at an existing path), fingerprints each (files via partial content hash, dirs via sorted `(relpath, size)` listing — no byte reads), and logs the result as the `_dataset_manifest` param. Lives in `core/` (only depends on `core.hashing`/`core.utils`) so `Experiment.finish()` calling it isn't a core→capture inversion; `capture/dataset.py` re-exports it for back-compat. Best-effort (never raises)
    script_snapshot.py        Script source capture: content-addressed snapshot + `git diff HEAD` of the run's own script, called by `Experiment._maybe_snapshot_script`. Its expensive half (`_script_facts`: read, md5, `store_code_snapshot` + commit, and a `git diff` subprocess) is memoized module-level on `(abspath, mtime_ns, size)` — every `Experiment()` snapshots its script, so a sweep constructing 100 runs in one process would otherwise redo all of it 100 times on a byte-identical file (~69 ms each, ~7 s per sweep, plus 100 fsyncs and 100 subprocesses). Editing the file mid-process invalidates the entry
    storage.py                Storage measurement + metric reclamation. `table_byte_sizes(conn)` reads SQLite's `dbstat` virtual table, so per-table bytes are **exact** (real pages, each table's indexes and free space included); below the table level nothing has page-level identity, so `metric_storage(conn)` (bytes per metric key) and `experiment_storage(conn)` (estimated database bytes per run, largest first) apportion that true total by row count and are labelled *estimated* everywhere they surface. Returns `{}` when dbstat is unavailable so callers fall back to a row-count estimate rather than reporting a confident zero; the walk covers every page, so it is a report-time call, never a hot path. `metric_storage` aggregates with two stacked `GROUP BY`s rather than a `COUNT(*) OVER (PARTITION BY …)` window (the window materialises one intermediate row per metric row — ~20x slower on 2M rows), and `experiment_storage` joins one aggregate pass per child table instead of six correlated subqueries per experiment, with `_shared_diff_bytes` computing every run's diff share in three whole-database queries rather than three per run. Also `prune_metrics` / `preview_metric_prune` — see the **Reclaiming metric resolution after the fact** pattern
    trash.py                  Unified-trash aggregation: `list_unified_trash(conn)` / `count_unified_trash(conn)` gather trashed experiments (`experiments.deleted_at`), trashed session nodes (`session_nodes.deleted_at`, grouped by session, key `sessions`), and trashed *whole* sessions (`sessions.deleted_at`, key `trashed_sessions`) into one payload for the dashboard's single Trash view (three sections: Experiments / Sessions / Session nodes). The destructive-file primitive (`_trash_or_local`) already lives in `db.py` and is shared by both domains; per-kind soft-delete/restore/purge stay in `db.py` (experiments) and `sessions/manager.py` (nodes + whole sessions)
    git.py                    Git branch/commit/diff capture. `_git_status(*cmd)` returns `(ok, stdout)` and runs every git command with `stdin=/dev/null` and a non-interactive env (`GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=echo`, `GIT_OPTIONAL_LOCKS=0`) so a credential prompt or contended `index.lock` can never freeze a notebook cell (e.g. `%exptrack checkpoint`); `_git()` is the string-only wrapper (`""` on error). **`git_diff` distinguishes a clean tree from a capture failure**: a genuinely empty diff is `""`, but when the diff command errors *inside a git repo* (`_is_git_repo()` true) it returns the sentinel `CAPTURE_FAILED` (`[capture-failed]`) so a failed capture is never recorded or rendered as "no changes"; outside a repo an empty result stays `""`. The sentinel is handled wherever `[compacted…]` is (CLI `diff`/`show`, dashboard detail + session diff render, export, and compaction/stats skip-filters) so a failed capture is never rendered as a diff or compacted into a ref. **There are three such markers and they all live in `core/db.py` beside `resolve_git_diff`, which produces two of them**: `DIFF_UNAVAILABLE` (`[diff-unavailable]`), `COMPACT_PREFIX` (`[compacted…]`), and `CAPTURE_FAILED` (re-used from `core/git.py`). `DIFF_UNAVAILABLE` is returned when a stored `[ref:sha256:…]` pointer's `git_diffs` row is gone — that case used to **fail open**, handing back the raw pointer, so every consumer rendered the literal `[ref:sha256:…]` string as the diff body and `diff_lines` counted it as one line of changes. Two shared classifiers gate every consumer: **`is_diff_sentinel(diff)`** ("this is a status, not diff text" — works on a raw column value or a resolved one) and **`diff_sentinel_kind(diff)`** (`'capture_failed' | 'unavailable' | 'compacted' | None`, shipped to the client on the `/api/diff` payload as `sentinel` so the JS branches on a field instead of re-hardcoding marker strings — they had already drifted between the two JS renderers). Always use these rather than re-testing prefixes: every read (`diff_lines`, CLI `diff`/`show`), every write-out (dashboard + CLI diff export) and **both** compaction paths *and their previews/dry-runs* gate on them, so a sentinel is never measured, rendered, written into a ```` ```diff ```` fence, or stamped over with a `[compacted — N B stripped]` summary for a body that no longer exists

  capture/
    __init__.py               Re-exports capture modules
    argparse_patch.py         Patches parse_args() and parse_known_args(). The hooks are installed once on `ArgumentParser` but read a module-level `_active_exp` that every `patch_argparse(exp)` call retargets — so a second run in the same process (notebook kernel, programmatic reuse, back-to-back runs) captures onto the *current* experiment, not the first one the class was ever patched for
    matplotlib_patch.py       Patches plt.savefig() and Figure.savefig() (also records the figure path on the active Session Trees node, by reference)
    tensorboard_patch.py      Patches `SummaryWriter.add_scalar`/`add_scalars`/`add_histogram` on `torch.utils.tensorboard` and `tensorboardX` so scalars/losses/activation histograms logged to TensorBoard mirror into exptrack's `metrics` table (zero code change, no `tensorboard`/`protobuf` dep — patches the writer at the call site, never parses `.tfevents`). Retargetable module-level `_active_exp` (like `argparse_patch`) plus a `_nb_state["exp"]` fallback for notebooks. Since writer modules are usually imported *after* the patch installs (patching precedes the script run), it patches already-imported writers **and** registers a one-shot `sys.meta_path` import hook (`_WriterImportHook`/`_PatchingLoader`) that patches a writer imported later. `add_histogram` values are summarized to `<tag>/{mean,std,min,max}` via numpy (skipped if numpy absent). Originals always run; best-effort throughout (a capture failure never crashes training). Gated by `auto_capture.tensorboard`
    notebook_hooks.py         IPython pre_run_cell + post_run_cell hooks, cell snapshots (skips %%scratch cells).   cli/

- **`capture/notebook_hooks.py`** — `pre_run_cell` + `post_run_cell` hooks: stdout capture (a `_StdoutTee` installed in the pre-hook tees `sys.stdout` to a buffer so `print()` output is recorded while still showing in the notebook; `_collect_stdout_capture` always tears it down — even on an early return — so the tee never leaks, and `_combine_cell_output` merges captured stdout with the trailing-expression repr into one capped blob), content-addressed cell lineage, diff against parent cells, variable change detection with fingerprinting, assignment expression enrichment, timeline event emission, HP auto-detection, cell snapshot saving. - **`capture/variables.py`** — Variable fingerprinting (scalars via repr, ndarrays/DataFrames/Tensors via content hash, collections via JSON). DataFrames/Series are content-hashed via `pandas.util.hash_pandas_object` (`_hash_pandas`) which is object/string-column safe and **stable across cells** — the old `df.values.tobytes()` hashed *pointer addresses* for object columns and churned every cell, falsely flagging untouched frames as "changed". Object-dtype ndarrays avoid `tobytes()` for the same reason. Content hashing is size-capped by `var_fingerprint(val, max_bytes=…)` — objects whose buffer exceeds the cap (config `var_fingerprint_max_mb`, default 100), and every fallback path, use a **stable shape/dtype signature** (`_stable_sig`, never `id()`) so an untouched object keeps the same fingerprint (the tradeoff: the fallback won't catch a pure in-place edit that leaves shape/dtype unchanged; the `hash_pandas_object` path does). HP name regex detection. Assignment expression extraction from cell source. Observational cell detection. **`notebook_hooks._capture_variables` fingerprints each namespace variable exactly once per cell** (single pass building both the new/changed sets and the snapshot) and returns, per variable, both a rich `display` (assignment-form, for the timeline `var_set` event) and a stable bare-summary `param` value (for the `_var/<name>` param), so re-logging an unchanged variable is idempotent
- **`capture/matplotlib_patch.py`** — Patches `plt.savefig()` and `Figure.savefig()`. Copies figures to experiment output directory. Buffers artifacts saved before experiment creation. Deduplication by path. Also, if a Session Trees node is active (`get_current_session()`), records the saved figure path on that node via `SessionManager.record_image()` (by reference, no copy) so branches can show/compare their plots — wrapped so it never breaks the user's savefig
- **`capture/cell_lineage.py`** — Content-addressed cell tracking: SHA-256 hash of source, parent discovery via 30% SequenceMatcher similarity, simple_diff for cell change display. `is_magic_only(source)` (source is only IPython magics/`!`shell/comments/blanks **and** has at least one magic line) gates lineage: `find_parent_hash` returns `None` for a magic-only subject and skips magic-only candidate rows, so an `%exptrack checkpoint/branch` cell never gets a fuzzy-matched "parent" to word-diff against (two short magics easily clear the 30% bar) and never pollutes matching for real code cells. `notebook_hooks._process_cell_lineage` short-circuits magic-only cells to no parent / no diff / no new-or-edited badge (still stored so "view source" works). Distinct from `notebook_hooks._is_magic_only`, which also treats comment/blank-only cells as magic-only for the deferred-start skip. **Perf**: `find_parent_hash` used to run a full `SequenceMatcher.ratio()` against *every* stored cell (O(N·L²) per executed cell). An exact re-run now short-circuits via `lookup_stored_parent(cell_hash, notebook)` (one PK lookup — a content-addressed cell's parent is already frozen), and the fuzzy search prunes candidates by a length band and `real_quick_ratio`/`quick_ratio` upper bounds (reusing one `set_seq2`-fixed matcher) before the real ratio — behaviorally identical to the old scan (the exact `>= 0.3` acceptance boundary and first-match tie-break are preserved). **`lookup_stored_parent` is notebook-scoped**: identical source in two notebooks hashes to the same `cell_hash` (and `store_cell_lineage` INSERT-OR-IGNOREs on that shared PK), so without the `notebook` filter a parent resolved in notebook A would leak into notebook B; a hit in a different notebook reports `found=False` so the fuzzy search runs against B's own lineage
- **`notebook.py`** — `%load_ext exptrack` magic + explicit API (`start()`, `metric()`, `metrics()`, `param()`, `tag()`, `note()`, `artifact()`, `out()`, `done()`, `current()`, `log_last()`). **`log_last(**metrics)` / `%exp_log k=v` is the post-hoc path** — see the **Logging the numbers after the run is over** pattern; `_parse_metric_assignments` is its `key=value` parser (reports malformed and non-finite tokens rather than dropping them, so a typo can never look like a logged metric). Deferred experiment creation (skips `%load_ext` cell itself) — fires on the first real code cell. Gated by `auto_capture.notebook` (default true): when false, `load_ipython_extension` registers the magics and session/cell hooks but passes `start_fn=None`, so no run is auto-created — Session Trees can be used standalone and runs are started explicitly via `%exp_start` / `start()`
- **`core/queries.py`** — read-side query layer for the CLI and dashboard (`list_experiments`, `get_experiment_detail`, `get_stats`, `diff_runs`/`format_run_delta`, study/tag aggregation and mutators). **`_json_list(value, context)` is the tolerant parser for the `tags`/`studies` JSON columns** and must be used instead of a bare `json.loads` at every read site: a hand-edited DB, an older writer, or a third-party script can leave a bare string (`baseline` instead of `["baseline"]`) or garbage in those columns, and a raw parse propagated out of `list_experiments` and killed the *whole* request — the dashboard then rendered an empty table with no error while the stats cards still reported a run count (`get_stats`/`get_all_tags` had always guarded; the list path had not). It salvages a bare string as a one-element list, drops non-string members, degrades anything unusable to `[]`, warns on stderr, and never raises. **`_latest_metric_rows(conn, exp_ids)` is the one implementation of "each key's latest value + source"**, shared by `get_latest_metrics`, `get_latest_metrics_with_source` and the batched `…_batch` the experiment list calls — and it must never go back to a correlated subquery. It used to pick the latest point with `WHERE COALESCE(step,0) = (SELECT MAX(COALESCE(step,0)) FROM metrics m2 WHERE m2.exp_id=m.exp_id AND m2.key=m.key)` plus a second correlated subquery for the distinct-source count, each of which re-scans a whole `(exp_id, key)` group *once per row in that group* — so the cost is quadratic in points-per-metric. That is invisible on a few hand-logged numbers and fatal on real runs: ~70 experiments × 5 keys × 2k points (680k rows) never completed, so `/api/experiments` hung indefinitely while `/api/stats` — which doesn't touch `metrics` — returned instantly, and the dashboard rendered its headline counts above a permanently empty table with no error (`loadExperiments` never resolves, so not even the empty-state row is drawn). It's now two linear passes over the same indexed row set — a `ROW_NUMBER()` window for the latest point and a plain `GROUP BY` for the source count — which also makes the pick **deterministic**: ordering by `(step, ts, rowid)` means the genuinely last-logged point wins, where the old query returned every row tied at the max step and let the Python dict keep whichever SQLite emitted last. An index on `(exp_id, key, step)` was measured and deliberately *not* added — it bought ~4% for ~30% more database size, because the remaining cost is the unavoidable single scan of the listed runs' metric rows. `tests/test_latest_metrics_scaling.py` guards the complexity by counting **SQLite VM opcodes** (via `conn.set_progress_handler`) rather than wall-clock, so the regression test is deterministic and machine-independent: doubling the points must not quadruple the work (old plan: exactly 4.0×; new: ~2×)
- **`cli/`** — subcommands across 4 modules (the dispatch table in `cli/main.py:_DISPATCH` is the authoritative list; don't quote a count in docs, it has drifted twice). ANSI-colored terminal output. Shell pipeline commands (`run-start`/`run-finish`/`run-fail`) print to stdout for `eval $()` capture, everything else to stderr. **Exit-code contract**: hard-error / not-found paths (a missing experiment, a bad/missing argument) route through `cli/formatting.py:die(msg, code=1)` — message to **stderr**, non-zero exit — so `exptrack show $ID || …` works; informational no-ops ("already done", "tag not found on any experiment", empty-list results) stay exit 0 but print to stderr
- **`plugins/__init__.py`** — `Plugin` base class with 4 lifecycle hooks (`on_start`, `on_finish`, `on_fail`, `on_metric`). `registry` singleton loads plugins dynamically from config. `make_exp_proxy(conn, exp_id, status, duration_s)` builds a full plugin-facing experiment stand-in from DB rows (all fields `github_sync` reads: `project`, `created_at`, `duration_s`, `script`, `git_*`, `_params`, `tags` as a **list**, `notes`, and a `last_metrics()` closure) — used by both `cmd_finish` and `cmd_run_finish` so a lifecycle-command sync no longer silently `AttributeError`s on a missing field
- **`dashboard/`** — Web UI: stats cards, experiment list with filters, detail view with overview chart preview, dedicated Charts tab (single/all view with scale controls and configurable downsampling), timeline view with cell source viewer, compare view (pair + multi), image comparison, git diff viewer, per-experiment Confusion Matrix tab (binary or NxN, computes accuracy/precision/recall/F1 with macro and weighted aggregates; supports **multiple named matrices per experiment** with per-matrix palette + intensity slider, side-by-side **Compare** view with a metric-difference table; "Save as metrics" persists results via `/api/experiment/<id>/log-result` (prefixed with the matrix name when more than one matrix exists); matrix state persisted server-side via `POST /api/experiment/<id>/save-confusion` and `GET /api/confusion/<id>`, stored as a JSON-encoded manual param `_confusion_matrices`; legacy localStorage state auto-migrates on first load). ## Key Design Patterns

- **Run-vs-run loop (change → break → fix → rerun → compare)**: exptrack's headline workflow is iterating on one or two lines at a time, so the loop is first-class end to end. **(1) Broken runs self-identify**: a notebook cell that raises is detected in `notebook_hooks._post_run_cell` (`_detect_cell_error` → `_nb_state["last_error"]`, read+cleared by `consume_cell_error`); the automatic finish paths (`notebook._finish_active(auto=True)` — kernel-shutdown atexit, a new-run boundary) mark that run `failed` with its traceback instead of silently `done`, while an explicit `%exp_done`/`done()` (`auto=False`) always declares success. `Experiment.finish()` honors `auto_trash_failed` (config, default off) to Trash a failed run at finish. The dashboard hides `failed` runs behind a **Show failed (N)** toggle (`showFailed` state, `getFilteredExperiments`). **(2) Every run reports its delta**: `core/queries.py:get_previous_run` (next-older run of the same script, ordered by **`(created_at, rowid)`** — two runs launched inside the same clock tick tie on the timestamp and the tie-break was whatever order SQLite returned, so "previous" could resolve to the run that started *after* this one; `rowid` is insertion order, i.e. launch order, so the chain always runs backwards in time. `find_previous_by_script` uses the same row-value comparison). **Which runs can be a baseline is one shared rule** (`_BASELINE_WHERE`, applied by both lookups so the strip, the card and the finish-time summary never disagree): trashed runs are excluded — they're gone from every list, so a delta against one names a baseline the user can't open or verify, and deleting a run between two attempts would silently change the numbers with no visible cause; instead "previous" walks back to the next surviving run, matching the list. `running` runs are excluded too — their metrics are still moving, so a delta against one doesn't reproduce a minute later and a parallel sweep would compare each run against a half-finished sibling (a row left `running` by a killed process is what `exptrack stale`/`finish` are for). But a **`failed` run is kept** as a baseline: "it broke, I fixed it, what changed?" is the loop this whole affordance exists for, and skipping the failure would hide exactly the comparison wanted — its `status` is carried through on both payloads instead, so `format_run_delta` prints `prev (name, failed)` and the dashboard marks the baseline `failed` (`_baselineFailedTag` on both the card header and the strip's baseline chip) with a note that the metric values are wherever it crashed, not a finished result (params and code are exact either way)) + `diff_runs` (`{param_changes, metric_changes, code_changed, source_changed}`, skips `_`-prefixed params; a **metric present on only one run is not a change** — a key missing on one side is "not measured", not a `None→value` move, so it's skipped, killing the flood when comparing against a metrics-less/phantom or pre-metrics run; and **float noise is not a change** — `_metric_moved(a, b)` gates every metric on a relative epsilon (`_METRIC_EPS_REL` = 1e-12, mirrored client-side as `metricMoved` in `js/core.py`), because `0.9 + 0.03` and `0.85 + 0.04 * 2` are both 0.93 yet differ by 1.1e-16, which surfaced as a change rendering `▼ -0.0000 (-0.0%)` — a delta reading as zero on a row that exists only because something supposedly moved). **Two code-change facts, kept separate**: `code_changed` is the repository-wide `_run_code_signature` (commit + the *entire* working-tree diff + `_script_hash`), while `source_changed` compares `_run_source_identity` — the run's own content-addressed script-snapshot hash, else its ordered `cell_exec` cell hashes, i.e. exactly what `compare_run_code` diffs (`None` when either run captured no code, so "same" is distinguishable from "unknown"). Collapsing them into one flag made an edit to *any other tracked file* stamp a byte-identical rerun with an amber `code changed` chip, directly contradicting the Code-changes panel beneath it; the strip now renders `code changed` only for `source_changed`, and a muted `repo changed elsewhere` chip (`.vs-chip-repo`, via `_vsCodeChip`) for the wider signal, with `format_run_delta` making the same distinction. **Deltas never round a real move to zero**: `fmtDeltaNum` drops to exponential below 1e-4, `fmtDeltaPct` prints `<0.1%` instead of `0.0%`, and `fmtMetricPair(before, after)` (plus `_vsFmtPair` for the strip's chips) widens precision until the two sides differ, since at a fixed 4dp a genuine 1e-7 move printed the same string twice + `format_run_delta` produce a one-line finish summary (`Experiment._print_delta_vs_previous`) and the dashboard detail "vs previous" strip (`GET /api/run-delta/<id>`; its baseline chip states how much **earlier** the baseline ran (`relEarlier`, e.g. "2 days earlier" / "just before", with the absolute timestamp in the tooltip and `current_created_at` added to the payload to compute it) and `_VS_PREV_LABEL` spells out "the last run of this script started before this one" — an absolute time can't carry that: `fmtDt` resolves only to the minute, so two runs launched seconds apart print the same string — "previous" alone is ambiguous when the run list is newest-first, so the run being compared against sits *below* the current row and reads as the next one). **(3) Every run stays re-runnable**: the real launch command is captured into `experiments.command` — for shell pipelines via `run-start`/`run-finish --cmd` (`_capture_pipeline_command`, so a run wrapped in a bash/SLURM script records the true command, not a truncated wrapper argv), and for the `exptrack run` / `python -m exptrack` **runpy** path via `__main__.main`, which builds a plain runnable `python <absolute-script-path> <args>` *before* mutating `sys.argv` and threads it through the new `Experiment(command=…)` param (falling back to `_build_command()` from `sys.argv` when not supplied). Without this, `cmd_run` left the script as `argv[0]` and `_build_command()` basenamed it — the reproduce box showed just `basic_script.py`, no interpreter, not runnable. The dashboard **Reproduce box** can toggle the shown command between this plain `python …` form and the tracked `exptrack run …` form (interpreter-prefix swap, lossless; `_preferredReproForm`/`_reproFormAlt`/`toggleReproduceForm` in `js/core.py`, pref in localStorage `exptrack-reproduce-tracked`). Also, the full script/shell-script source is snapshotted content-addressed into `code_snapshots` (`capture_script_snapshot` → `store_code_snapshot`, deduped by hash, `.ipynb` never stored, capped by `snapshot_max_kb`) and referenced from the `_code_snapshot` param. **(4) A notebook attempt = a run with zero ceremony**: `%exp_new` (and `start(new=True)`) closes the current run and opens a fresh comparable one without a kernel restart — put `%exp_new` at the top of the notebook to make every Run-All a separate attempt. **(5) "See what's best" is one click**: the experiment table's **Sort by metric** selector orders runs by a chosen metric's latest value (`setMetricSort`/`updateMetricSortOptions`, `getFilteredExperiments` `metric:` sort). **(6) Compare shows the edit**: `compare_run_code(conn, base_id, new_id)` returns the code diff between two runs — paired `cell_exec` cell-source diffs for notebooks (notebook JSON is excluded from git diffs, so the cell edit only lives in `cell_lineage`), or the `_code_snapshot` script-source diff for scripts — surfaced on `/api/compare` (`code_diff`) and rendered in the Compare view's **Code changes** panel via the shared word-level diff renderer (`_renderCompareCodeDiff` → `_lineDiffRows`/`_renderDiffRows`)
- **Logging the numbers after the run is over**: the notebook loop routinely produces the result *after* the run has finished — you run the notebook, close it out, then evaluate and only then have test/train accuracy. Every other logging path needed either a live run (`metric()`) or a run id you had to go find (`exptrack log-metric <id>`), so the numbers most worth keeping were the most awkward to attach. `notebook.log_last(**metrics)` — surfaced as **`%exp_log test_acc=0.93 train_acc=0.98`** — logs onto the active run when there is one, and otherwise resolves the most recent surviving run of *this notebook* via `queries.find_latest_by_script`, resumes it, logs, and finishes it again so it is handed back in the state it was found (not left `running` forever). Three properties are load-bearing: **(1)** the chosen run is always printed, because attaching a number to the wrong run *silently* is worse than not attaching it; **(2)** trashed runs are excluded from the lookup for exactly the reason they can't be a baseline — a run deleted from every list would file the number where the user cannot see it; **(3)** `_parse_metric_assignments` reports a malformed or non-finite token instead of dropping it, since a metric that looks logged but isn't is the worst outcome of the three (non-finite is refused here for the same reason `json_dumps` scrubs it on the way out — `Infinity`/`NaN` are not parseable JSON).
- **A run can name its own baseline (`variant_of`)**: every delta exptrack shows — the "vs previous" strip, the "What changed" card — resolves its baseline *chronologically*, and that is wrong for the commonest loop in the product: re-run one notebook with a different model and "the previous run of this script" is whatever happened to run last, not the run you mean to compare against. A run may therefore declare the run it is a variant of, and that target wins over chronology in **both** resolvers (`queries.get_previous_run` and `find_previous_by_script`, via the shared `_explicit_baseline`) so the strip and the card can never name different baselines. It is stored as the **`_variant_of` param, not a column**: the `_` prefix already keeps it out of run naming, the params table and the param diff, and it needs no migration or `_SCHEMA_VERSION` bump. `_explicit_baseline` re-applies `_BASELINE_WHERE` to the target rather than trusting the link, so a **stale link degrades to chronological** — a trashed or still-running target must not leave the run with no comparison at all, which is strictly worse than the default it replaced. `set_variant_of` refuses a self-link, an unknown target and a one-step cycle (A→B while B→A, after which neither run has a stable baseline). Surfaced as `exptrack variant-of <id> [baseline]` (omit the baseline to clear it), `POST /api/experiment/<id>/set-variant-of`, and a `variant_of` field on the detail payload.
- **Run adoption (no phantom run under `exptrack run`)**: `exptrack run script.py` (`__main__.main`) must create its wrapper `Experiment` *before* the script runs (argparse/savefig/TensorBoard patching + stdout capture all need a live run up front) and injects it as the script's `__exptrack__` global. A cooperative script logs onto that global → one run. But a script written for plain `python script.py` — which does `from exptrack.core import Experiment; with Experiment() as exp:` and ignores `__exptrack__` — would create a *second* run for the same script: the wrapper gets the code snapshot but no metrics, the script's own run gets the metrics, and the same-script diff then floods with `None→value` changes. To prevent that, `__main__.main` calls `experiment.publish_run_wrapper(exp)` to register the wrapper as adoptable; `Experiment.__new__` claims it (once, via `_claim_run_wrapper`, which sets `_adopted=True`) and returns the wrapper instead of a fresh instance, and `__init__` short-circuits when `self._adopted` so the wrapper isn't re-created. Adoption is deliberately narrow: **only a bare `Experiment()` (no args/kwargs) adopts** — a script passing its own `name`/`params`/… clearly wants its own run and is never silently merged (a sweep loop keeps independent rows) — and **only the first** construction adopts (the wrapper is claimed once). `Experiment.resume` uses `object.__new__` so it bypasses adoption; notebooks and plain `python` never publish a wrapper, so both are unaffected. Because an adopted `with Experiment()` block finishes the wrapper itself, `__main__`'s post-run finish/fail calls are all guarded by `if not exp._finished:` (a second `finish()` raises "Cannot finish twice"). **The arg-passing-sweep case is handled by trashing, not adoption**: a script that constructs Experiments with explicit args (a sweep) deliberately does *not* adopt — merging would silently drop each run's distinct name/params — so those runs get their own rows, but the wrapper is then left metrics-less. `Experiment.__init__` flags this: while the wrapper is still published (`_run_wrapper` non-None), any *non-adopted* construction of a different `Experiment` sets `_run_wrapper._had_foreign_child = True` (the wrapper's own `__init__` runs *before* `publish_run_wrapper()`, so it never flags itself). At finish, `__main__._maybe_trash_phantom_wrapper(exp, resume)` soft-deletes the wrapper (`trash_experiment` → Trash, recoverable) when it saw a foreign-built run **and** logged no metrics of its own — so an explicit-args sweep under `exptrack run` no longer leaves an empty phantom row. **The "no data of its own" test counts artifacts as well as metrics**, because savefig/auto-output capture stays pointed at the wrapper for the whole script: a sweep that plots per iteration without logging a metric leaves its only artifact rows there, and trashing on the metric count alone took the plots out of the Images tab with no hint. The rows every wrapper gets for free are excluded from that test — the `output_dir` row and the `[log] stdout.log`/`[log] stderr.log` rows the stream tee registers — since counting those means no wrapper is ever a phantom and the trashing silently stops happening at all. Guarded: a resumed run (`--resume`) and a hybrid wrapper that logged its own metrics are never trashed. `Experiment.resume` uses `object.__new__` so it bypasses adoption; notebooks and plain `python` never publish a wrapper, so both are unaffected
- **Zero-friction capture**: Argparse monkey-patching and IPython hooks intercept params without user code changes
- **Diff-only storage**: Script changes are diffed against `git HEAD`; notebook snapshots store only cell diffs and variable change hashes — no full-source copies, keeps `.exptrack/` light
- **Content-addressed cell lineage**: Cells identified by SHA-256 of source content, parent found via 30% SequenceMatcher similarity. Handles cell reordering and splits. **Magic-only cells are excluded from lineage** (`is_magic_only`) — `%exptrack checkpoint/branch`, `%load_ext`, etc. are commands, not editable code, so they get no parent, no diff, and no `new`/`edited` badge in the Timeline, and are not offered as parents for real code cells. The Timeline view also guards at render time (`_isMagicOnlyCell`) so runs captured before this fix still display cleanly
- **Project root detection**: Walks parent directories looking for `.git` or `.exptrack/`
- **stdout/stderr separation**: Shell pipeline commands (`run-start`) output `export` statements to stdout so `eval $()` works; all status messages go to stderr
- **Auto artifact linking**: `plt.savefig()` is monkey-patched so saved plots auto-register as artifacts. Figures saved before experiment creation are buffered and flushed
- **TensorBoard metric auto-capture**: `capture/tensorboard_patch.py` monkey-patches `SummaryWriter.add_scalar`/`add_scalars`/`add_histogram` (on both `torch.utils.tensorboard` and `tensorboardX`) so any scalar/loss/activation-histogram already routed through TensorBoard is *mirrored* onto the active experiment's `metrics` table — the metrics analogue of the savefig→artifact patch. Best-effort — a failure here never crashes the user's run
- **Failure capture (traceback, not just a message)**: When a wrapped script crashes, `Experiment.fail(error, traceback=…)` stores the short message as the `error` param (backward compat) **and** the full formatted traceback (file + line) as the `_error_traceback` param — `_`-prefixed so it's skipped by run-naming and the param overwrite-warning, capped at `_MAX_TRACEBACK_CHARS` (20k). `get_experiment_detail` pops it out of `params` into a dedicated `error` key, and the dashboard detail view renders a **Run failed** panel (`.error-panel`, with a Copy button) on failed runs. The `__main__.py` crash handler prints the traceback *before* `_restore_streams` so it also lands in `stderr.log` (the restore closes the log files). The `SystemExit` path matters as much as the bare-`raise` path: a script that catches an exception and calls `sys.exit(1)` (common with frameworks/CLIs) would otherwise record only `SystemExit(code)` — the handler now follows `SystemExit.__context__` to the real chained cause and surfaces *that* traceback (terminal + log + DB), while a deliberate `sys.exit(code)` with no chained cause just records the code. Best-effort — capturing the traceback never crashes the failure path

- **Scannable experiment table at scale (param columns · empty-column collapse · readable names)**: The main table's job is answering "what did I change and what did it do?" across a hundred near-identical runs, so three things are load-bearing. **(1) Params can be columns.** A column id of the form `param:<key>` (`PARAM_COL_PREFIX`, `isParamCol`/`paramColKey`/`paramColLabel` in `js/core.py`) adds any captured hyperparameter as a real, sortable column — `ALL_COLUMNS` used to be a fixed list, so the very thing that differs between two runs of the same script (`--lr`, `--threshold`) was invisible in the list and required opening every run. - **Polarity-aware metric deltas (green means better, not bigger)**: Every delta the dashboard renders goes through `metricGoodDirection(key)` → `_deltaVisual(key, d)` in `js/core.py`, which returns `-1` when *lower* is better. - **Failures are visible, never a silently blank view**: Two layers, because a blank table that claims "140 total runs" is worse than an error. **Server side**, `core/queries.py:_json_list` keeps one corrupt `tags`/`studies` row from taking down the whole list request (see **`core/queries.py`** under Key modules). **Client side**, `api()`/`postApi()` in `js/core.py` no longer let a failure escape: a network-level rejection, a non-JSON/truncated body, and a non-OK status all route through **`_showApiError(path, detail)`** → a fixed bottom `.api-error-bar` naming the failing endpoint with **Retry** (reload) and dismiss buttons. - **Notebook cell output capture (print + returned value)**: A `pre_run_cell` hook installs a `_StdoutTee` on `sys.stdout` that writes to both the real stream (so output still shows in the notebook) and a `StringIO` buffer; `_collect_stdout_capture()` runs at the very top of `_post_run_cell` (before any early return) to read the buffer and restore the original stream, so the tee can never leak — and it only restores if the tee is still the active stream, leaving alone any `sys.stdout` the user's own cell swapped in. `_combine_cell_output(stdout_text, result_repr)` merges the captured stdout with the trailing-expression repr (prints first, then the returned value, mirroring the notebook), capped at `_MAX_CELL_OUTPUT` (4000 chars). - **Knowing where the bytes went (exact per table, apportioned below it)**: The storage report counted metric *rows* and never said what they cost, and nothing anywhere attributed storage to a run — so the two questions that lead to an action ("what kind of data is big" and "which run do I prune or delete") were both unanswerable. `core/storage.py` answers them, and is careful about which numbers it can stand behind. `table_byte_sizes` reads SQLite's **`dbstat`** virtual table, so per-table figures are *exact*: real pages, including each table's indexes and its free space. Nothing below a table has page-level identity, so `metric_storage` (bytes per metric key) and `experiment_storage` (bytes per run) apportion that true total across rows — accurate enough to rank, and labelled **estimated** at every surface rather than presented as measured. dbstat is a compile-time option (`SQLITE_ENABLE_DBSTAT_VTAB`), so an absent one degrades to a bytes-per-row constant instead of a confident zero, and the payload carries an `exact` flag the UI shows. Because it walks every page of the database it is a report-time call only — `exptrack storage` and the Settings panel, never a request hot path. A run's share of a `[ref:sha256:…]` git-diff body is **split across everything referencing it** (sibling runs and session nodes), since charging the full blob to each holder would over-count the database several times over. Surfaced as `exptrack storage [--by-metric] [--top N]`, and a Settings panel that leads with bytes-by-metric and the largest runs (each clickable through to the run) instead of the five row counts it used to show. **`trash_storage(conn)` covers the one place storage accumulates invisibly**: soft delete is the default everywhere, so a trashed run keeps every row *and* its output files (deliberately — Restore has to stay lossless), and nothing anywhere said what that cost. It reports three figures that are reclaimed by three different actions and must not be added into one: `db_bytes` (trashed experiments via `experiment_storage`'s own apportionment, plus trashed session nodes — counting both `session_nodes.deleted_at` **and** nodes under a `sessions.deleted_at` session, since trashing a session does not stamp its nodes), `output_bytes` (files on disk, sized through `output_dirs_owned_by` — the *same* ownership rule the permanent delete uses, so the Trash can never advertise bytes the delete refuses to take because a surviving run also claims that directory), and `local_bytes` (`.exptrack/trash/`, the OS-trash fallback, which nothing but the user removes; `db.local_trash_dir()` is the one definition, shared with `_trash_or_local`, so the report measures the directory files actually land in). Surfaced as a **Trash** section in `exptrack storage` (silent when empty), in the dashboard's storage panel, and as a one-line "Holding …" strip at the top of the Trash view — carried on `/api/trash` rather than the polled badge count, since measuring it walks the database's pages and the trashed runs' output directories
- **Reclaiming metric resolution after the fact (prune) — and reading it without changing it (smoothing)**: `thin_every`/`metric_keep_every` only ever applied at *write* time, so a run recorded at every iteration was stuck at that resolution permanently; `exptrack compact`'s modes (diff/cells/timeline/deep) never touched metrics, which are usually the largest table. `core/storage.prune_metrics` is the way back. **The first point, the last point, and the min and max of every series always survive** — so a pruned chart keeps its endpoints and its extremes, and the final value read off it stays exact. Selection runs **per `(exp_id, key)` series**, because "every Nth point" is only meaningful within one curve — striding across the interleaved rows of five metrics would thin each by a different, arbitrary amount. `preview_metric_prune` and `prune_metrics` share one selection function, so a preview provably describes the delete that follows it, and the byte figure is computed *before* the delete (afterwards the bytes-per-row is apportioned over the survivors and would understate what was freed). Deleted pages go to the database's free list, not back to the filesystem — both the CLI and the dashboard say so and point at `--vacuum` / `exptrack clean --vacuum`. Exposed as `exptrack prune [id...] --max-points N | --keep-every N [--key K] [--dry-run] [-y] [--vacuum]` and `POST /api/prune-metrics`, with the dashboard always running the dry-run first and quoting its real numbers in the confirm — and the confirmed delete removes **exactly the previewed set**: the dry-run stashes its doomed row ids server-side under a `preview_token` and the JS round-trips only the token, since the ids are millions of integers (this is why it can't use the clean-orphans shape, where the client posts back the paths it displayed); the route then passes the cached set as `doomed=`. Memory is bounded two ways because each entry is large: a TTL swept on **both** the stash and the claim path (sweeping only on stash left an abandoned dialog's set resident until the next preview, which may never come) and a hard cap on entries with oldest-first eviction, above 1 so two tabs don't invalidate each other. The stash also carries the dry-run's `table_byte_sizes` result so the confirm doesn't repeat that whole-file page walk — an unknown/expired token refuses rather than re-selecting, since points logged while the dialog was open would make a fresh selection a larger, different delete than the one confirmed. The route also runs `checkpoint_truncate` afterwards, like the delete-permanent routes. Separately and non-destructively, the Charts tab has a **smoothing slider** (`js/charts.js`): a debiased exponential moving average over the plotted points, persisted in localStorage. The debias divisor is load-bearing — without it every curve is dragged toward zero for its first points, so a loss starting at 2.0 appears to start near 0 and *climb*. The unsmoothed series stays visible as a faint ghost line behind the smoothed one, since a smoothed curve alone reads as far less noisy data than was actually recorded; both datasets exist at all times (the ghost merely `hidden` at zero) so moving the slider never changes the dataset count and the charts update **in place**, preserving the live-run refresh contract
- **Exports are summaries, and `--full` is the way back**: A checkpoint-per-epoch run registers thousands of artifacts, which buried the params, metrics and charts on the Overview and made an export unreadable. `core/queries.summarize_artifacts` is the one summariser — it caps the list *and* reports counts by type and by containing directory, so the omitted remainder is described ("4000 files — 3990 model, 10 image; `outputs/ckpts` (3990)") rather than silently dropped. Applied to every **human-readable** surface: markdown export (25), CLI `show` (15), the dashboard's plain-text export (25), each with a `… and N more` line; `--max-artifacts N` overrides, `0` lists all. **JSON used to be exempt from all of this and it was the wrong call**: a run logging every iteration made `metrics_series` tens of thousands of one-line objects and the artifact list thousands more, so the params and the final numbers — the reason anyone opens an export — were buried under raw data that the reader almost never wanted inline. So `get_export_data(conn, id, full=False, artifact_limit=ARTIFACT_LIST_LIMIT)` is a **summary by default for every format, JSON included**: `metrics` carries one `summarize_metric_series` entry per key (`count`/`first`/`last`/`min`/`max` plus the step each extreme sits at — what you'd read off the chart), the artifact list is capped, and `artifacts_summary` (`total`/`listed`/`omitted`/`by_type`/`by_dir`, dirs capped at `SUMMARY_DIR_LIMIT`) states the shape of the rest. **Round-tripping is preserved by an explicit opt-in, not by defaulting to everything**: `full=True` (`exptrack export --full`, `?full=1`, dashboard **Export → JSON (full)**, `/api/bulk-export` body `{"full": true}`) adds the raw `metrics_series` *alongside* the summary and lists every artifact; `artifact_limit=0` uncaps just the list. Truncation is never silent — `omitted` is on the payload and every renderer prints it. **`export_metric_summaries(data)` is the one reader of both shapes** (summary-only, full, or a legacy payload carrying only `metrics_series`), used by the markdown and CSV formatters and mirrored client-side by `_summarizeMetricSeries` in `js/detail.js`, so no consumer re-implements "last value of a series" and none of them break when handed either form. In the dashboard the Overview's Artifacts section **starts collapsed** past 25 with a type summary in the heading, and artifacts **group by containing directory** past 12 with each group foldable — built by `_summarizeArtifacts` in `js/detail.js`, the client-side mirror of the Python helper, shared with the plain-text export (thresholds live beside it as one group of constants). Type classification is `artifactKind(path)`, mirroring `core/queries.artifact_kind`'s vocabulary so the terminal, the export and the dashboard name the same file the same thing; `artifactTypeBadge` renders *that* rather than being the classifier, since counting by type used to mean building badge markup and regex-parsing the CSS class back out of it — which made class names a parsing contract that silently degraded every count to `file` when touched. Grouping switches the older flat 50-row cap *off* rather than stacking with it: running both meant an expanded group could still render nothing, because its rows sat past the flat cutoff
- **Every run snapshots its own source, however it was started**: `capture_script_snapshot` used to be called only from `__main__`, i.e. only under `exptrack run`. A script run as plain `python train.py` building its own `Experiment()` — a fully supported pattern, and the one the **Run adoption** pattern exists to serve — therefore recorded no source at all. The symptom was a contradiction on screen: the "vs previous run" strip reported `code changed`, since that comes from the repository-wide `_run_code_signature` and needs no snapshot, while the Code-changes panel directly beneath it had nothing to diff and said no code was captured. So two runs that had each diverged from the committed file *and from each other* could not be diffed against each other — exactly the run-to-run comparison the panel exists for. `Experiment.__init__` now calls `_maybe_snapshot_script()` whenever the run has a real script file, so the source is captured however the run started; label scripts (`run-start --script pipeline`) and notebooks are skipped, having no file and their own capture paths. **`Experiment._maybe_snapshot_script` is the single entry point** and `Experiment` owns the idempotence flag (`_script_snapshotted`, a class-level default so the `object.__new__` resume path is safe): `__main__` calls that method rather than reaching past it into the capture layer, because `Experiment.resume` bypasses `__init__` and cannot know the path this invocation resolved. Whichever call runs first wins, and the second no longer writes a duplicate `cell_exec` timeline event and a second set of params. The module itself lives in **`core/script_snapshot.py`**, not `capture/` — `core.experiment` calling it on every run made the old `core → capture` import a real, permanent runtime dependency, the same layering inversion moving `dataset.py` into `core/` was meant to end, and a function-local import only hides that from the import graph. Its expensive work is memoized on `(path, mtime, size)` so a param sweep does it once, not once per run
- **Scan-path suggestions come from what the run touched**: the Images and Data Files tabs let the user register directories to scan, and the suggestions were `output_dir` plus its immediate subdirectories — hidden entirely once *one* path had been saved, which is the moment they had proved useful. `read_routes._suggested_scan_paths` draws them, best first, from the run's output dir, the directories its registered **artifacts** were written to, the datasets its **`_dataset_manifest`** fingerprinted (so `--data_dir data/raw` is offered on the Data Files tab without the user typing a path), and finally a bounded walk of the project for directories actually holding matching files. Each suggestion carries the *reason* it was offered, rendered on the chip, so picking one is a decision rather than a guess; already-added paths are filtered out server-side and the rest stay visible. The project walk is capped by depth (`_SCAN_MAX_DEPTH` 3) and total directories (`_SCAN_MAX_DIRS` 400), prunes `.git`/`node_modules`/venv-style trees, and is **cached per project root for `_SCAN_CACHE_TTL` (60 s)** — it runs on a tab open, and up to 400 directory listings is ~10 ms on local disk but seconds on an sshfs/NFS-mounted project, which is precisely the shape of the request-thread stall the **Concurrent request serving** pattern exists to prevent. It would otherwise re-run on every Images *and* Data Files request, including the two a Compare view issues at once and the ones a live run's 5-second refresh re-issues. The cache stores a per-directory extension histogram rather than a filtered count, so Images and Data Files (different extension sets) share one walk
- **Listing a *saved* scan path is bounded, and its boundary check is the real one**: `_collect_scan_files(root, paths, exts)` is the single walk behind both `api_list_logs` and `api_list_images` (they had two copies of it, differing only in the extension set and one `ext` field). Unlike the suggestion walk above it **cannot be cached** — it has to show files the run just wrote — and it is re-issued constantly: a live run's 5-second refresh, the two requests a Compare view opens at once. It used to be an unbounded `os.walk` with a `stat` per file and every result serialized into the response, so a scan path pointing at a checkpoint-per-epoch tree meant thousands of stats and a vast JSON body *per tab open* — seconds of held request thread on an sshfs/NFS project. It is now capped by `_SCAN_MAX_WALK_DIRS` (2000) and `_SCAN_MAX_FILES` (5000), prunes `_SCAN_SKIP_DIRS` (so a path at the project root doesn't spend its budget inside `node_modules`), and sorts `dirnames` in place so a truncated listing is at least the *same* truncated listing next request. **Truncation is stated, never silent** — `truncated` + `max_files` come back on both payloads and `_scanTruncNotice` renders a `.scan-trunc` line in each tab, the same contract the experiment list's `renderTruncNotice` follows. Containment goes through **`config.readable_project_path(rel)`** — the one definition of "a path the dashboard may read on the user's behalf", shared with `_serve_file`. It applies *both* rules: inside the project root (`realpath` on both sides plus a separator boundary — a bare `startswith(root)` accepts a sibling whose name merely begins with the root's, `/home/me/proj` matching `/home/me/proj2`, and resolving no symlinks accepts a link inside the project pointing anywhere on disk) **and** not under `.exptrack/`. The scan routes previously had a weaker copy of only the first rule, so a saved scan path of `.exptrack` enumerated `config.json` and every notebook-history snapshot — both `.json`, both in the Data Files extension set — which the file server has always 403'd. It lives in `config.py` because where a path sits relative to the project, and which subtrees are exptrack's own, is config-layer knowledge, not the HTTP handler's. Guarded by `tests/test_scan_path_bounds.py`
- **Metric thinning (count points, never test the step value)**: Two-layer system for large metric series. Write-time: `thin_every` on `Experiment` or `metric_keep_every` in config, applied by `Experiment._keep_metric_point(key)` — **1 of every N points logged, counted per metric key on the per-instance `_metric_logged` dict, with a key's first point always kept** (count 0). Read-time: min-max bucketing downsamples for chart display (`metric_max_points`, display-only and non-destructive). The gate used to be `step % keep_every == 0`, which silently assumes the caller logs on *every* step: the common `if (i+1) % 5 == 0` cadence logs steps 5, 10, 15 …, so with `keep_every=999` the two are coprime, **no step ever satisfies the test, and the run stores zero points** — a setting reading as "thin this" acting as "discard everything", diagnosable only as an empty chart. Even a compatible factor was wrong (`1000` on a 200-step run kept step 0 alone). Counting points delivers what the setting always claimed, at any cadence, and cannot take a series to zero. Three properties are load-bearing: **(1)** the count is per key, so `log_metrics({loss, acc})` thins both identically while a key logged on only some calls still keeps every Nth of *its own* points — hence `log_metrics` calls the gate per key inside its loop rather than once for the dict; **(2)** a step-less `log_metric(k, v)` is thinned on the same rule (the old gate returned `True` for `step is None` because it had nothing to take a modulo of, so those series ignored the setting outright); **(3)** an unusable config value (`0`, `-3`, `"abc"`, `None`) degrades to keeping everything — a hand-edited config must never be why a run recorded nothing. `_metric_logged` is a class-level `None` (not a shared dict, which every run in the process would mutate) set per instance in `__init__` and in `resume`'s `object.__new__` path, and `_keep_metric_point` re-initializes it defensively. **Dropping data is never silent**: the first drop prints a one-line stderr notice naming the factor (once per run, via `_thin_notice_shown`), and the dashboard field is "Store 1 of every N points" with a `.settings-note` consequence line (`_updateKeepEveryNote`) that appears only above 1 and points at `exptrack prune` as the non-destructive alternative. Guarded by `tests/test_metric_thinning.py`
- **Metric write cost at loop scale (a commit is an fsync)**: metrics are the only thing exptrack writes inside the user's *inner loop* — a 100k-iteration run calls `log_metrics` 100k times — so the per-call commit that is fine everywhere else dominates here. It was ~96% of the write cost: 100k iterations × 5 metrics took **151s**, against 8s for the same inserts committed in batches, i.e. exptrack added two and a half minutes to a run it is supposed to passively observe. `Experiment._commit_metrics` now commits at most once per `metric_commit_interval_ms` (config, default 250; `0` restores commit-per-call), and `log_metric`/`log_metrics` take the connection as `conn = get_db()` rather than `with get_db() as conn:` — **sqlite3's connection context manager commits on exit**, so the `with` form silently defeats both this and `batched_writes()` (which metrics had therefore never actually honored, despite the docstring). Three properties are load-bearing and each has a test. **(1) The window is time-based, not count-based**, because uncommitted rows are invisible to the dashboard's separate connection: a count-based batch would stall a slow run's chart for however long N iterations take, while a time window bounds the lag at the interval regardless of loop speed. **(2) The first write of a run always commits** — `_last_metric_commit` starts at `-inf`, not `now`; starting the window at creation defers the first point until the *second* write, so a run logging once per epoch would show its chart permanently one epoch behind, the exact opposite of the intent. **(3) Everything that can end a run flushes**: `finish` (before anything in it can raise), `fail`/`__exit__` via `finish`, any other logging call (committing the shared connection commits these too), and interpreter shutdown via the module-level `_live_runs` WeakSet + `atexit` hook — so a script that just falls off the end without `finish()` keeps its points. Only `kill -9` loses anything, bounded by the interval. Because `_live_runs` holds weak references, the flush cannot rely on the registry alone: a run GC'd mid-window (function scope, exception unwind) vanishes from it with rows still buffered, and the next `Experiment()`'s `BEGIN IMMEDIATE` then died on "cannot start a transaction within a transaction", destroying those points in its rollback. **`db.flush_pending(conn=None)` is the answer and it asks the connection, not a registry** — `conn.in_transaction` is maintained by sqlite3 and is True exactly when an implicit transaction is open, so it covers *every* writer rather than only the ones that remembered to set a flag. (An earlier version kept a thread-local flag beside it; that was a hand-maintained mirror which went stale against `close_db` — the flag outlived the connection it described — and reported nothing for writers that never touched it.) `_flush_live_runs` ends with a `flush_pending()`, and `close_db()` calls it before closing so a pending window is never silently rolled back. The pending window also leaves an **implicit transaction open on the shared connection**, so `Experiment.__init__` calls `_flush_live_runs()` before its `BEGIN IMMEDIATE` — otherwise creating a second run after a metrics loop dies with `cannot start a transaction within a transaction`. `Experiment.__exit__` guards both its branches with `if not self._finished:` — a script may `finish()` explicitly inside the `with` block, and an unguarded second finish raised (in the exception branch, replacing the user's real exception). A call that thins a point away still ticks the window via **`_tick_commit_window()`**, so a long fully-thinned stretch can't leave an earlier kept point uncommitted indefinitely — and that helper tests the elapsed window against *instance* state before touching the DB layer, because `get_db()` re-derives the path, `mkdir`s the parent and runs a `SELECT 1` liveness probe on every call (~14 µs, ~9x the cost of the whole thinned call): calling it per dropped point put a syscall and a round trip on the one path that must stay nearly free
- **Charts must render faster than the poll that refreshes them**: `get_metrics_series` backs `/api/metrics`, which the detail view **polls every 5 seconds** while a run is live — so its cost is not a page-load nicety, it is a hard budget. It used to `SELECT` every point for the experiment and build a dict per row before handing the list to `_downsample_points`, which discarded ~99% of it: 500k rows (one 100k-iteration run × 5 metrics) took ~6s to produce 2500 chart points, of which under 1.5s was the scan. Each poll then occupied a request thread for longer than the poll interval. The bucketing now runs in SQL (`_bucketed_points`) and only surviving points are built in Python. Two aggregate passes per key — one keeping each bucket's lowest-valued point, one its highest — each relying on SQLite's **bare-columns-with-a-single-min/max** rule to get that point's own `step`/`ts` rather than just its value; that rule is *why it is two queries and not one with both aggregates*, since having both voids the guarantee and the bare columns go arbitrary. Buckets are cut on **`COALESCE(step, rowid)`**, and the result is sorted on that same value: the step for a training loop, insert order for the step-less `log_metric(k, v)` case where every step is NULL — bucketing on step alone collapses such a series into one bucket, and sorting the *output* by `step`/`ts` instead scrambles it, since `ts` resolves only to the second. First and last points get reserved buckets (`-1` and `num_buckets`) so a chart spans the run's true extent and the final value read off it is exact. A key already at or under `max_points` skips bucketing entirely and is returned exactly as stored. The bucket-local value ranking is also what **bounds** the output: filtering on `value = MIN(value) OVER …` would return every row of a flat series

- **Shared code rendering (syntax highlighting + word-level diffs)**: `js/highlight.py` is the single source of truth for rendering Python in the dashboard, used by both the Sessions tab and the experiment detail view. `_highlightPy(line)` is a dependency-free tokenizer (keywords/strings/comments/numbers/decorators/builtins/function-calls; every token HTML-escaped as emitted so it's injection-safe). Token colors are theme-aware `.tok-*` classes defined **unscoped** in `css/code.py`, reading a small, calm `--tok-*` palette centralized in `css/reset.py` so both views (and both themes) stay coordinated. For diffs, `_renderUnifiedDiff(diffText)` (raw `git diff` string) and `_renderCodeChangeParts(value)` (the `; `-joined `_code_change/cellN` summary fragments) both build `{kind:'add'|'del'|'ctx'|'hunk', text}` rows and pass them to `_diffRowsToHtml`, which **pairs a run of consecutive deletions with the immediately-following run of additions and word-diffs each pair** — `_wordDiffPair` tokenizes both lines, runs an O(n·m) token LCS (`_tokenLcs`, guarded to fall back to plain highlighting past 40k token-pairs), and wraps only the changed span in a `.dword-add` / `.dword-del` pill while syntax-highlighting the unchanged runs around it. So an in-place edit like `threshold=0.7` → `0.5` spotlights just the `7`/`5` instead of two near-identical red/green lines. The pill is styled for legibility — a soft tint (`--diff-add-bg`/`--diff-del-bg`) plus a colored underline (`box-shadow: inset 0 -2px 0 var(--diff-*-bar)`, with a strikethrough for deletions) carries the add/remove signal while keeping normal ink rather than whiting out the token, so the changed span stays readable when a long line is expanded (the changed span is plain escaped text — never `.tok-*` — so there's no longer any in-pill token rule). **The word-pill spotlight is gated by similarity** — `_wordDiffPair` computes a Dice ratio (`2·common / (aReal+bReal)` over non-whitespace tokens) and, below 0.5, treats the pair as a rewrite rather than a tweak and falls back to plain per-line highlighting, so big changes don't turn into word-pill confetti. **The whole word-diff layer is user-toggleable** — `_diffRowsToHtml` consults `_wordDiffEnabled()` (localStorage `exptrack-word-diff`, default on) and, when off, never pairs del/add runs so every diff renders as plain line-level add/remove; the toggle lives in Settings → Display (**Highlight word-level diff changes**, wired via `setWordDiff()` in `js/core.py`, which re-renders the open detail view on change). **Green/red are reserved for added/removed**: `--tok-str` (strings) shares the amber `--tok-num` value rather than the success-green, so a string literal never reads as an added line even outside a diff. Diff lines render as `.code-diff > .dl` rows with a background tint + left bar (`--diff-add-bg`/`--diff-del-bar` etc., the same vars the Sessions split-diff uses) and a sign gutter. **Inside a diff, color carries only one meaning — added vs. removed:** `css/code.py` mutes the syntax `.tok-*` colors to plain ink within `.code-diff` (comments → `--text-3`) so a green string literal can't be misread as an "added" line. The red/green tints + sign gutter + word-pills carry all the change semantics; non-diff code surfaces (`.tl-code-preview`, `view source`) keep full syntax highlighting since they have no add/del meaning to collide with. Consumers: `js/detail.py` (Code Changes + Uncommitted-Changes git diff), `js/timeline.py` (`source_diff` previews + `viewCellSource` full source). **`viewCellSource` renders the *full* cell source as a diff when the cell has a parent** — `_lineDiffRows(parent, current)` (a line-level LCS in `js/highlight.py`, capped at 4M line-pairs) turns unchanged lines into `ctx` and changed lines into del/add runs, then `_renderDiffRows` word-diffs them, so expanding an edited cell spotlights the changed token across the whole source (not just the short timeline preview) and honors the word-diff toggle. No parent (or a source too large to diff) falls back to plain highlighted source with the previous version dimmed via `opacity`. **Code diffs carry an old/new line-number gutter** — `_diffRowsToHtml(rows, lineNumbers)` / `_renderDiffRows(rows, lineNumbers)` emit a `.dl-no` gutter (`.code-diff-numbered`) tracking old- and new-file line counters; `_renderUnifiedDiff` (git diff) seeds them from the `@@ -a,b +c,d @@` headers and the `viewCellSource` source diff starts at 1. Short fragment renders (the timeline `source_diff` preview, `_renderCodeChangeParts`) call `_renderDiffRows(rows)` with no line numbers since fragments have no real positions. Nested-box doubling is avoided with `.code-changes .code-diff` / `.diff-view:has(.code-diff)` overrides that strip the inner frame.
- **Session Trees (opt-in exploratory tree tracking)**: A second tracking mode for notebooks that records the *shape* of exploration (checkpoints + branches + scratch cells) as a tree, layered on top of standard `%load_ext exptrack` capture. Activated only by `%exptrack session start "name"` — without it every other session magic is a silent no-op, so existing capture is unaffected. `%exptrack checkpoint "label"` writes a node and snapshots a per-checkpoint git diff (`git diff` from the previous checkpoint's commit, falling back to `git diff HEAD`). `%exptrack branch "label"` adds a child of the most recent checkpoint and tags it as the current node so subsequent commits/checkpoints flow under it. **Every magic is idempotent under a Run-All**, which is the workflow the whole feature exists for: re-running the notebook re-executes the magics while the current node is still wherever the last pass ended, so `checkpoint(label)` resolves a label already present as a child *or an ancestor* of the current node (`_find_ancestor_checkpoint`) and returns to it. Without the ancestor case the checkpoint was created *under the previous pass's branch*, and the next branch under that — every Run-All grew a fresh duplicate spine, with its own cells and its own diff blob. Three sibling paths had the same hole and each grew the tree per pass. **`_find_ancestor_checkpoint` starts its walk at the current node itself**, not its parent, so re-declaring the checkpoint you are standing on resolves through the normal path and lands on `checkpoint()`'s single `_switch_to_node`. That case used to be structurally invisible to the resolver and was covered by a special-cased early return which returned the id *without* re-arming the cursors (so every cell of the node was appended again per pass) and without updating `_last_checkpoint_id`; fixing the resolver deleted the special case. **`start()` on an already-active session returns to the session root** (via `_session_root_id`), because re-executing the notebook's *first* magic is the strongest "replaying from the top" signal there is; doing nothing left the pre-checkpoint cells (imports, data loading) recorded onto whatever node the last pass ended on, appending a copy per pass while the root's own copies sat untouched. `session_hooks._session_start` has to cooperate — it used to `return` on an active session, so `start()` was never reached from a real notebook; Content matching needs no `node_type` filter and no `LIKE` escaping of user text, and it only runs on the rare collision path. `%%scratch` is a cell magic that executes the cell body but its source begins with `%%scratch`, so the `_post_run_cell` hook detects it via `is_scratch_cell()` and skips all logging — no DB row is ever inserted, not insert-then-delete. **`%%setup` is a third tier between a normal cell and `%%scratch`: recorded-but-secondary prep code.** `_post_run_cell` detects it via `is_setup_cell()` and routes it through `_record_setup_cell()` instead of the normal path: `SessionManager.record_setup_cell()` appends source+output to the node's **own** byte-budgeted columns (`setup_source`/`setup_outputs`, `_NODE_SETUP_MAX_BYTES`, so a big prep block can't evict real cells) — through the **same replay recognition tracked cells get**, against the setup store's own cursor pair (`_setup_replay_idx`/`_last_setup_idx`, armed by `_switch_to_node` alongside the cell pair). - **A live run's detail view keeps the view state you set**: while an experiment is `running`, `_autoRefreshPoll` (5 s, `js/detail.py`) re-renders the detail panel as metrics arrive — which means every piece of view state the user set has to survive a re-render, or watching a training run is impossible. **The active tab is the load-bearing one**: `refreshDetail` rebuilds the panel from one template string with `class="tab active"` hardcoded on Overview, so each poll silently threw the user back to Overview — the numbers updated, but Charts could not be *read* on a run that was still going, which is the one time you most want it. It's gated on `!isInitialEntry` — opening a run should start at the top; only an in-place refresh keeps the offset. A null `/api/metrics` response returns early — `api()` already surfaces the failure, and keeping the last good chart beats blanking the tab on one bad poll out of a run's hundreds. **The poll itself never overlaps**: `_autoRefreshInFlight` is held across the whole fetch-and-render cycle (the tab reloads are `await`ed for exactly this reason) and a tick that fires while the previous one is still working returns immediately. The interval is 5 s and a poll can exceed it — a large run, a network filesystem, a tunnel — so without the guard the requests stack and each re-renders the panel underneath the last. Two more things the poll must get right, both of which were wrong: `api()` can return `null`, and reading `.error` off it threw *into the poll's own `catch`*, so a failed request was indistinguishable from a healthy one (`if (!exp || exp.error) return;`, and `exp.metrics || []`); and the run can be closed or switched away from *while the request is in flight*, so `currentDetailId` is re-checked after the await before anything is redrawn

- **A delete that reclaims nothing visible is indistinguishable from a delete that failed**: `delete_experiment` has always removed every child row, but SQLite moves the freed pages to the database's **free list** rather than shrinking the file, so `ls` reports the same size afterwards and the storage report's per-table breakdown silently stops adding up to the file size (delete a run holding 120k metric points and the tables account for 8 MB of a 12 MB file, with nothing naming the other 4 MB). Three things close that gap and they are all *reporting*, not new deleting. **`core/storage.free_space(conn)`** is the measurement — `freelist_count × page_size`, two pragmas and no page walk, so it is cheap enough to call either side of a delete. **Every delete says what it freed**: `cli/mutate_cmds._print_reclaimed(conn, before)` (shared by `rm`, `clean`, `clean --older-than`, gated at `_RECLAIM_NOTE_MIN_BYTES` so a couple of pages isn't announced) and the dashboard's `freed_bytes` on both delete-permanent responses, rendered by `_reportFreedSpace` — each naming `clean --vacuum` as the one operation that hands the space back. **The storage report shows it as part of the file**, as an `of which free` line under the database size and a matching row in the Settings panel, so the breakdown reconciles. **The WAL is the other half**: a delete pushes every rewritten page through it, and the dashboard's per-request checkpoint is deliberately PASSIVE (it must never wait on a live training run), which drains the WAL but leaves the file at its high-water mark — so a dashboard delete left a same-sized database *and* a new multi-MB `-wal` beside it. **`db.checkpoint_truncate(conn, timeout_ms=250)`** is the bounded escape hatch used only by the explicitly-destructive routes: it lowers `busy_timeout` for the duration and restores it, so TRUNCATE's busy handler can wait at most that long and a blocked checkpoint returns `False` instead of stalling the request (the next PASSIVE checkpoint or process exit drains it anyway). Never call it from a hot path. The CLI needed nothing here — its process-exit `close_db` already truncates. **Orphans are the same failure one layer down**, and `core/storage.orphan_storage(conn)` is their report: rows pointing at an experiment that no longer exists are invisible in every list (nothing joins to a missing run) while still occupying the file. exptrack does not create them — `delete_experiment` removes the children first and `PRAGMA foreign_keys=ON` would refuse otherwise — but a database written by an older version, hand-edited, or left by a process killed mid-delete can carry them. `count_orphans` always found them and the CLI-exit `close_db(sweep=True)` always swept them; what was missing was any surface *saying so*, and the storage report's warning was gated on `exp_count == 0`, so a project with 5 runs and 20k orphaned metric rows reported perfect health. It now reports the count and apportioned bytes per table in **Database Health**, and `/api/storage-info` carries the same payload for an **Orphaned rows** section with a Clean button — the dashboard needs that more than the CLI does, since its per-request `close_db(sweep=False)` deliberately never sweeps (the anti-join counts are far too expensive per request), so a UI-only user would otherwise carry a legacy database's orphans forever
- **Reclaiming storage without losing data (refcounted blobs · one reset list · files are opt-in)**: Cleanup has one rule — *DB rows are bookkeeping and can be swept freely; files and content-addressed blobs are user data and need a reference check or a confirmation.* Three mechanisms in `core/db.py`, each with exactly one implementation so the CLI and dashboard can't drift. **(1) The two content-addressed blob tables are reference-counted, not exp_id-keyed.** `code_snapshots` (full script source) and `git_diffs` (whole working-tree diff body) are shared across runs by content hash, so neither can be deleted with a `WHERE exp_id=?`. `_GIT_DIFFS_ORPHAN_COND` is the pure-SQL condition for `git_diffs` (a blob is dead when no `experiments.git_diff` *or* `session_nodes.git_diff` holds its `[ref:sha256:…]` marker — session nodes matter, they reference diffs too) and `_unreferenced_snapshots` handles `code_snapshots` in Python because the reference lives inside a JSON param value SQL can't decode; `_sweep_blobs(conn)` runs both. **They are deliberately *not* in `_ORPHAN_SPECS`**: both are expensive (the SQL condition full-scans experiments ∪ session_nodes — no index serves a `LIKE` prefix across two tables — and the snapshot check reads every `_code_snapshot` param into Python) and neither can go stale without a delete, so `close_db`'s per-command-exit sweep passes `blobs=False` and pays nothing for a guaranteed-zero result. `sweep_orphans(conn, blobs=True)` (the default, used by `exptrack clean` and the dashboard) does the full set, and `count_orphans(conn)` counts the same specs without deleting so a dry-run/confirm can never describe a different set than the sweep removes. `_referenced_snapshot_hashes` scans the raw `_code_snapshot` text for hash-shaped tokens rather than replicating all three encodings that param has had (native list, double-encoded legacy, pipeline pre-encoded string): **over-retention is harmless, under-retention destroys a run's only copy of its source**, so the scan is deliberately generous. `delete_experiment` calls `_sweep_blobs` *after* deleting the run's `params` (before it, the run's own reference is still visible); pass `reclaim_blobs=False` when deleting in a loop and sweep once after — every bulk caller does, since per-run reclaim made a 200-run delete 200 full scans, and the reset paths skip it entirely because `reset_all_tables` truncates both tables wholesale. A **trashed** run still occupies `experiments`, so its blobs survive soft delete and Restore is lossless — only the permanent path drops the last reference. Before this, "permanently delete" left the run's script source and full diff (routinely including an accidentally-staged `.env`) readable forever, and `sweep_orphans` reported a clean DB while both tables grew monotonically. **(2) A reset clears one shared list.** `_RESET_TABLES` / `reset_all_tables(conn)` is used by both `exptrack clean --reset` and `api_reset_db`; the two previously kept separate hardcoded lists that each omitted `code_snapshots` + `sessions` + `session_nodes`, so "delete everything, cannot be undone" stranded every script source and every notebook cell body. Order is FK-safe (`session_nodes` before `sessions`, since `PRAGMA foreign_keys=ON`). **(3) Orphaned output paths are reported, then trashed — never `rmtree`d.** `find_orphan_output_paths` only *identifies* candidates under `outputs/` (a dir claimed by an experiment's `output_dir` or its name; a loose file claimed by living inside a claimed dir — trashed experiments still occupy the table, so their outputs never qualify); `describe_orphan_output_paths` adds file count + bytes for the confirm dialog; `trash_orphan_output_paths` moves them via `_trash_or_local`. Both accept an already-computed `paths` list, and callers discover once and pass it along — annotating walks every orphan tree with `rglob`+`stat` (routinely a checkpoint tree), so the delete request skips it entirely rather than computing an annotation it discards. The CLI's `--orphans` preview annotates through the same helper, so its byte total can't drift from the dashboard's dialog for the same path set. `api_clean_db(conn, body)` sweeps rows on every call but returns `orphan_files` and touches nothing on disk unless `body["delete_files"]` is set, and `settingsCleanDb()` posts twice: once to get the list, then — after an itemised `confirm()` — again with the flag. **The second post carries the paths the first one displayed** (`body["paths"]`), and the route trashes only the intersection of that list with the paths still orphaned *now*, reporting the remainder as `skipped_unconfirmed`. The confirm is built from a previous request, so re-discovering orphans at delete time meant anything written under `outputs/` in between — a run started while the dialog was open, a file dropped in by hand — was moved to the Trash having never appeared in the confirm. Omitting `paths` keeps the old discover-and-act behaviour for older callers. **(4) A permanent delete only removes output directories the run actually owns.** `output_dirs_owned_by(conn, exp_id, name, output_dir)` is the shared rule, used by both `_delete_experiment_files` and `get_delete_preview` so the dialog can never size a directory the delete leaves alone (or the reverse) — and the preview sizes **every** owned candidate, not just the first that exists, since the delete trashes all of them (a diverged recorded `output_dir` + name-derived `outputs/<name>` used to under-state the confirm). There are two candidates — the recorded `output_dir` and the name-derived `outputs/<name>` — and the second is only ours when no *other* experiment row claims it. **What "claims" means is defined once, in `claimed_output_paths(conn, exclude_id=None)`, and `find_orphan_output_paths` uses the same function**: the two must never disagree, or a directory the delete protects because another run owns it gets reported as debris and trashed by the very next Clean click — the guarantee undone one button over. Comparison is lexical (`_norm_path`) on both sides rather than `resolve()`; consistency between the two consumers is the property that matters, and resolving would put a syscall on every row of a scan that runs per delete. A precomputed set is deliberately *not* threaded through the bulk-delete loops the way `reclaim_blobs=False` is: hoisting it would change the answer in exactly the collision case this exists for — bulk-deleting two runs that share a name would see each claimed by the other and leave the directory behind. **Names are not unique**: `api_rename` accepts any name and `rename_output_folder` deliberately refuses to move a folder onto an existing one, so two runs can carry the same name while only one owns the directory — trashing the name-derived path unconditionally destroyed the *other* run's outputs, with nothing in the confirm saying whose files were being counted. A **trashed** run still counts as a claimant, for the same reason its blobs survive soft delete: Restore has to stay lossless. This matters because **"orphan" is a heuristic that includes files the user explicitly kept**: the permanent-delete modal defaults `delete_files` to *false*, so deleting a run while keeping its checkpoints made those checkpoints unclaimed, and the old unconfirmed `shutil.rmtree` destroyed them on the next Clean click (along with anything hand-placed in `outputs/`). Every file-removal path in the codebase now ends at `_trash_or_local`; `rmtree`/`unlink` appear nowhere outside empty-dir `rmdir` cleanup
- **Per-branch metric attribution (tag at write time, don't infer it later)**: A notebook session funnels every `metric()` call into one auto-created run, so "which branch produced this number?" has to be recorded, not reconstructed. `Experiment.log_metric`/`log_metrics` stamp each row with `_active_session_node()` — the live `SessionManager._current_node_id`, or NULL outside a session — and `materialize_experiment` copies the rows naming the node it's graduating. This replaced a timestamp heuristic: `_copy_node_window_metrics` used to take every metric whose `ts` fell in `[node.created_at, next node's created_at)`, which is wrong the moment you **revisit** a branch — `branch("existing label")` *switches* to a node without creating one, so the window never moves and the new metric is credited to whichever node happens to be newest. Promote the 0.7 branch and you could get the 0.5 branch's accuracy, silently, in exactly the compare-branches workflow the feature exists for. The window survives only as a **fallback for rows written before the column existed**, and it is restricted to `session_node_id IS NULL` rows — letting it claim a *tagged* metric would re-introduce the same theft it was replaced for. The tag is layered so it can't break metric logging: the import of the (optional) session subsystem is function-local and any failure degrades to NULL. Migration is `_migrate_metrics` (nullable `TEXT` + `idx_metrics_session_node`); **the index is created there, not in `_create_base_schema`** — the base script runs first, so indexing the column there would fail on every pre-existing DB, and one failed statement aborts the whole script, i.e. every install breaks on upgrade
- **A trashed thing that's still reachable must say it's trashed**: soft-delete hides a row from the *live lists*, but not from every path that can reach it — so any surface that can still land on a trashed row has to label it, or the user sees something the rest of the UI denies exists. Concretely for sessions: `build_tree` deliberately does **not** filter `sessions.deleted_at` (inspecting a session before restoring it is legitimate, and an experiment promoted out of a session keeps a `session_origin` back-link that opens it directly), so the payload carries `session.deleted`, `_session_origin` carries `session_deleted`, and `list_all_trashed_nodes` / `_trashed_node_groups` carry `session_deleted` per node group. The dashboard renders each as an **in Trash** tag (`.session-trashed-tag` on the session header, `.so-trashed` on the back-link banner) and swaps the live-only header actions (Finalize / End session) for **↺ Restore session** — finalizing or ending a session the sessions list doesn't show is a mutation with no visible subject. The unified Trash marks a node group whose session is itself trashed (`.trash-session-note`) with a link to restore the session, because restoring one of those nodes alone changes nothing the user can see. `restoreSession(id)` is shared by the Trash view and the session header, so it only refreshes the views actually mounted
- **Deleted files stay restorable (OS Trash contract)**: `_trash_or_local` is the only way exptrack removes a file — OS Trash first, `<project>/.exptrack/trash/` as fallback, and the file left in place with a warning if both fail. On macOS it goes through Finder via `osascript`; on Linux it implements the XDG spec directly, and **the `.trashinfo` record is created before the file is moved**, with `O_CREAT|O_EXCL` (mode 0600, since it stores an absolute path). Both halves of that matter: a file in `Trash/files` with no matching record is a blob no file manager will restore (which is what a post-move write failure produced), and the exclusive create makes the destination-name reservation atomic so two concurrent trashes can't collide; if the move then fails, the record is unlinked so it never points at nothing. Windows and other platforms have no stdlib OS-trash path and fall through to the local fallback
- **Typed request bodies + a real error boundary (a route bug is a status code, not a dropped socket)**: every mutation endpoint was written against the dashboard's own JS, which sends form fields as strings, so all 46 body reads did `body.get("value", "").strip()` directly. Any *other* client sending correct JSON types — `{"value": 0.8}` rather than `{"value": "0.8"}` — hit `.strip()` on a float and raised `AttributeError`. Two things then went wrong: the endpoint failed for well-formed input, and the exception escaped `do_POST`, so `BaseHTTPRequestHandler` closed the connection **with no response written at all** — the caller saw a bare disconnect, which neither the dashboard's `_showApiError` bar nor `curl` can report as anything useful. Both halves are fixed. `write_routes/_shared.py:body_str(body, key, default)` is now the only way a body field is read as a string: identical behaviour for strings, coerces a number/bool, and maps JSON `null` to the default (a `null` means "absent", not the literal `"None"`). **`test_no_route_strips_a_raw_body_value` enforces this by scanning the package sources** — the first sweep pattern-matched `body.get(k, "").strip()` and missed nine sites of `(body.get(k) or "").strip()`, which fails identically, so the rule is checked rather than remembered. And the error boundary lives in **`handle_one_request`**, the one point every request passes through, rather than being wired per verb — a `do_HEAD`/`do_PUT` added later would otherwise silently revert to the old failure mode. It prints the traceback to the console the user launched `exptrack ui` from and returns a **500**; the `_responded` flag (set in `end_headers`, the choke point every response passes) keeps it from trying to send a second response once a body is already going out. New endpoints should use `body_str` rather than `.strip()`ing a raw body value
- **JSON we emit must be JSON anyone can parse (non-finite floats)**: `json.dumps` renders `inf`/`-inf` as the bare tokens `Infinity`/`-Infinity`. Python's own `json.loads` reads them back — a documented non-standard extension — but `JSON.parse` rejects them, and it rejects the **whole document**, not the offending value. So one non-finite metric on a run made *every* response mentioning it unreadable in the browser: `/api/experiment/<id>` failed to parse, so the detail panel rendered its `!exp` branch — **"Experiment not found"** for a run sitting in the list two inches away — while `/api/metrics/<id>` failed alongside it and surfaced as a bare fetch error in the `_showApiError` bar. Nothing server-side noticed for the same reason it was possible: `json.loads` round-trips exactly what `json.dumps` wrote, so a test asserting the payload parses proves nothing about the browser. **`core/utils.json_dumps(data, **kw)` is the only serializer for anything a non-Python consumer will read** — `DashboardHandler._json` for every API response, and the CLI's `--format json` export paths, which were writing the same token into files no other tool could load. It forces `allow_nan=False` and, on the resulting `ValueError`, walks the payload once replacing non-finite floats with `None` and re-dumps: the clean path pays only the check the C encoder already performs (measured: no change on a 4000-point payload), and the walk runs solely for a payload that tripped it. `null` is the right rendering — every consumer already types a metric value as a number, so a chart gap or a blank cell is the honest display of a measurement that isn't one, and the run's other points come back intact. The walk is cycle-guarded so a circular payload still raises the readable `ValueError` rather than exhausting the stack in the retry. **This is a read-side guarantee on purpose**: `Experiment.log_metric`/`log_metrics` do refuse a non-finite value, but that guard postdates a lot of stored data and the other ten `INSERT INTO metrics` paths (pipeline CLI, dashboard manual metric, materialize) never had one — so the encoder, not the writer, has to be the thing that cannot be broken by a row that already exists. (SQLite coerces `NaN` to `NULL` on write but stores `±inf` faithfully, so inf is the case that actually reaches the encoder.) `tests/test_dashboard_headers.py` asserts it over a real socket with a `parse_constant` hook that makes `json.loads` as strict as `JSON.parse`
- **Response hardening (the dashboard serves user-supplied files)**: every response carries `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, plus a Content-Security-Policy, all attached in `DashboardHandler.end_headers` rather than `_send_bytes` — `send_error` renders HTML too and never goes through `_send_bytes`, so hooking the shared exit is what makes the coverage total. `no-referrer` is not boilerplate here: `fileUrl()` puts the auth token in the query string (`?token=…`), so without it every outbound link leaks the token in the `Referer` header. There are three policies. **`_CSP_HTML`** (the shell) blocks external origins, framing, and `<base>`/`<object>`/`<form>` hijacking, but deliberately keeps `script-src 'unsafe-inline'` — the UI is built on inline `on*` handlers throughout (see the `escJsAttr` rule below), so this is a containment layer, *not* an XSS backstop; don't mistake its presence for one. **`_CSP_FILE`** (`/api/file/`) is the load-bearing one: it sandboxes the response. `.svg` is in `IMAGE_EXTS`, so SVG artifacts render in the Images tab with thumbnails linking to the full file — and an SVG is a live document, not a picture. Served as `image/svg+xml` from the dashboard's own origin, a hostile `.svg` (a cloned repo, a shared dataset, a plotting library fed attacker-controlled labels) executed script with the token sitting in `location.search`. `sandbox` with no `allow-scripts`/`allow-same-origin` disables scripting *and* drops the document into an opaque origin, so it can neither run nor read the dashboard's storage; `style-src 'unsafe-inline'` keeps inline `<style>` in matplotlib SVG output working. **`_CSP_STRICT`** (`default-src 'none'`) is the default for everything else — JSON, bundles, error pages — none of which is rendered as a document. The policy is a parameter of `end_headers(csp=_CSP_STRICT)` rather than handler state, so it cannot leak from one response to the next and a caller that forgets to choose (including `send_error`'s own no-arg call) fails closed. `tests/test_dashboard_headers.py` asserts all of this over a real socket, because the older handler tests stub `end_headers` out entirely and would never see it
- **Serving a user file must not cost the size of that file (stream, and window the text)**: `/api/file/` serves whatever the run wrote — and `.log`/`.txt`/`.out`/`.err`/`.csv`/`.tsv`/`.json`/`.jsonl` are all served types, so a tee'd training stdout log or a per-step metrics CSV routinely runs to hundreds of MB. It used to `f.read()` the whole file into the request thread and hand the bytes to `_send_bytes`, while `viewLogFile` fetched all of it as text and walked it character by character — for a window it then threw away, since the viewers render at most the **last 500 lines** of a log or the **first 200 rows** of a table. Two changes, and the split between them is the point. **`_send_stream(fh, length, …)`** writes any body in `_STREAM_CHUNK` (64 KB) pieces, so server memory is bounded no matter how big the file is; an image can't be windowed and doesn't need to be, it just needs to not be resident. **`_read_bounded_text`** serves a text file over `_TEXT_PREVIEW_MAX_BYTES` (4 MB) as a window — the **tail** for `_TAIL_EXTS` (a log's interesting end is the last one, and it matches what the viewer renders) and the **head** for `_HEAD_EXTS` (a CSV's header row is line 1; a tail window would lose the column names). The window is trimmed to a line boundary in both directions, which also avoids slicing mid-UTF-8-sequence into a replacement character. Truncation is **stated, never silent**: `X-Exptrack-Truncated: head|tail` + `X-Exptrack-Total-Bytes` come back on the response, `_truncationNote(resp)` renders them as a banner in all three viewer branches, and the row/line counts switch to "N rows loaded" / "N lines loaded" so a partial count is never read as the file's length. `_send_bytes` and `_send_stream` share `_send_head` so the header tail (status, Content-Type, Content-Length, Cache-Control, security headers, CSP) stays one implementation
- **Keep-alive (HTTP/1.1) and the undrained-body hazard**: `DashboardHandler.protocol_version = "HTTP/1.1"`. The stdlib default is HTTP/1.0 — a fresh TCP connection per request — which is invisible on localhost and is a full setup round trip per request through an `ssh -L` tunnel or VS Code port forwarding, paid ~8 times on page load and again every 5s by the detail poll. Two things make it safe and both must stay true. **(1) Every response carries an accurate `Content-Length`**: `_send_head` sets it for all `_send_bytes`/`_send_stream` responses, the stdlib's `send_error` sets its own, and `_send_stream` sets `close_connection` if the file shrank mid-send and it could not deliver the length it promised (under keep-alive the client would otherwise read the *next* response as the missing tail). `_server_error` does the same when it fires after a body has started. **(2) A response written without draining the request body must end the connection**: the 413 over-large-body guard deliberately does not read the body (that's the point of the guard), and the Host/auth rejections answer before reading it — all three go through `send_error`, which emits `Connection: close`, so a reused connection can never parse a leftover body as the next request line. A new early-return path in `do_POST` that answers without consuming `Content-Length` bytes must use `send_error` (or set `close_connection`) for the same reason. Guarded by `tests/test_dashboard_concurrency.py` over a real socket — two requests down one connection, and the 413 case asserted to close
- **Concurrent request serving (a quiet connection must not stall the server)**: the dashboard runs on `app.DashboardServer`, a `ThreadingHTTPServer` subclass — threading here is a correctness requirement, not a performance tweak. The stdlib `HTTPServer` accepts one connection and then blocks in `readline()` until *that* client sends a request line, so a socket that is merely open stalls every other request for as long as it stays quiet and forever if it never sends. On localhost that window is invisible (the browser connects and writes in the same instant), which is why this survived from the initial release; through a remote tunnel it is the normal case — ssh `-L`, VS Code port forwarding and cloudflared all pool and pre-open TCP connections to the forwarded port and relay bytes a round-trip later. One idle pooled socket deadlocked the whole dashboard, and because nothing was ever written back the browser reported a bare `NetworkError` (`js/core.js:_request`'s catch → the `_showApiError` bar) rather than any status code — naming whichever fetch was still pending, usually `/api/experiments?limit=1000&offset=0` as the slowest of the ~8 the boot burst (`js/init.js:_bootDashboard`) fires at once. Three settings carry it and each is guarded by `tests/test_dashboard_concurrency.py` (run against a real socket — the failure is in the accept loop, which the stubbed-handler suites never exercise): `daemon_threads` (Ctrl+C stays immediate), `request_queue_size` = 64 (the stdlib default of 5 is below one page load), and `DashboardHandler.timeout` = 30s so a pre-opened socket that never sends is reaped instead of parking a thread for the life of the process. Threading is safe for the DB because `core/db.get_db()` caches on a `threading.local`, so each request thread gets its own SQLite connection (WAL + `busy_timeout=5000` handle the concurrency) — but that also means a thread-per-connection server would leak one open connection per request, so `process_request_thread` calls `close_db(sweep=False, checkpoint=False)` in a `finally` (`sweep=False` because the orphan scan is anti-join COUNTs over params/metrics/timeline, far too expensive per request; the CLI-exit close and `exptrack clean` still sweep). **`checkpoint=False` is the other half of a rule that applies to every WAL checkpoint on a request path: never one that can wait on the user's training loop.** `wal_checkpoint(TRUNCATE)` (and `RESTART`) invoke SQLite's busy handler, so they block on any connection holding a write transaction — which is exactly what a run does between metric commits (`metric_commit_interval_ms`). Measured against a modest writer loop a single TRUNCATE blocked for 0.63 s, with the 5 s `busy_timeout` as the ceiling. The dashboard used to run one before every GET dispatch, one after every POST, *and* one in the per-request `close_db` — up to two blocking truncates per request, on a UI that fires ~8 requests at boot and polls the detail view every 5 s, which is the same "the dashboard hangs through a tunnel" symptom the threading fix above addresses. Now: **reads never checkpoint** (a GET appends nothing to the WAL, so there was nothing to reclaim — it was pure latency), `DashboardHandler._wal_checkpoint` uses **PASSIVE** (does what it can get for free, returns immediately if a writer is active), and the WAL is only truncated to zero by `exptrack clean` and the process-exit `close_db`. `tests/test_dashboard_concurrency.py` guards all three — including a read issued while a writer holds `BEGIN IMMEDIATE`, which must return in well under the busy timeout. **Opening those per-thread connections is itself a race, and `busy_timeout` does not cover it**: changing `journal_mode` needs a brief exclusive lock that SQLite acquires *without* running the busy handler, so neither `sqlite3.connect(timeout=…)` nor `PRAGMA busy_timeout` applies — a boot burst against a database still in its default rollback journal (a fresh project, a test's `tmp_project`) raised `database is locked` straight out of `PRAGMA journal_mode=WAL` in whichever thread lost. `get_db` therefore sets `busy_timeout` **first** (it takes no lock, and every later statement wants it), then does the WAL switch + `_ensure_schema` under a module-level `_open_lock` so in-process threads can't fight, and performs the switch via **`_set_wal_mode(conn)`**, which retries with a short backoff on a lock/busy error *or* on the pragma reporting back a mode other than `wal` (a contended switch can return the old mode instead of raising) — and, having exhausted the retries, degrades to the existing journal mode rather than raising into the request, since a non-WAL connection still works. Only the switch is retried; an unrelated `OperationalError` propagates. The steady-state path does nothing under `_open_lock` (matching schema stamp → no migration), so it isn't a throughput bottleneck. Guarded by `tests/test_db.py` — a repeated 8-thread first-open burst over fresh database files, plus deterministic retry/degrade/re-raise unit tests, since the thread race only reproduces intermittently
- **Table-driven GET dispatch (ordering hazards become data, not control flow)**: `do_GET` matches `_GET_EXACT` (a dict, path → handler) before `_GET_PREFIXED` (a tuple of `(prefix, suffix, handler)`), with `/api/file/` handled separately as the one GET that serves bytes rather than JSON. The split is the point: a dict entry cannot be shadowed by a sibling, so every route whose full path is known needs no ordering thought at all. **`_match_prefixed_get` then runs two passes over the prefixed table — every suffixed entry before any bare-prefix one — so its order carries no meaning either.** In the previous 47-branch if/elif chain that hazard was invisible and silent — `/api/experiment/<id>/delete-preview` worked only because it was written above the generic `/api/experiment/<id>` branch, and reversing them doesn't error, it resolves the request to the generic handler with `"delete-preview"` as the experiment id (two comments in the old code warned about exactly this). Handlers are uniform `(conn, qs, path)` callables; ids come from `_seg(path, 3)` or `_last(path)` — **`/api/logs/` and `/api/images/` deliberately use segment 3** rather than the last segment, so a trailing extra segment is ignored instead of being taken as the id. `tests/test_dashboard_routing.py` is a characterization suite written against the pre-refactor chain (so the tables are provably equivalent) plus two structural guards: one reverses `_GET_PREFIXED` and asserts dispatch is unchanged (a regression to first-match-wins fails even if the committed order happens to work), the other fails if the two tables ever overlap
- **Secrets stay out of the committable config**: `.exptrack/config.json` is documented as safe to commit and is deliberately left out of the generated `.gitignore` — so it must never hold a credential. The dashboard auth token lives in `.exptrack/dashboard_token` instead — `config.py` owns both the path (`token_file_path()`) and the write (`write_token()`, mode 600), since where a file sits under `.exptrack/` and which paths are gitignored is config-layer knowledge, not the HTTP handler's. **`write_token` calls `ensure_gitignore_rules()` first**, so the ignore rule is a *precondition* of writing the secret rather than a side effect of `init` — a project initialized before the token moved out of `config.json` would otherwise have had no rule for it, and the CLI would print "gitignored" for a file that wasn't. `GITIGNORE_RULES` / `ensure_gitignore_rules()` are the single additive rule list, shared with `init`. `_get_auth_token()` resolves env var → token file → legacy `config.json` key → in-process session token; the legacy key is still honored so existing setups keep working, and `app._warn_if_token_in_config()` flags it once per start with the command to move it. `config.init` also gitignores `.exptrack/trash/` (the local OS-Trash fallback, which holds deleted artifacts and checkpoints). When adding a new setting, ask whether it's a secret before putting it in `config.json`
- **Soft-delete (Trash) with explicit permanent path**: `experiments.deleted_at` (nullable ISO timestamp) marks a row as trashed. The dashboard's `Delete` button (per-experiment and bulk) routes through a confirm modal that defaults to **Move to Trash** — `trash_experiment(conn, id)` only sets `deleted_at` and never touches disk; `restore_experiment(conn, id)` clears it. The modal's **Permanently delete…** tab calls `delete_experiment(conn, id, delete_files=...)`; the bound checkbox "Also move files to system Trash" defaults to OFF, so file removal only runs when the user explicitly opts in. **File removal goes to the OS Trash, not `rm -rf`** — `_send_to_os_trash(path)` uses `osascript` → Finder on macOS, the XDG trash spec (`~/.local/share/Trash/{files,info}`) on Linux; if the OS-trash call fails or the platform isn't supported, `_trash_or_local` falls back to `<project>/.exptrack/trash/<timestamp>__<name>/`. Destructive `unlink`/`rmtree` is never used as a final fallback — if both OS-trash and local-fallback fail, the file is left in place with a stderr warning. `delete_experiment` returns a `{os_trash, local_trash, missing, failed}` count dict, which `api_delete_permanent` and `api_bulk_delete_permanent` surface as `file_stats` in their responses. `list_experiments`, `get_stats` (every count, plus a new `trashed` counter), `get_all_tags`, `get_all_studies`, `get_studies`, and unique-branches stats all filter `WHERE deleted_at IS NULL` by default; `list_experiments(include_trashed=True)` opts back in. Single-experiment lookups (`find_experiment`, `get_experiment_detail`) are deliberately unfiltered so the Trash view can still load detail by id. The Trash view (Settings → Database → 🗑 Open Trash, adds `body.trash-active`) lists trashed experiments with **Restore** / **Permanently delete…** actions plus bulk Restore / Permanent. Endpoints: `POST /api/experiment/<id>/{delete,restore,delete-permanent}` (delete = soft, delete-permanent body `{delete_files}`), `POST /api/{bulk-delete,bulk-restore,bulk-delete-permanent,bulk-delete-preview}`, `GET /api/trash`, `GET /api/experiment/<id>/delete-preview` (returns metric/param/timeline/artifact counts + output_dir size for the modal). Schema migration adds `deleted_at` + `idx_exp_deleted_at` via idempotent `ALTER TABLE` in `_ensure_schema`

## Database Schema

SQLite WAL mode with 10 tables:

- **`experiments`** — run metadata (id, name, status, created_at, duration_s, git_branch, git_commit, git_diff, hostname, python_ver, notes, tags, output_dir, **command** — the real launch command (`run-start`/`run-finish --cmd`; see the **Run-vs-run loop** pattern), **session_node_id** — nullable FK into `session_nodes` set only by `%exptrack promote`, **deleted_at** — nullable ISO timestamp; non-null = soft-deleted/Trash. Indexed on `deleted_at`, **name_is_auto** — `INTEGER DEFAULT 0`; 1 means the run still carries its generated name. Set on insert from `not bool(name)`, cleared by `POST /api/experiment/<id>/rename`, preserved by internal auto-renames (`Experiment._rename`). Backfilled idempotently in `_ensure_schema()` via `looks_auto_named` so pre-1.11 runs flag too)
- **`params`** — key/value pairs (exp_id, key, value as JSON string, source). Source is 'auto' (captured from script/argparse) or 'manual' (added via dashboard or `api_create_experiment`). Auto params are read-only in the UI; manual params can be edited, renamed, and deleted via dashboard inline editing
- **`metrics`** — float values (exp_id, key, value, step, ts, source, **session_node_id**). Source is 'auto' (from scripts), 'manual' (dashboard), or 'pipeline' (CLI). `session_node_id` is a nullable tag naming the Session Trees node that was active when the metric was written (`experiment._active_session_node()`, NULL outside a session), indexed via `idx_metrics_session_node` — see the **Per-branch metric attribution** pattern
- **`artifacts`** — output files (exp_id, label, path, content_hash, size_bytes, timeline_seq, created_at)
- **`timeline`** — execution events (exp_id, seq, event_type, cell_hash, cell_pos, key, value, prev_value, source_diff, ts)
- **`cell_lineage`** — content-addressed cell history (cell_hash, notebook, source, parent_hash, created_at)
- **`code_baselines`** — position-based cell baselines (notebook, cell_seq, source, source_hash)
- **`code_snapshots`** — content-addressed full script/shell-script source (hash PK, content, kind, path, size_bytes, created_at). Written at run time by `capture_script_snapshot` (deduped by content hash, `.ipynb` never stored, size-capped by `snapshot_max_kb`) and referenced from the `_code_snapshot` param, so a run stays re-runnable after the file is edited. See the **Run-vs-run loop** pattern
- **`sessions`** — Session Trees container (id, name, notebook, status `'active'|'ended'`, git_branch, git_commit, created_at, ended_at, **deleted_at** — nullable unix timestamp; non-null = soft-deleted/Trash, indexed via `idx_sessions_deleted`). Created only by `%exptrack session start`. Soft-deletable + restorable (mirrors experiments/nodes). A trashed session is hidden from `list_sessions`/`find_session` but **still loadable** by `build_tree`, which surfaces it as `session.deleted` — see the **A trashed thing that's still reachable must say it's trashed** pattern
- **`session_nodes`** — tree nodes (id, session_id, parent_id, node_type `'root'|'checkpoint'|'branch'|'abandoned'`, label, note, cell_source, **cell_outputs** — SEP-joined per-cell output blob aligned 1:1 with `cell_source` (trailing-expression `repr` per recorded cell; `%load_ext exptrack` captures it and `record_cell(source, output)` keeps the two blobs segment-aligned through dedup/elision), **setup_source** / **setup_outputs** — nullable SEP-joined blobs holding `%%setup` prep cells (recorded-but-secondary; own `_NODE_SETUP_MAX_BYTES` budget so they never evict real cells, written by `record_setup_cell()`), **images** — nullable JSON list of `{path, label, ts}` for plots saved by reference (no copy) while the node was active, deduped by path and capped at 30 via `record_image()`, git_diff, git_commit, seq, created_at, **deleted_at** — nullable unix timestamp; non-null = soft-deleted/Trash). Indexed on (session_id, seq), (parent_id), and (session_id, deleted_at)

Indexed on: metrics(exp_id, key), params(exp_id), artifacts(exp_id), timeline(exp_id, seq), experiments(created_at, status).

`metric_commit_interval_ms` (default 250): how long a metric write may sit

**Run-vs-run loop** pattern).

## Coding Best Practices

### General Principles
- **stdlib only**: No external dependencies. Every import must come from the Python standard library
- **Keep functions focused**: Each function should do one thing. If a function exceeds ~40 lines, consider splitting it
- **Reuse existing utilities**: Check `core/db.py` (`get_db`, `_find_exp`), `cli/formatting.py` (ANSI color helpers), and `config.py` (project root, config loading) before writing new helpers
- **Deduplication**: `log_artifact()` already deduplicates by resolved path. Use this pattern — check before insert — for any new data types
- **Error boundaries**: Wrap external operations (file I/O, git, plugin calls) in try/except. Never let a capture failure crash the user's training script

### Dashboard Modularization

The dashboard has been fully modularized. `static.py` assembles the JS/CSS bundles (`DASHBOARD_CSS`/`DASHBOARD_JS`) and the HTML shell (`DASHBOARD_HTML`), which references the bundles via hash-versioned `<link href="/static/dashboard.css?v=…">` / `<script src="/static/dashboard.js?v=…">` (external serving — the browser caches the ~600 KB of JS/CSS instead of re-inlining it every load; the shell is ~31 KB). `_assemble_html()` swaps the inline `<style>`/`<script>` slots for the external refs (asserting the html.py boundary tokens so a future edit fails loudly).

**The JS/CSS content lives in real files** under `exptrack/dashboard/static/{js,css}/*.{js,css}` (so it's editable with JS/CSS tooling — ESLint, formatters, editor language servers). The `static_parts/{js,css}/*.py` modules are thin **loader shims**: each loads its file via `static_parts/_loader.py` (`_load_js`/`_load_css`, `lru_cache`d) and binds it to the same `JS_*`/`CSS_*` constant name as before. So `get_all_js()`/`get_all_css()`/`DASHBOARD_HTML` are byte-for-byte identical and every existing import (incl. per-module `from ...static_parts.js.core import JS_CORE`) still works. **To edit dashboard JS/CSS, edit the `.js`/`.css` file, not the `.py` shim.** Lint with `npm run lint` (or `npx eslint exptrack/dashboard/static/js`); config in `eslint.config.js` (dev-only Node tool — the Python package stays stdlib-only). Static files ship in the wheel/sdist via `pyproject.toml` `package-data` (`"exptrack.dashboard" = ["static/js/*.js","static/css/*.css"]`) + `MANIFEST.in`.

**Current structure:**
- **`static/js/*.js` + `static/css/*.css`** — the actual dashboard JS (22 files) and CSS (16 files) content
- **`static_parts/css/`** — 16 loader-shim modules (reset, layout, cards, table, detail, charts, code, timeline, compare, components, studies, images→[images,image_compare], toolbox, sessions, trash). Each binds a `CSS_*` constant loaded from `static/css/`. `get_all_css()` assembles them
- **`static_parts/js/`** — 22 loader-shim modules (core, highlight, owl, sidebar, table, experiments, inline_edit, detail, charts, compare, mutations, timeline, image_compare, studies, stage, manual, todos, commands, confusion, sessions, trash, init). Each binds a `JS_*` constant loaded from `static/js/`. `get_all_js()` assembles them
- **`static_parts/_loader.py`** — `_load_js`/`_load_css` file readers (lru_cache)
- **`static_parts/html.py`** — HTML_HEAD, HTML_BODY, HTML_FOOTER
- **`static_parts/styles.py`** and **`static_parts/scripts.py`** — thin re-export shims for backward compatibility
- **`dashboard/js/__init__.py`** — convenience re-exports with short aliases (e.g., `from exptrack.dashboard.js import core`)
- **`routes/read_routes.py`** — GET API endpoints
- **`routes/write_routes/`** — POST API endpoints. Was one 1940-line module with 79 public functions; now a package of 10 submodules grouped the same way `handler.py` dispatches (experiments, params, metrics, studies, settings, compact, bulk, admin, toolbox, sessions). `__init__.py` re-exports every endpoint plus the handful of `_`-prefixed internals tests import directly, so no import anywhere had to change. Add a new endpoint to its submodule *and* to `__all__`; `tests/test_dashboard_routing.py` fails if `handler.py` references a name the package doesn't export, and if `__all__` drifts from the real surface. **Cross-package imports here are absolute** (`from exptrack.core.db import`), not relative: most of them are function-local, so a wrong relative depth would resolve to the wrong package and fail at *call* time rather than import time — one endpoint broken and green tests. Only same-package imports (`from ._shared import body_str`) stay relative

**Rules for dashboard changes:**
- When modifying JS, keep the existing function signatures stable — other parts of the JS may call them
- All API calls should go through `api()` (GET) or `postApi()` (POST) helpers
- New UI features should follow the inline-editing pattern (double-click to edit, Enter/Escape to save/cancel)
- CSS custom properties (variables) are defined in `:root` — use them instead of hardcoded colors
- **Escaping in inline handlers**: `esc()` (in `js/mutations.py`) HTML-escapes for text/attribute contexts; `escJs()` is the JS-string-context escaper. Any user-controlled value placed inside an inline `on*="…('…')"` handler passes through HTML decoding *then* JS parsing, so it must be JS-escaped first, then HTML-escaped. Use the composed helper **`escJsAttr(value)`** (= `esc(escJs(value))`) at every such site so the order can't be transposed — don't hand-nest `esc(escJs(x))`. Plain `esc()` alone inside a handler is a stored-XSS/broken-button bug. `test_dashboard_js_integrity.py` enforces this and that every inline-handler function is defined

## Rules for Changes

Every user-visible change (new feature, bug fix, behavior change) must update **all three** of the following before commit:

1. **`CLAUDE.md`** — keep the codebase documentation in sync. Update the relevant sections (Architecture, Key modules, Key Design Patterns, Database Schema, Configuration) so this file accurately reflects the current state
2. **`CHANGELOG.md`** — add an entry under the current unreleased version using the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. Use `### Added` / `### Changed` / `### Fixed` / `### Removed` sub-headings. Lead each bullet with a bolded short title (e.g. `**Param editing in the dashboard**`) followed by a one-sentence description of what changed and why a user should care
3. **`pyproject.toml`** — bump the `version` field. Patch (`x.y.Z+1`) for bug fixes; minor (`x.Y+1.0`) for new features or schema migrations; major (`X+1.0.0`) for breaking API changes. The `__version__` exposed in `exptrack/__init__.py` reads from package metadata, so this is the single source of truth

Internal-only refactors with no user-visible effect (e.g. moving a helper, renaming a private function) may skip the changelog and version bump, but should still update `CLAUDE.md` if the structural map changes.

**Cosmetic dashboard tweaks (carve-out):** purely presentational dashboard CSS/JS changes that add no new module, route, schema column, config key, or behavior contract — a button, a hover affordance, a sticky bar, a color/spacing tweak, a copy helper — update **`CHANGELOG.md` + `pyproject.toml` (patch bump)** only. Do **not** rewrite the large `Key Design Patterns` paragraphs in `CLAUDE.md` for these; the design pattern is unchanged, only its surface. (Touching a route, manager function, DB column, or a documented behavior is *not* cosmetic — update all three as above.) This keeps small UI fixes cheap to land.

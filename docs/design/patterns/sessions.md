# Session Trees

The opt-in exploratory tree for notebooks: checkpoints, branches, materializing nodes into runs, per-branch metric attribution.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **Session Trees (opt-in exploratory tree tracking)**: A second tracking mode for notebooks that records the *shape* of exploration (checkpoints + branches + scratch cells) as a tree, layered on top of standard `%load_ext exptrack` capture. Activated only by `%exptrack session start "name"` — without it every other session magic is a silent no-op, so existing capture is unaffected. `%exptrack checkpoint "label"` writes a node and snapshots a per-checkpoint git diff (`git diff` from the previous checkpoint's commit, falling back to `git diff HEAD`). `%exptrack branch "label"` adds a child of the most recent checkpoint and tags it as the current node so subsequent commits/checkpoints flow under it. **Every magic is idempotent under a Run-All**, which is the workflow the whole feature exists for: re-running the notebook re-executes the magics while the current node is still wherever the last pass ended, so `checkpoint(label)` resolves a label already present as a child *or an ancestor* of the current node (`_find_ancestor_checkpoint`) and returns to it. Without the ancestor case the checkpoint was created *under the previous pass's branch*, and the next branch under that — every Run-All grew a fresh duplicate spine, with its own cells and its own diff blob. Three sibling paths had the same hole and each grew the tree per pass. **`_find_ancestor_checkpoint` starts its walk at the current node itself**, not its parent, so re-declaring the checkpoint you are standing on resolves through the normal path and lands on `checkpoint()`'s single `_switch_to_node`. That case used to be structurally invisible to the resolver and was covered by a special-cased early return which returned the id *without* re-arming the cursors (so every cell of the node was appended again per pass) and without updating `_last_checkpoint_id`; fixing the resolver deleted the special case. **`start()` on an already-active session returns to the session root** (via `_session_root_id`), because re-executing the notebook's *first* magic is the strongest "replaying from the top" signal there is; doing nothing left the pre-checkpoint cells (imports, data loading) recorded onto whatever node the last pass ended on, appending a copy per pass while the root's own copies sat untouched. `session_hooks._session_start` has to cooperate — it used to `return` on an active session, so `start()` was never reached from a real notebook; it now just calls `start(name)` and prints per the result. **The replay-vs-conflict rule lives in `start()`**, which keeps `self.session_name` from the row it wrote and returns `""` for a *different* name while a session is live: the rule belongs next to the rewind it guards, so every caller gets it rather than only the one magic that happens to call this today (the hook is a thin print switch like every other function in that file, and the DB round-trip it used to make for the name is gone). **The collision fork is idempotent too**: `_resolve_branch_collision` consults `_find_sibling_by_first_cell(parent, recorded)` before forking, since `_find_child_by_label` only ever resolves the *unsuffixed* label, so each Run-All of an edited branch re-collided with the original and forked another suffix (`A (2)`, `A (3)`, `A (4)`, one per pass). **Identity there is the first recorded cell, not the label**: matching a `"{label} ("` prefix instead was defeated by the very thing the fork notice invites the user to do — rename the fork — and by promoting one to a checkpoint, either of which made it unfindable and re-forked it on the next pass, i.e. the label heuristic re-created the bug it was written to fix. Content matching needs no `node_type` filter and no `LIKE` escaping of user text, and it only runs on the rare collision path. `%%scratch` is a cell magic that executes the cell body but its source begins with `%%scratch`, so the `_post_run_cell` hook detects it via `is_scratch_cell()` and skips all logging — no DB row is ever inserted, not insert-then-delete. **`%%setup` is a third tier between a normal cell and `%%scratch`: recorded-but-secondary prep code.** `_post_run_cell` detects it via `is_setup_cell()` and routes it through `_record_setup_cell()` instead of the normal path: `SessionManager.record_setup_cell()` appends source+output to the node's **own** byte-budgeted columns (`setup_source`/`setup_outputs`, `_NODE_SETUP_MAX_BYTES`, so a big prep block can't evict real cells) — through the **same replay recognition tracked cells get**, against the setup store's own cursor pair (`_setup_replay_idx`/`_last_setup_idx`, armed by `_switch_to_node` alongside the cell pair). The old helper deduped only against its *last* segment, which is enough for a back-to-back re-run and useless for a replay: a node with two or more setup cells appended a fresh copy of every one on every Run-All, doubling the blob until the cap began evicting real content and replaying each duplicate as its own `setup` timeline event on materialize. **`_record_segment()` is now the one implementation of the segment rules** (align the two blobs, refresh a repeat in place via `_match_segment`, elide oldest in pairs over the cap, return the advanced cursors), used by `record_cell` and `record_setup_cell` alike — `record_cell` used to carry its own inline copy, so the byte-budget arithmetic and the elision sentinel lived twice, 140 lines apart, free to drift on exactly the duplication bugs they exist to prevent, and a muted `setup` timeline event (full source + output) is attached to the active experiment so a promoted run stays self-contained — but it never enters cell lineage, variable tracking, or git diffs. Both `%%scratch` and `%%setup` run their body via `session_hooks._run_cell_body()`, which AST-splits the trailing expression and routes it through `ip.displayhook` so a bare final `df` renders (plain `exec` swallowed it). The dashboard shows setup cells dimmed under a collapsed **Setup / prep** section (`renderSetupCells`, `.setup-cell`, `pill-setup`) in the node detail plus a `🛠 N` count on the tree node. `%exptrack promote "label"` writes the active experiment's `session_node_id` to the current node and appends the label to the node's `note`. `%exptrack session end` flips any open branch (no descendant) to `node_type='abandoned'` and sets `sessions.status='ended'`. That DB half lives in **`lifecycle.end_session_rows(conn, session_id)`** (one `UPDATE`, returning its `rowcount`), shared by `SessionManager.end()` and the dashboard's `api_session_end` — the route had its own copy of the UPDATE *without* the `deleted_at IS NULL` filters, so it relabelled trashed branches (which then restored as `abandoned`) and counted trashed children as children, leaving a branch whose only children are trashed un-abandoned forever. Both filters are load-bearing. The route additionally delegates to `mgr.end()` when the session is live *in that process*, so the open branch's working-tree diff is captured and the in-process state cleared. The current `SessionManager` lives in `exptrack.sessions` as a module-level singleton (`get_current_session()` / `set_current_session()`); it caches `_current_node_id` and `_last_checkpoint_id` so branches always attach under the most recent checkpoint. The dashboard's `Sessions` tab (toggled via the `☰ Sessions` header button, which adds `body.sessions-active`) renders the tree as a **git-graph lane rail** (`renderTreeRows` + the pure layout pass `computeTreeLayout`, replacing the old recursive `renderTreeNode`): the nested tree is flattened (pre-order DFS over seq-ordered `children`) into a flat list of `.tree-row`s, each a 2-column grid `[.tree-rail | .node-row content]`. The **checkpoint chain is the neutral spine** (lane 0, `--branch-c0` = `--text-2`): exactly one child continues the parent's lane — the first checkpoint/root child (`spineIdx` in `computeTreeLayout`) — and **every branch (and abandoned dead-end) forks into its own color-coded lane that descends straight from the checkpoint's dot** (each edge lives in the *child's* lane, and the parent row draws a `forkChildren` "sprout" curve per branch), so two branches off the same checkpoint read as equal siblings with no stray parallel spine-line, and **promoting a branch to a checkpoint makes it rejoin the spine** as the main line on the next render. A compact `.tree-legend` (`_treeLegendHtml`) above the graph explains the spine/branch-color/dot-shape/`⑂`/`← latest`/`⟨⟩` marks so the graph is self-describing. Each node also carries inline **code tracing**: an always-visible one-line **defining change** (`✎ …`, via `_definingChange` — the first added line of its diff-vs-parent, paired as `old → new` when a similar removed line exists, else the first cell-source line) and a `⟨⟩` **code toggle** (`toggleNodeCode`) that expands the node's full syntax-highlighted cell source (`_nodeCodePeek` → shared `_highlightPy`) inline in the row, so "what did this branch run?" is answerable without opening the detail pane. Lane color is **bounded and state-based, not per-branch** (`_laneClass(node_type, lane)` → `tc-spine`/`tc-branch`/`tc-ab`): because a tree's lanes never merge, lane *position* already tells branches apart, so color only encodes kind — neutral spine (`--branch-c0`=`--text-2`), one calm teal for **every** branch line (`--branch-c1`), amber for abandoned (`--branch-ab`). The palette therefore never grows with the number of branches (the old `--branch-c0..c5` djb2-hashed rainbow is gone). All three tokens live in `css/reset.py`, redeclared under `body.dark`, kept clear of accent-blue and the violet `--compare-accent` so a branch line never reads as a selection/pick. The node marker is an overlaid round `.rail-dot` colored by node **type** (CSS, independent of the lane color, so a checkpoint is **always** a neutral filled dot even on a teal branch line): checkpoint/root = neutral filled, branch = teal ring, abandoned = amber dashed ring, divergence = ring-halo — i.e. **dot shape = node type, line color = spine vs. branch** (spelled out in the `.tree-legend` note). **Rail geometry is pixel-anchored, not percentage-stretched.** `_railHtml` draws straight lane lines as absolutely-positioned CSS `.rail-v` divs whose junction sits a fixed `_TITLE_Y` (16px) from the row top — so the `.rail-dot` (also anchored at `top:_TITLE_Y`) lands exactly on the node's **title line** regardless of how tall the row grows (the old full-height SVG put the junction at 50%, which floated the dot down to the vertical middle of tall rows — the param/result lines pushed it off its own label). A fork is a **fixed-height elbow** (`_FORK_H`=20px), not a row-spanning curve: a tiny `.rail-fork` SVG offset to `top:_TITLE_Y; height:_FORK_H` draws one short bezier per branch child jogging from the parent lane to the child lane, then the child lane continues as a **straight** `.rail-v` vertical the rest of the way down — through the parent row, any rows between (pass-through), and into the child's own row (incoming → dot). Because the curve is bounded and every long run is a straight pixel-anchored div, a fork can never stretch long or **overshoot past its own dot** regardless of how tall a row is (the earlier full-height stretched-curve fork did exactly that — a leaf branch's line ran on below its dot and dangled). Pass-through lanes are full-height `.rail-v` divs in their own branch color; a node's own lane is incoming (top→dot) plus, only when a checkpoint/spine child continues it, a continuation (dot→bottom). A checkpoint that forks shows a `⑂ N` **divergence badge**; the single most-recent live node gets a `← latest` **frontier tag** (max `created_at`, computed in `renderTreeRows`); and any node with children carries a collapse caret (`toggleNodeCollapse` → per-session `localStorage['exptrack-tree-collapsed:<sid>']`; `computeTreeLayout` skips collapsed descendants and shows an `N hidden` hint) to keep big sessions scannable. The `.node-row` content cell is byte-identical to before (same `data-node-id`/`onclick`), so selection (`.node-row.selected`), compare pins (`.compare-picked`), promote/delete/`→ exp` badge all keep working. The tree header carries a **Produced** outcome strip (`.session-outcomes` — clickable experiment chips that open the run + checkpoint/branch/abandoned counts, from `build_tree`'s read-time `session.outcomes`), and the node detail opens with a clickable **lineage breadcrumb** (`.node-lineage`, `root › checkpoint › branch › …`, each crumb `selectNode`s an ancestor) built from the id-bearing `lineage` list `build_tree` now attaches to every node (in-memory parent walk, no new endpoint). Each node shows label, time, diff summary, and a `→ exp <id>` badge when promoted — and **the `→ exp` badge actually navigates now**: `showDetailView()` (js/sidebar.py) closes the Sessions tab first, because `body.sessions-active` hides `#detail-view` with `display:none !important`, so clicking the badge previously fetched the run but never showed it. Clicking a node shows its source/diff/note in `#session-detail`, with inline note editing via `POST /api/session/<id>/note-node`. Cell runs render as collapsible `<details>` blocks (header shows `cell N / M` and line count) with an inline line-number gutter; **every block defaults collapsed** (session code is reference material — shared renderer `_cellBlocksHtml`), and a clickable `▸ N cells collapsed — expand all` hint sits above the list so the count is visible. Each cell summary, each `Out` panel, the **Latest result** block, and each **Compare** column carry a `⧉ Copy` button (`_copyBtn` → `copySessionText`) that copies the raw source/output to the clipboard — the raw text is stashed in a `data-raw` attribute since the rendered `<pre>` interleaves line-number spans and `textContent` would lose newlines. **Each individual code line also has a hover-revealed `⧉` per-line copy button** (`.cl-copy` → `copyCellLine`, raw line stashed in the `.cl`'s `data-line`) so a single line can be grabbed without dragging a selection that picks up the gutter or collapses the `<details>`. Cell `<details>` carry a stable `data-ck` key (`<prefix>-<i>`) so `renderSelectedNodeDetail` can **remember which cells are expanded and restore them after a re-render** (note save / diff-mode toggle no longer collapses open cells). The cell-code and output/result blocks have **no height cap** (`pre.cell-code`, `.cell-output`/`.node-latest-result`/`.cmp-result` are `overflow: auto; resize: vertical`) so long cells/outputs expand fully instead of hiding behind an inner scrollbar that fights copy/paste — drag the bottom edge to shrink a huge block. Tree nodes render on two lines — primary row is the label plus pills (`abandoned`, `→ exp <id>`) and the secondary `.node-meta` row carries time · cells · `+N −M` in 11px monospace dim. Selection is signalled by a 3px left accent bar on `.node-row.selected` (driven by `data-node-id` lookup, not `onclick`-string parsing). Abandoned branches show an amber `abandoned` pill, dashed amber left border, and strike-through label. A branch or checkpoint created by a magic-only cell starts with no `cell_source` (the calling cell is skipped by `_is_session_cell`) — until the next cell runs and `record_cell()` populates it, the node renders an italic `awaiting first cell…` placeholder so the empty-state is explicit instead of looking like a render bug. Diffs respect the `git_diff_exclude` config (default `["*.ipynb"]`) — `core/git.py:git_diff(*range_args)` appends `-- :(exclude,glob)<pattern>` pathspecs to every `git diff` invocation across `git_info()`, `checkpoint`, `branch`, and `_compute_diff_vs_checkpoint`, so notebook JSON churn no longer eats the `max_git_diff_kb` budget for actual source edits. The note editor disables Save until dirty and renders a "Saved · HH:MM" inline status on success; the diff section's Split / Unified toggle + `+N −M` summary live in a `position: sticky` header that stays anchored while scrolling a long diff. Session cards in the left rail are a tighter two-row layout — name + status pill on top, notebook · checkpoints · relative time below. Git diffs render in a GitHub-style **split** (side-by-side) view by default with a `Split / Unified` toggle (persisted in localStorage as `exptrack-diff-mode`); each file is its own collapsible card with per-file `+N −M` stats, hunk headers, and theme-aware tinted backgrounds (`--diff-add-bg`, `--diff-del-bg`, `--diff-add-bar`, `--diff-del-bar`, `--diff-empty-bg`, `--diff-hunk-bg`, all redefined under `body.dark`). Branch nodes capture their `git_diff` (vs. the parent checkpoint's commit, plus working-tree changes) at creation via `SessionManager._compute_diff_vs_checkpoint`, and refresh it on **structural transitions only** — `_refresh_branch_diff()`, called from `checkpoint()`, `branch()`, `promote()` and `end()`, i.e. the moments you leave a branch; checkpoints freeze their diff at creation. It used to refresh after *every recorded cell* (throttled by a 2 s window that interactive cells almost always exceed), so each cell paid two or three `git` subprocesses plus a rewrite of the node's whole diff blob — ~11 ms/cell on a 60-file repo — overwhelmingly to store a byte-identical diff, since exploration happens in cells and cells aren't in the working tree. The tradeoff is explicit: a working-tree edit made mid-branch lands on the node at the next transition rather than instantly, and nothing is lost because every path that *reads* a branch's diff (promote, materialize, finalize, end) passes through one first. **Node diffs are capped and content-addressed**: `_shared._store_node_diff(conn, diff)` applies `max_git_diff_kb` (a node used to store whatever `git diff` produced, uncapped and inline) and writes the body to `git_diffs` via `store_git_diff`, returning a `[ref:sha256:…]` marker — sibling branches off one checkpoint share a working tree, so they share one blob instead of storing N copies of the same text. A status sentinel (`[capture-failed]`) is stored as-is, never as a blob. `build_tree` resolves each node's ref back to text via `_shared._resolve_node_diff(conn, raw, cache)`, memoized because that sharing means one body would otherwise be re-read once per node. Because session nodes now hold refs, **`_compact_git_diffs` checks `session_nodes` as well as `experiments`** before deleting a blob — otherwise compacting a run stripped the body out from under the tree it came from. Tree reconstruction tolerates orphaned nodes (attached to root) and synthesizes a root if none exists. CLI: `exptrack sessions`, `exptrack session show|nodes|rm|restore|purge|finalize|rm-node|restore-node|trash|note|promote-checkpoint`. `rm-node <node_id_prefix>` cascade-**soft**-deletes a single branch/checkpoint and all its descendants by setting `session_nodes.deleted_at` (rows persist for Restore); the dashboard exposes the same via a hover-revealed `×` on every non-root tree node, with a confirm dialog driven by `/api/session/<sid>/delete-node-preview` → `/api/session/<sid>/delete-node`. `delete_node()` clears `experiments.session_node_id` on linked runs (experiments themselves are preserved) and resets the live `SessionManager._current_node_id` / `_last_checkpoint_id` if either pointed at a trashed row, so subsequent magics don't dangle — **via `_switch_to_node`, never by assignment**: the manager caches the current node's cell blobs and both replay cursors, and a bare assignment left all of them describing the *deleted* node, so the next recorded cell was written as "the deleted node's cells + this one" onto the fallback — the trashed branch's code silently reappeared on its parent checkpoint, and restoring the branch then duplicated it. `_switch_to_node`'s docstring states the invariant. Trashed nodes are surfaced in the **unified Trash view** (see the **Soft-delete (Trash)** pattern) — the global Trash (Settings → 🗑 Open Trash) now has a **Session nodes** section, grouped by session, alongside the **Experiments** section, so there is one place to restore/purge anything. The session-view header's `🗑 Trash (N)` button opens that unified view (`openTrashView()`); the `(N)` chip still shows this session's trashed-node count (`GET /api/session/<sid>/trash`). The per-session trash *panel* that used to live inside the session view was removed. `restore_node(node_id)` (POST `/api/session/<sid>/restore-node`, or `exptrack session restore-node <node_id>`) brings the trashed subtree back and additionally revives any trashed ancestors so the restored node is never re-orphaned at the synthesized root. The cross-session listing that feeds the unified view is `list_all_trashed_nodes(conn)` (session-annotated, in `manager.py`); the per-session `list_trashed_nodes(session_id)` still backs `exptrack session trash <id>`. Linked experiments do not re-attach on restore — `delete_node` cleared their `session_node_id` and there's no way to pick the "right" run. `build_tree`, `list_sessions` (checkpoint count), `_find_child_by_label`, and `api_session_nodes` all filter `deleted_at IS NULL`. **Whole sessions are themselves soft-deletable now** (mirroring nodes/experiments): `delete_session(session_id)` is **soft by default** — it sets `sessions.deleted_at` (recoverable; nodes + linked experiments untouched) and `list_sessions`/`find_session` filter trashed sessions out; pass `permanent=True` (or the Trash's **Delete forever**) to hard-delete everything (linked runs preserved, `session_node_id` cleared). `restore_session(session_id)` clears `deleted_at`; `purge_session(session_id)` refuses a non-trashed session so removal is always a trash → purge two-step. The unified Trash gains a **Sessions** section (`list_trashed_sessions` → `trash.list_unified_trash`'s `trashed_sessions` key; `restoreSession`/`purgeSession` JS → `POST /api/session/<sid>/{restore,purge}`); CLI `exptrack session rm` (soft, `--permanent` to purge), `session restore`, `session purge`. **Permanent purge**: trashed nodes can be removed for good via `purge_node(node_id)` (one trashed subtree) and `empty_trash(session_id)` (all trashed rows in a session) in `manager.py` — both refuse anything not already trashed, so true removal is always a deliberate trash → purge two-step. Surfaced as a **Delete forever** button per row and an **Empty trash (N)** button in the dashboard Trash panel (no-undo `confirm()`), `POST /api/session/<sid>/purge-node` + `POST /api/session/<sid>/empty-trash`, and CLI `exptrack session purge-node <node_id>` / `exptrack session empty-trash <id_or_name>` (prompt unless `-y`/`--yes`). Linked experiments are preserved (purge re-clears any dangling `session_node_id`). **Per-node results capture**: `record_cell(source, output)` stores each cell's output into `session_nodes.cell_outputs` (a SEP-joined blob parallel to `cell_source`; over-cap elision drops oldest source+output segments together to stay aligned). **A cell that repeats one already recorded refreshes it in place instead of appending a copy** — `_match_recorded_cell` accepts two kinds of repeat: the cell recorded most recently (`_last_cell_idx`, a back-to-back re-run) and the one at the replay cursor (`_replay_idx`, a Run-All stepping through the node's cells in their original order). `_switch_to_node` arms the cursor at index 0, since entering a node is exactly when a Run-All starts replaying it; recording a genuinely new cell appends and clears the cursor, so diverging mid-replay is recorded normally. Before the cursor, only a back-to-back repeat was caught, so every Run-All appended a second copy of every cell and the node's stored cells doubled per pass until the byte cap began evicting the real content. The `output` is the combined `print()` stdout + trailing-expression repr built by `_combine_cell_output` (see the **Notebook cell output capture** pattern), so session nodes capture printed output too — not just bare returned values. The dashboard shows it three ways: a one-line `⤷ <result>` `.node-result-mini` preview on each tree node, a **Latest result** `.node-latest-result` block in the node detail, and an `Out` `.cell-output` panel under each cell block. **Branch comparison**: a `⇄ Compare branches` header toggle (`session-compare-toggle`) flips `_compareMode`; while on, clicking nodes adds them to an ordered `_compareNodes` list. Every non-root tree node also carries a hover-revealed per-node `⇄` pin (`.node-compare-btn` → `pinCompareNode`) that adds it straight to the comparison and enables `_compareMode` on demand (no need to find the global toggle first when the tree is long); a picked pin renders filled in the compare-accent and clicking it again removes the node (thick 6px `.compare-picked` bar + tint + a numbered `.compare-pick-num` order badge; the single-select `.selected` accent is suppressed while `_compareMode` is on so a pick can't be mistaken for the node you were viewing) instead of opening single-node detail, and a `#session-compare-bar` shows the count + a **Compare N** button. The compare bar is `position: sticky` (top of the view) and carries **Compare / Clear / Done** buttons (Done = `toggleCompareMode`), so a comparison can be started (per-node `⇄` pin) and stopped anywhere in a long tree without scrolling back to the header toggle. `toggleCompareNode`, `clearCompare`, and `toggleCompareMode` all re-render the whole tree via `_rerenderTreeContainer()` (from the cached tree) so the order badges renumber when a middle pick is removed. `runCompare()` renders the picked nodes from the cached tree as side-by-side `.cmp-col` columns (type, cell count, `+N −M` diff summary, promoted-exp link, captured **Result**) into `#session-compare`. Compare picks use a dedicated violet accent (`--compare-accent` / `--compare-bg`, now centralized in `css/reset.py` — it is the only purple left in the palette) for the bar/tint/badge/toolbar/columns so a pick is never confusable with the blue `.selected`/hover accent. **Branch-label collision guard**: re-using a branch label under the same checkpoint can't be classified at `branch()` time (the cells haven't run), so on collision `branch()` switches to the existing node and arms `_pending_collision = {existing_id, label, parent_id, baseline_first}`; the next `record_cell()` calls `_resolve_branch_collision(recorded)` which compares the incoming cell against the existing node's first cell — identical ⇒ genuine Run-All re-run (merge, dedup), different ⇒ a new idea reusing the name, so it forks a fresh `_unique_branch_label()` node via `_create_branch_node()`, switches to it, and prints a stderr notice. The guard is one-shot (cleared in `record_cell`, `branch`, `checkpoint`, `end`). **Node rename**: `rename_node(node_id, label)` (module-level in `manager.py`; rejects empty labels and trashed nodes) backs inline rename in the dashboard node-detail header (double-click `#node-label-text`, Enter/blur saves, Escape cancels — `startNodeRename`), `POST /api/session/<sid>/rename-node`, and `exptrack session rename-node <node_id> "label"`. **Promote branch → checkpoint**: `promote_to_checkpoint(node_id)` (module-level in `manager.py`; rejects non-branch / root / trashed nodes, no-op on an already-checkpoint) flips a branch's `node_type` to `checkpoint`, freezing its live-refreshed `git_diff` in place and repointing the live `SessionManager._last_checkpoint_id` so later branches attach under it. Surfaced as a hover `↑ checkpoint` button on branch/abandoned tree nodes (`promoteBranch` JS → `POST /api/session/<sid>/promote-to-checkpoint`) and `exptrack session promote-checkpoint <node_id>`. **Promote node → experiment (dashboard)**: `materialize_experiment(node_id)` (module-level in `manager.py`) creates a standalone experiment from a node's captured data — name from the node label, `git_branch`/`git_commit`/`git_diff` + note copied over, status `done`, and the node's **whole ancestor chain** of recorded cells (root → … → node, via `_node_ancestor_chain`) replayed as `cell_exec` timeline events (source + output) so the run is **self-contained / re-runnable** — a branch cell like `run_pipeline(data, threshold)` carries the upstream root/checkpoint cells that defined `run_pipeline`/`data`, not just its own fragment — then links it (`experiments.session_node_id`). **It also re-attributes metrics** — see the **Per-branch metric attribution** pattern: `_copy_node_window_metrics(conn, node_row, exp_id)` copies the session's live-run metrics belonging to this node onto the materialized run, so each graduated branch carries its own numbers (the 0.7 branch gets the 0.7 accuracy), not just its code. **Each replayed cell's full source is also written to the content-addressed `cell_lineage` table (`INSERT OR IGNORE`, keyed on `cell_hash`) and the event's `cell_hash` set to point at it**, so the Timeline's "view source" button (which is gated on `cell_hash`) appears and serves the whole cell via `/api/cell-source/<hash>` — without this only the one-line preview survived promotion and the session code couldn't be retraced/rerun. Because the body lives there, the timeline event stores only a **preview** (`source_preview`, capped at 200 chars exactly as the live capture path caps it): it used to store the whole cell *as well*, so materializing N sibling branches wrote N copies of every shared ancestor cell into timeline JSON. Setup events keep their source inline (they render inline, with no view-source button and no `cell_lineage` row) bounded by `_SETUP_EVENT_MAX_BYTES`, mirroring the live path's `{source, source_preview}` shape. - **Per-branch metric attribution (tag at write time, don't infer it later)**: A notebook session funnels every `metric()` call into one auto-created run, so "which branch produced this number?" has to be recorded, not reconstructed. `Experiment.log_metric`/`log_metrics` stamp each row with `_active_session_node()` — the live `SessionManager._current_node_id`, or NULL outside a session — and `materialize_experiment` copies the rows naming the node it's graduating. This replaced a timestamp heuristic: `_copy_node_window_metrics` used to take every metric whose `ts` fell in `[node.created_at, next node's created_at)`, which is wrong the moment you **revisit** a branch — `branch("existing label")` *switches* to a node without creating one, so the window never moves and the new metric is credited to whichever node happens to be newest. Promote the 0.7 branch and you could get the 0.5 branch's accuracy, silently, in exactly the compare-branches workflow the feature exists for. The window survives only as a **fallback for rows written before the column existed**, and it is restricted to `session_node_id IS NULL` rows — letting it claim a *tagged* metric would re-introduce the same theft it was replaced for. The tag is layered so it can't break metric logging: the import of the (optional) session subsystem is function-local and any failure degrades to NULL. Migration is `_migrate_metrics` (nullable `TEXT` + `idx_metrics_session_node`); **the index is created there, not in `_create_base_schema`** — the base script runs first, so indexing the column there would fail on every pre-existing DB, and one failed statement aborts the whole script, i.e. every install breaks on upgrade. **Write-time tagging is necessary but not sufficient across a collision fork.** A branch-label collision is only *decided* at `record_cell` time — after the cell body ran — because the decision reads the cell's code (identical ⇒ merge, different ⇒ fork). But `metric()` and the savefig patch fire *during* the body, when `_current_node_id` still points at the pre-fork node, so their rows are tagged to the original while the diverging code graduates to the fork: the original keeps numbers it never produced and the fork carries code without them — the exact theft above, re-entered through the fork path. `_resolve_branch_collision` therefore calls `_reattach_cell_records(old, new, pc)` on **both** fork paths (a fresh fork and returning to a prior pass's fork), moving this cell's rows from the old node to the fork. "This cell" is bounded by marks captured when `branch()` armed the collision: `metric_mark` = `MAX(metrics.id)` at that instant (metric rows past it were logged during the cell), and `image_mark` = a wall-clock ts (node images with a later `ts`). The identical-re-run merge path never re-attaches — those rows already sit on the right node — and each Run-All pass moves only its own cell's rows (its mark is past the prior pass's), so it stays idempotent. (`%exptrack promote`'s note append is likewise made idempotent in `promote()` itself, not in the shared `append_to_current_note`, which stays append-only for `%%pin`'s timestamped trail.)

- **A trashed thing that's still reachable must say it's trashed**: soft-delete hides a row from the *live lists*, but not from every path that can reach it — so any surface that can still land on a trashed row has to label it, or the user sees something the rest of the UI denies exists. Concretely for sessions: `build_tree` deliberately does **not** filter `sessions.deleted_at` (inspecting a session before restoring it is legitimate, and an experiment promoted out of a session keeps a `session_origin` back-link that opens it directly), so the payload carries `session.deleted`, `_session_origin` carries `session_deleted`, and `list_all_trashed_nodes` / `_trashed_node_groups` carry `session_deleted` per node group. The dashboard renders each as an **in Trash** tag (`.session-trashed-tag` on the session header, `.so-trashed` on the back-link banner) and swaps the live-only header actions (Finalize / End session) for **↺ Restore session** — finalizing or ending a session the sessions list doesn't show is a mutation with no visible subject. The unified Trash marks a node group whose session is itself trashed (`.trash-session-note`) with a link to restore the session, because restoring one of those nodes alone changes nothing the user can see. `restoreSession(id)` is shared by the Trash view and the session header, so it only refreshes the views actually mounted

- **Run-All idempotency has to hold for the paths that don't look like cells**: three of the four idempotency breaks found in the 1.4 audit were in code that arms or looks up a node, not in `record_cell`. (1) The branch-collision baseline was armed from *tracked-cell* source only, so a branch whose first replayed cell is `%%setup` never matched and every pass forked `tryA (2)`, `tryA (3)`… with duplicated cells and re-attached metrics — a parallel `baseline_setup_first` is armed alongside it and setup source is compared against setup source. (2) The existing-node lookup excluded type `checkpoint`, but `promote_to_checkpoint` changes a branch node's type *in place*, so after a promote the next Run-All found no node with that label and created a second one beside the promoted original. (3) Session re-adoption matched only `status='active'`, missing the commonest notebook shape there is — `session start` at the top, `session end` at the bottom — so each pass built a whole new tree; an `ended` session of the same name is re-adopted and reopened, but only on a **definite** notebook match, since the lenient rule that lets a missing notebook name still re-adopt after a kernel restart would otherwise let an unrelated notebook reopen a session someone deliberately closed

- **A session is active per kernel, not per run**: `_active_session_node` stamped `session_node_id` onto *any* metric logged while a session was live, whoever owned the run — and `materialize` then copied those foreign numbers onto the graduated branch, re-introducing through the tag the very cross-attribution the tag exists to prevent. `SessionManager.owns_experiment` is the ownership test: this session's auto-linked run, or a run linked to a node in this session. An *unlinked* run still counts while the session has adopted none, because the notebook hook autolinks only after the first cell body runs — but once a session has adopted a run, a second unlinked one is somebody else's

- **The numbers were already there; nothing read them back**: metrics have carried `session_node_id` since Session Trees shipped, but the tree payload didn't include them, so comparing `val_acc` across two branches meant materializing both into experiments first — a heavyweight, irreversible-feeling step to answer "which one was better". `build_tree` now carries per-node metrics (one query for the whole tree, canonicalized through the alias map like every other metric read) and the node comparison shows them with polarity-aware best marking

- **A graduated branch is a run like any other**: `materialize_experiment` wrote no `script` and copied no params, so every materialized branch was a run of nothing — outside every baseline chain and every "What changed" card, and a param study over a finalized session reported *nothing varying* even though the branches differed by exactly the knob being explored. It now records the session's notebook as the script, and promotes the node's own scalar hyperparameter assignments (`lr = 0.2` in its cells) as real params. Deliberately literal-only and HP-named: `df = load()` is not a hyperparameter and `lr = base_lr * 0.1` is not a value this layer can know. The node's cells are the *only* per-node record of the knob — a session's `_var/` params live on the single auto-created run, attached to whichever node happened to be current when the variable changed

- **A session's study is keyed by name *and* notebook**: the study a session's runs are grouped under was its name alone, so two notebooks each running a session called "explore" — the obvious name, and the one the docs themselves use — merged into one study. A param study over it then reported parameters varying across two unrelated pieces of work. `_session_study_name` qualifies with the notebook stem when there is one, and it is the single source all three writers (autolink, materialize, finalize) share, so they cannot disagree about which study a run belongs to

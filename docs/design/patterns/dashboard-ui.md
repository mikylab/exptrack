# Dashboard: the experiment list and detail view

Table columns, grouping, filtering, inline editing, the filmstrip, and what a live run's poll must not disturb.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **Scannable experiment table at scale (param columns · empty-column collapse · readable names)**: The main table's job is answering "what did I change and what did it do?" across a hundred near-identical runs, so three things are load-bearing. **(1) Params can be columns.** A column id of the form `param:<key>` (`PARAM_COL_PREFIX`, `isParamCol`/`paramColKey`/`paramColLabel` in `js/core.py`) adds any captured hyperparameter as a real, sortable column — `ALL_COLUMNS` used to be a fixed list, so the very thing that differs between two runs of the same script (`--lr`, `--threshold`) was invisible in the list and required opening every run. Column lookup goes through **`getColumnDef(colId)`**, which returns the static entry or *synthesizes* one for a param column, so the header renderer, `getColWidth`, and the row builder treat both alike (`visibleCols` validates param ids by shape rather than membership, and `_colOrderIndex` slots them as a group just before Metrics so a row reads name → config → results → time). `paramColCandidates()` scans the loaded runs for `isParamColCandidate` keys (non-`_`-prefixed, `isUserParamKey`) and flags each with whether its value **varies**, listing varying ones first; the ⚙ Columns panel renders them as a **Params** section with a `●` marker plus an `addVaryingParamColumns()` one-click button. Cells come from `_paramCellHtml` (right-aligned `.param-cell`, tabular figures, full value in the `title`) and sorting is numeric when both values parse as numbers, else a string compare, with missing-param runs pinned to the bottom exactly like `metric:` sort. **(2) Empty columns stop hoarding width.** `emptyCollapsedCols(exps)` (over `COLLAPSIBLE_COLS` = tags/studies/stage/notes/changes, via `_colHasData`) returns the columns with no data anywhere in the current view, and `renderTableHeader` renders those at `EMPTY_COL_WIDTH` (60px) instead of full width, with `th.col-empty` styling the header label dimmed, lowercase and at `--text-xs` so it still *names* the column at that width. **A collapsed header must keep its label**: at 44px it didn't fit, so the label was hidden behind a `·` — four unlabelled dots between STATUS and METRICS read as a broken table rather than as empty columns, and gave you a narrow strip you could sort by without knowing what you'd sorted (the tooltip alone doesn't fix that). The collapse also never *widens* a column: it only applies when the column's own width exceeds `EMPTY_COL_WIDTH` — with no tags/studies/stages set, three columns were a wall of `--` at full width while Name and Metrics got clipped. It's width-only, never a hide, so the ⚙ Columns checkbox never lies, and a width the user set by dragging always wins (`colWidths[colId]` short-circuits it). `renderExperiments` re-runs `renderTableHeader` so the collapse tracks filter changes. **(3) Names keep both ends.** `midEllipsis(text, max)` + `nameCellMaxChars(hasAutoBadge)` middle-truncate the name to the actual column width — an auto name (`Jul28_ablate__lr0.01__2aac1081`) differs from its neighbours only in its *tail*, so CSS head-truncation turned a rerun burst into a screen of identical `Jul28_abl…` rows. The char budget must be computed, not fixed: the cell lives in a `table-layout: fixed` column with `text-overflow: ellipsis`, so a JS string longer than the column gets its tail clipped by CSS and the middle-ellipsis is undone. `#exp-table` also overrides the global `th`/`td` padding (16px sides, 1px letter-spacing) down to 9px/0.3px, because a 6-letter header like "STATUS" otherwise needed ~86px of column just to render its own label

- **Polarity-aware metric deltas (green means better, not bigger)**: Every delta the dashboard renders goes through `metricGoodDirection(key)` → `_deltaVisual(key, d)` in `js/core.py`, which returns `-1` when *lower* is better. Colouring used to key purely on the sign of the change, so `train/loss` climbing 0.221 → 0.275 rendered as a green ▲ — the run regressed and the UI called it an improvement, which is precisely the question the run-vs-run loop exists to answer. `LOWER_IS_BETTER_RE` matches the metric's base name (after the last `/`, so `train/loss` resolves like bare `loss`) and each `_`-separated part (catching `smooth_loss`, `val_rmse`, `grad_err`): `loss`/`err`/`error`/`mse`/`rmse`/`mae`/`mape`/`nll`/`kl`/`perplexity`/`ppl`/`wer`/`cer`/`fpr`/`fnr`/`eer`/`regret`/`cost`/`latency`/`runtime`/…. The **arrow still shows the numeric direction** (▲ = the value rose) while the **colour shows better/worse**, so no information is lost, and the tooltip states which way is better for that key. A per-key user override lives in localStorage `exptrack-metric-polarity` (`{key: 'lower'|'higher'}`, written by `setMetricPolarity`) for metrics the heuristic can't know. Consumers: `metricDelta(before, after, key)` (Compare's metrics table + the Overview "What changed" card), `_fsDeltaHtml(prev, val, key)` (filmstrip badges), and the "vs previous run" strip chips (`.vs-chip-better`/`.vs-chip-worse`, previously a single neutral colour). **The filmstrip's baseline is resolved by timestamp** (`_fsPrevByTime`), not by list position — `exps[i+1]` is only the older run under the default `created_at desc` sort, so with *Sort by metric* on or any pin reordering the list the badge silently became a comparison against an arbitrary run while still reading as a chronological delta

- **Failures are visible, never a silently blank view**: Two layers, because a blank table that claims "140 total runs" is worse than an error. **Server side**, `core/queries.py:_json_list` keeps one corrupt `tags`/`studies` row from taking down the whole list request (see **`core/queries.py`** under Key modules). **Client side**, `api()`/`postApi()` in `js/core.py` no longer let a failure escape: a network-level rejection, a non-JSON/truncated body, and a non-OK status all route through **`_showApiError(path, detail)`** → a fixed bottom `.api-error-bar` naming the failing endpoint with **Retry** (reload) and dismiss buttons. Previously only `401` was handled and everything else rejected with nothing catching it, so the render that depended on the fetch never ran — no rows, no empty-state, no error, no clue. Because `api()` can now return `null`, the state-assigning callers guard it: `loadStats` returns early rather than painting `undefined` numbers, `loadExperiments`/`loadMoreExperiments` require `Array.isArray(page)` so a bad response leaves the last good data on screen, and `getFilteredExperiments` coerces a non-array `allExperiments` to `[]` so no render path can throw. **Auth**: `ensureAuth` probes `/api/ping` unauthenticated via `_authDisabledOnServer()` before showing the login overlay — with `exptrack ui --no-auth` there is no token, and the old code fell straight through to a login prompt that asked for a token which did not exist and could never be satisfied, making the whole dashboard unreachable

- **Collapsible groups (sidebar + main table)**: The experiments sidebar's `#sidebar-group-btn` opens a **grouping picker** (`toggleSidebarGroupMenu`/`setSidebarGroupBy`) offering **None · Study · Script · Day · Git branch** (`sidebarGroupBy`, persisted as `exptrack-sidebar-group-by`; migrates the old boolean `exptrack-sidebar-group-study` key on first load). Day and Git branch were added because the two questions the run list is most often asked — "what did I run yesterday?" and "what did I run on this branch?" — had no answer in the rail at all; the button became a **menu rather than a cycle** at the same time, since with five modes reaching the one you want meant clicking blind through the ones you did not, re-rendering the list each time. **`GROUP_MODES` (js/core.js) is the one definition of how a mode keys and labels a run**, shared by the main table and the rail: `{keyOf(e), labelOf(key, items), empty}` per mode, with `NO_GROUP` as the sentinel for "this run has no value here" and `groupLabelHtml(modeId, key, items)` rendering the escaped header (the italic placeholder for the empty group). The two views used to derive the same six modes independently and had already drifted: the table keyed an unset branch as the literal `'no branch'` while the rail used `'__no_branch__'`, the day key was computed in three places (`renderExperiments`, `setGroup`'s pre-collapse loop, the rail), and the table rendered its "(no X)" placeholder for Study only — so its Script and Branch modes showed a bare `no script` header. The *rendering* and the collapse state stay per-view on purpose (different markup, and opposite expanded-by-default conventions). **`SIDEBAR_GROUP_MODES` (js/sidebar.js) is then the view-specific half only**: icon, tooltip, menu label, and this mode's own expanded-set + localStorage key. Its `set` field is a *function* because those Sets are module-level `let`s in core.js and capturing the value at load time would freeze the table against whatever replaces them. **Each mode keeps its own collapse state** (`expandedStudyGroups`/`expandedScriptGroups`/`expandedDayGroups`/`expandedBranchGroups`) so collapsing a date cannot silently collapse a study that happens to share its name; `expandedStudyGroups` is the one shared with the main table. The main-table group bar has matching "Study" and "Script" options alongside Git Commit / Branch / Status / Day / None, and the main-table group bar has matching "Study" and "Script" options alongside Git Commit / Branch / Status / Day / None. **The main table defaults to `script` grouping and persists the choice** (`exptrack-group-by`, written by `setGroup`); it used to default to `git_commit`, which is the worst grouping for this workflow — every run has its own commit, so you got one "— 1 run" header per run, doubling the row count for zero information. Script grouping keys on the training script's basename (`e.script.split('/').pop()`) — aimed at the "tweak one line, run `exptrack run train.py`, repeat" workflow, where a burst of near-identical runs against the same script would otherwise flood a flat list. The two views use **different defaults**: the sidebar defaults groups to **collapsed** (study via `expandedStudyGroups`/`exptrack-expanded-studies`, script via its own `expandedScriptGroups`/`exptrack-expanded-scripts` — kept separate so collapse state doesn't cross-contaminate between modes) since a busy left rail is the main motivation; the main table defaults to **expanded** like the other groupings (uses the existing `collapsedGroups` set, so click-to-collapse behavior matches Git Commit / Branch / Status). Experiments without a study/script fall under a "(no study)"/"(no script)" header in both views. `list_experiments`/`/api/experiments` expose the `script` field (the resolved script path `Experiment.__init__` captures) needed for this grouping

- **Pinnable Todos / Commands panel**: The toolbox drawer (Todos + Commands) can be pinned as a persistent right-side panel via the pushpin button in the drawer header or the "Pin Todos / Commands panel" checkbox in Settings → Display. When pinned, `body.toolbox-pinned` shifts the header and `#app-layout` right by `var(--toolbox-w)` (the drawer width), the overlay is hidden, and `closeToolbox()` is a no-op. The drawer's left edge is a drag handle when pinned — drag to resize between 260–800px (RAF-throttled). State persists in localStorage (`exptrack-toolbox-pinned`, `exptrack-toolbox-tab`, `exptrack-toolbox-w`). Each panel also has export buttons: Todos → `.md`/`.txt`/`.json`, Commands → `.sh` (runnable script)/`.md`/`.json`. Tab switches re-render local state without re-fetching

- **Save exports to project folder**: A "Save exports to project folder" toggle in Settings → Display routes all downloads (Todos, Commands, experiment exports) through `POST /api/save-export`, which writes to `<project_root>/exports/` and auto-suffixes filenames (`foo.md`, `foo_2.md`, …) so existing files are never overwritten. The unified `saveOrDownload(text, filename, mime)` helper in `js/core.py` wraps `downloadBlob` (browser download) with this server-side save path; preference is held in localStorage (`exptrack-export-to-folder`)

- **Inline editing (one editor at a time, inside its own column)**: All editable fields (name, tags, notes) support double-click inline editing in dashboard — no modal prompts. **Exactly one cell editor is open at any moment.** Nothing used to close the one already open, so working across a row left the tags, studies, stage and notes editors all live at once — and the table is `table-layout: fixed` with narrow columns, so each editor overflowed its column while the next `<td>` painted over it: they stacked, one editor's ✓ button landing inside the next one's input. `js/inline_edit.js` owns the mechanism and every starter uses it: **`closeOpenCellEditor()`** first, then **`_registerCellEdit(el, close, restore?)`** once built — which returns a **token** the starter keeps and hands back to **`_afterInlineEdit(token)`** when the edit finishes. `close` **commits**, matching what blurring already did — closing is a save, not a discard. Four things are load-bearing. **(0) The token, not the cell, identifies the editor**: a cell can host a second editor while the first one's save is still in flight (re-open the same cell during the round trip), and matching on the element let that stale save close the editor which had replaced it — the cell went blank on its own. `_afterInlineEdit` also clears the registration, so there is one call at the end of an edit rather than a two-call protocol whose first half, if forgotten, silently suppressed the re-render. **(1) `closeOpenCellEditor` restores the cell synchronously**, because the commit is async and the re-render it schedules is deliberately skipped while another editor is open — without it the closed cell keeps a dead editor on screen, which is the pile-up this exists to end. **(2) `_restoreEditedCell` replaces exactly one `<td>`, never the row** (rebuilt from live `allExperiments` via `renderExpRow`, so the cell shows what was just saved, with the pre-edit HTML snapshot as fallback): the editor being opened is usually a sibling cell, and re-rendering the row detaches the very node it is about to be built in — it then renders into a dead node and never appears at all. **(3) `_afterInlineEdit()` defers its re-render and skips it when an editor is open**, for the same reason — and the render it runs is the shared `_renderExpViews()`, since inline edits change names, tags and studies, which feed the "Needs naming" count and the metric-sort options as much as the two list renders do. **(4) The editor is a panel (`.cell-edit-pop`), anchored to the cell but not laid out inside it.** Tags, Studies, Stage and Notes collapse to `EMPTY_COL_WIDTH` (60px) when nothing on screen has a value — which is exactly the width they have when you go to add the *first* one — so an in-flow editor had nowhere to render: the input overflowed the column and the chips, their ✕ buttons and the ✓ were pushed out of reach, making a collapsed column impossible to add to. The panel gives every editor the same usable width (250–360px, right-anchored for the last columns so it opens inward) and the cell gets `.cell-editing` (own background, `z-index`, `overflow: visible`). **(5) A capture-phase `mousedown` listener on `document` closes the open editor when the click lands outside its cell** — committing, exactly as blurring does. Before it, the only ways out were opening another editor or tabbing away. **In the main table this is genuinely `ondblclick`**: the editable cells (name/tags/studies/stage/notes) were wired to `onclick` with a `cancelRowClick()`, so a single click anywhere in five of ~10 columns swallowed "open this run" and popped up an editor nobody asked for — most of the row width was a trap, and it contradicted this documented contract. `renderExpRow` builds both handlers from one place (`editOn(fn, titled)` for the cell's `ondblclick`, `editIcon(fn)` for the pencil), so a single click now falls through to the row handler and opens the run, while the hover pencil (`.edit-icon`, which resolves its target with `this.closest('.editable-cell')`) stays a **one-click** edit affordance so editing got no slower to reach. That makes the pencil the *only* fast way in, so it has to be findable and hittable: it was an 11px glyph with 2px of padding revealed only on **cell** hover — you had to find the cell to reveal the thing that tells you the cell is editable. It now reveals on **row** hover (`#exp-table tr:hover .edit-icon`) and carries a button-sized target (~24×26px). `onRowClick`'s existing 250 ms timer is what makes this work — the dblclick handler cancels the pending open. For the **rename input specifically**, the in-progress input is tracked on a module-level `activeRename` so that re-renders triggered by other UI events (a `loadExperiments` cycle from a mutation, a `refreshDetail` from auto-refresh, etc.) don't yank the input out from under the user mid-type. `renderExperiments`, `renderExpList`, and the detail-panel rewrite each call `_preserveActiveRename()` *before* mutating innerHTML; it detaches the input, returns a closure that re-mounts the same node into the freshly-rendered `[data-rename-slot="<id>"]` after the render (preserving value, focus, and selection). The blur handler no-ops when the input has been detached, so a re-render no longer counts as the user finishing. The slot lives on three render paths: the main table's `.editable-cell`, the sidebar's `.exp-card-name`, and the detail view's `#detail-name` h2; `activeRename.where` (`'table' | 'sidebar' | 'detail'`) keeps the input in the originating view across re-renders. The main table uses `table-layout: fixed` with narrow `.truncate-cell` columns (`overflow: hidden; white-space: nowrap`), so any input mounted inside one would have its right edge clipped — the cursor would sit in the hidden zone and the user's typing would appear invisible. CSS lifts the clip for the editing cell only: `#exp-table td.truncate-cell:has(.name-edit-input) { overflow: visible; position: relative; z-index: 5 }`, and `.name-edit-input` is `position: relative; z-index: 5` with an explicit `color: var(--fg)` (inputs don't inherit `color` in every browser)

- **Tag autocomplete**: `/api/all-tags` endpoint returns all tags with usage counts; UI shows autocomplete dropdown

- **Timezone-aware display**: Dashboard timestamps use `Intl.DateTimeFormat` with configurable timezone stored in project config. **`expDate(v)` in `js/core.js` is the one normalization, and it has to accept two storage formats**: `experiments.created_at` is a UTC ISO string with no zone suffix (so it is parsed with a `Z` appended — parsing it raw reads it as local time, which put "2h ago" out by the viewer's offset), while `sessions.created_at` and `session_nodes.created_at` are **unix floats**. The helpers are shared across both domains, so a number reaching a string-only parser is not hypothetical: `fmtTimeAgo(s.created_at * 1000)` on the sessions list handed one to `iso.endsWith(…)`, which threw a `TypeError` out of the render loop and took the whole session list down with it. A number is treated as epoch milliseconds (what `new Date(n)` already means — there is nothing to append a suffix to) and a non-string, non-number degrades to `null` rather than throwing. `fmtDt`/`fmtDtFull` had each re-implemented the ISO branch inline and so inherited the same assumption; both now go through `expDate`, which is the point of having one

- **Timeline-based tracking**: Every event (cell_exec, var_set, artifact, metric, observational) gets a sequence number for full execution order reconstruction

- **Experiment-list pagination + search debounce**: `list_experiments(conn, …, offset=0)` adds SQL `LIMIT ? OFFSET ?` (`/api/experiments?limit=&offset=`) so the dashboard isn't capped at the old silent top-50. `loadExperiments()` fetches one page of `EXP_PAGE_SIZE` (1000) and tracks `expPageLoaded`/`expHasMore`; a **Load more** button (`loadMoreExperiments()`, rendered in both the main table and sidebar when `expHasMore`) appends the next page to `allExperiments` (de-duped by id). **Truncation is stated, never silent**: filtering, search and `metric:` sort all run over `allExperiments` — the rows fetched *so far*, not the project — so a partially-loaded list makes *Sort by metric* answer "best of the loaded runs" while looking exactly like "best run". Hence the page size is large enough that most projects load whole in one request, and when they don't, `renderTruncNotice()` (called from `_renderExpViews`, and from `loadStats` once `expTotal` is known from `/api/stats`) renders a `.trunc-notice` strip above the table — "Showing the N most recent runs of M. Search, filters and metric sort only cover these" — with a **Load all runs** button (`loadAllExperiments()`, which pages through the remainder in sequence since each request needs the previous offset). The notice hides itself the moment `expHasMore` is false. Server-side sort/filter is deliberately *not* done: the honest notice plus a high cap covers the real workloads without splitting the filter logic across SQL and JS. The two search inputs call `onSidebarSearch`/`onMainSearch`, which set `searchQuery` synchronously but route the expensive re-render through a 150 ms `debounce()` (in `js/core.py`) so fast typing doesn't re-filter+re-sort+rebuild the table/sidebar per keystroke. Metric series remain separately downsampled (see Metric thinning); keyed incremental row-diffing is intentionally not done (full `innerHTML` rebuild is fine at these sizes). **`limit` is clamped server-side** to `_MAX_LIST_LIMIT` (5000) in `api_experiments` — it is a client-supplied number and was unbounded, so one request could ask the server to build and serialize the whole project. Nothing in the UI needs more, because both "load all" paths *page*: `loadAllExperiments` always did, and `_loadCmpExps(force, all)` now does too rather than issuing a single `limit = total + 1` request — against a cap that request comes back short, and a short response is indistinguishable from "that is all of them", which is exactly the silent-partial-set failure `_renderCmpTruncNotice` exists to prevent

- **Capture settings in the dashboard**: Settings → Capture surfaces two config keys without hand-editing `config.json` — `auto_capture.notebook` (a "Notebook auto-capture" checkbox; off = Session Trees standalone, no per-cell auto-run) and `var_fingerprint_max_mb` (a "Variable fingerprint cap (MB)" number input; lower it when per-cell capture is slow with big DataFrames, since objects over the cap fall back to the cheap `_stable_sig` shape/dtype signature). Read via `GET /api/config/capture` (`api_get_capture_settings`), persisted via `POST /api/config/capture` (`api_set_capture_settings`, clamps MB to 1–10000, `save()`+`reload()`). JS `loadCaptureSettings`/`saveCaptureSettings` in `js/core.py`; both require a notebook kernel restart to take effect (the owl note says so)

- **Auto-named runs flag + "Needs naming" filter**: `experiments.name_is_auto` (INTEGER, default 0) tracks whether the user has ever deliberately renamed a run. `Experiment.__init__` sets it to `1` when the constructor was called without an explicit `name` (so `make_run_name(...)` filled it in) and to `0` when a name was passed. Internal auto-renames after argparse/notebook capture (`Experiment._rename`) intentionally do **not** touch the column — only `POST /api/experiment/<id>/rename` clears the flag, marking the rename as user-intentional. The schema migration in `_ensure_schema()` backfills existing rows by fingerprinting names with `looks_auto_named()` (matches the trailing `__<8 hex>` suffix from either the readable or legacy `MMDD_<uid>` layout). `list_experiments` exposes `name_is_auto` as a bool; the dashboard renders a small amber `auto` badge (`.auto-name-badge`) next to the name in both the sidebar (`_renderExpCard`) and the main table (`renderExpRow`), and a `Needs naming` checkbox in the Group-by bar (`autoNamedOnly`, persisted as `exptrack-auto-named-only`) filters `getFilteredExperiments` down to flagged runs only. When the filter is on, just-renamed rows are held in a JS-side `recentlyRenamedIds` set so they stay visible after commit (their `name_is_auto` flips to false, so without this they'd vanish instantly with no visual confirmation that the rename worked); the held-over rows render without the `auto` badge — that's the confirmation — and the `(N)` count still reflects the real backlog. The set is cleared on `setAutoNamedOnly` toggle and on page reload

- **Experiment filmstrip (flip through runs from the detail view)**: A horizontal, scrollable strip of mini-cards pinned at the top of every run's detail panel (`#detail-filmstrip`, rendered by `renderFilmstrip(currentId)` in `js/detail.py` right after the panel HTML is injected). It lists **one card per run in the current filtered + sorted list** — it calls the shared `getFilteredExperiments()` (`js/table.py`) so the strip's order and contents always match the table/sidebar (filters, search, *Sort by metric*, pins all apply). Each card shows a status dot, the run name, and a **primary metric** value + a coloured **delta badge vs. the chronologically previous run** (resolved by timestamp via `_fsPrevByTime`, *not* the next card in the list — list order changes with sorting/pinning, run order doesn't). The delta uses a compact filmstrip-specific badge (`_fsDeltaHtml` — arrow + percent, short absolute fallback when the baseline is 0) rather than the full `metricDelta()` form (too wide for a 150px card), sharing `_deltaVisual()` so a lower-is-better metric colours the same here as everywhere else. Cards are `overflow:hidden` with the name and metric set to `min-width:0`/`text-overflow:ellipsis` so nothing ever spills past a card edge. The primary metric key is the active *Sort by metric* key when set (`sortCol` = `metric:<key>`), else the first metric present on any run (`_filmstripMetricKey`). The open run's card is `.active` (accent border/tint) and auto-centered within the track (`track.scrollLeft`, no page scroll); a `N / M` counter shows position. Navigation: clicking a card calls `refreshDetail(id, {keepSidebar:true})` directly (not `showDetail`, which would toggle-close the open run); `‹ ›` buttons and a global ←/→ keydown handler (`js/init.py`, ignored while focus is in an input/textarea/select/contenteditable and only while the detail view is actually visible) call `filmstripStep(±1)`, which steps to the adjacent run (also with `{keepSidebar:true}`). The `keepSidebar` flag suppresses `refreshDetail`'s auto-expand of a collapsed sidebar — filmstrip stepping is a lateral move between already-open runs, so it leaves the sidebar in whatever state the user set (only a fresh entry into the detail view from the table/welcome/compare auto-expands it). The strip hides when the list has fewer than two runs. All inline card handlers JS-escape via `escJsAttr` per the dashboard XSS rule. Styles (`.detail-filmstrip`/`.fs-track`/`.fs-card`/`.fs-delta`/`.fs-counter`) live in `css/detail.py`, reusing existing `--accent`/`--status-*`/`--diff` tokens (no new palette)

- **A live run's detail view keeps the view state you set**: while an experiment is `running`, `_autoRefreshPoll` (5 s, `js/detail.py`) re-renders the detail panel as metrics arrive — which means every piece of view state the user set has to survive a re-render, or watching a training run is impossible. **The active tab is the load-bearing one**: `refreshDetail` rebuilds the panel from one template string with `class="tab active"` hardcoded on Overview, so each poll silently threw the user back to Overview — the numbers updated, but Charts could not be *read* on a run that was still going, which is the one time you most want it. It now captures `currentDetailTab` before the rewrite and calls `switchDetailTab(restoreTab, id)` after (placed *after* `_chartsMetricsData` is cached, so a restored Charts tab renders this refresh's data), while a fresh entry into a *different* run resets both the DOM and `currentDetailTab` to `'overview'` — leaving the variable stale would restore the previous run's tab on the next in-place refresh. Because *every* `refreshDetail` caller benefits (a tag edit, a logged metric, the timezone setter), the fix lives there rather than in the poll. The poll additionally reloads **only** the Charts container (`loadChartsTab`) when that tab is active, instead of rebuilding the whole panel to update one canvas. **On the poll's hot path the tab is not re-rendered at all**: `loadChartsTab` fetches the new points and hands them to **`updateChartsInPlace(container, metricsData, expId, mode)`**, which pushes them into the Chart.js instances already on screen (`_applyChartPoints` + `chart.update('none')`) and returns `true`. Rebuilding the tab HTML every 5 s was itself the same class of bug as the tab reset above — it takes focus out of an axis-range input mid-typing, closes the metric dropdown if it's open, and restarts the draw animation, once per poll for the length of the run. The rebuild only runs when the on-screen tab genuinely can't show the data: `updateChartsInPlace` returns `false` for a different run (`_chartsExpId`), a different view mode (`_chartsViewMode`), a tab that was never built, or a changed metric-key set (`_chartsRenderedKeys` — a new key needs a new `<option>`), and the caller falls through. Because a chart's data can now be swapped under it, the click-to-delete handler reads its points from `chart.$points` (kept current by `_applyChartPoints`) rather than closing over the `points` array it was created with, which would go stale on the first in-place update. The rebuild path still has to preserve the tab's state, since mutations (`refreshDetail` → `switchDetailTab('charts')`) and view-mode switches go through it: the Single-view metric picker is remembered in `_chartsSelectedKey` (validated against the current run's keys via `metricKeys.includes`, so switching experiments falls back to the first metric) and the typed axis bounds are captured before the rebuild and re-applied after (`getChartScaleOpts` → `applyChartScaleInputs`; an unset bound is `''` throughout and `buildChartScaleConfig` skips it, so an all-empty scale needs no special case). `chartMetricKeys(metricsData)` is the one definition of "keys worth charting" (≥1 point), shared by the HTML builder, the initializer, the in-place check and the overview preview. The Overview tab's chart preview needs the same treatment for the same reason — it carries its own metric dropdown and `refreshDetail` rebuilds the whole panel around it each poll — so `renderOverviewChartPreview` remembers its pick in `_overviewPreviewKey` with the same `includes`-validated fallback. Overview is still a full panel rebuild per poll, so the **scroll offset** is preserved across it too: `#main-content` is the scroller and emptying `#detail-panel` collapses its content, which makes the browser clamp `scrollTop` to 0 — anything read below the fold jumped back to the top every 5 s. `refreshDetail` captures the offset before the write and re-applies it (`_restoreScroll`) both immediately after and again after the tab restore, which swaps the displayed tab div and can collapse the height a second time. It's gated on `!isInitialEntry` — opening a run should start at the top; only an in-place refresh keeps the offset. A null `/api/metrics` response returns early — `api()` already surfaces the failure, and keeping the last good chart beats blanking the tab on one bad poll out of a run's hundreds. **The poll itself never overlaps**: `_autoRefreshInFlight` is held across the whole fetch-and-render cycle (the tab reloads are `await`ed for exactly this reason) and a tick that fires while the previous one is still working returns immediately. The interval is 5 s and a poll can exceed it — a large run, a network filesystem, a tunnel — so without the guard the requests stack and each re-renders the panel underneath the last. Two more things the poll must get right, both of which were wrong: `api()` can return `null`, and reading `.error` off it threw *into the poll's own `catch`*, so a failed request was indistinguishable from a healthy one (`if (!exp || exp.error) return;`, and `exp.metrics || []`); and the run can be closed or switched away from *while the request is in flight*, so `currentDetailId` is re-checked after the await before anything is redrawn

- **Collapsed secondary stats**: `loadStats` renders the four run-status cards (Total/Done/Failed/Running) always, and the other seven behind a persisted `▸ More stats` toggle (`toggleMoreStats`, localStorage `exptrack-stats-more`, default collapsed) — at full height all eleven cards plus two section labels pushed the experiment table itself toward the fold, which is the one thing on the page that has to be visible. Card padding and the `.num` size are tightened to match.

- **Compact, non-overflowing group-by bar**: The main-table controls row (`#group-bar`) is `flex-wrap`-enabled so *Group by · Show · toggles · Sort by metric* wrap to a second line instead of overflowing on narrow windows, and the seven *Group by* options are a single compact `<select id="group-by-select">` (`onchange="setGroup(this.value)"`) rather than a button strip — `setGroup` syncs the select's value (replacing the old `data-group` button `.active` toggling) and `syncFilterControls` re-syncs it on boot, since the markup's first `<option>` is no longer the default. Each label is glued to the control it names by a nowrap `.gb-group` wrapper (`Group by:` + select, `Show:` + the range buttons, `Sort by metric:` + select) so the bar's wrap breaks *between* groups instead of orphaning a label from its `<select>`; the leading `.gb-sep` divider rule is dropped under 1100px, where a wrapped group would render it as a dangling vertical line. The **ID column is off by default** in the main table (`ALL_COLUMNS` `id` entry `defaultOn: false` in `js/core.py`) — the internal run-hash is rarely needed at a glance; it stays available (unchecked, sortable) in the ⚙ Columns panel, and the `visibleCols` merge preserves each user's saved column choices so existing installs are undisturbed

- **Group by Day + date-range filter**: The main table's group-bar has a `Day` option alongside Git Commit / Branch / Status / Study / None — keys come from `dayKeyOf(e.created_at)` (YYYY-MM-DD in the active timezone via `Intl.DateTimeFormat`, falls back to local time), labels from `dayLabelOf` (`Today` / `Yesterday` / `Wed, May 20, 2026`). When `setGroup('day')` runs it pre-collapses every day except the most recent so old work folds away. A parallel `Show:` segmented control (`All time` / `Today` / `7d` / `30d`) lives in the same bar and writes `dateRange` to localStorage (`exptrack-date-range`); the filter is applied inside `getFilteredExperiments` so the **sidebar and main table stay in lockstep**. Both `autoNamedOnly` and `dateRange` are re-hydrated on boot by `syncFilterControls()` (called from `init.py`)

- **Command templates (`{{variables}}`)**: Any saved Command may contain `{{name}}` placeholders. `_extractCmdVars` scans the command text for unique tokens; `renderCommands` then injects a `.cmd-vars` row of editable inputs above the code block, and `_fillCmdHtml` substitutes live values, wrapping every substituted segment in a `<span class="cmd-fill">` (or `cmd-fill-empty` for unfilled tokens) so the user can see at a glance which parts came from a variable. Unfilled tokens stay visible as `{{name}}`. Variables named `date`, `today`, or ending in `date`/`_date` (`_isCmdDateVar`) render as `<input type="date">` and **default to `_todayStr()` each session** instead of persisting (so they never go stale). All other values are debounced and saved per-command via `POST /api/commands/update` with a `values` map (added to the `_config_list_update` allowlist), persisted under each command's entry in `.exptrack/config.json`. The inline-edit reset path is suppressed for templates because the template text itself is never mutated. **Exports (`.sh` / `.md` / `.json`) write the substituted form** via `_fillCmd` so the exported script is runnable as-is; JSON keeps both the raw `command` and a `filled` field for round-tripping

- **Reorderable saved commands**: Only the `.cmd-drag-handle` glyph is `draggable="true"` — **never the whole `.cmd-item`**, because a draggable ancestor disrupts cursor/selection behavior in child `<input>` elements (notably in Firefox/Safari, the caret resets to position 0 between keystrokes in any input inside a draggable element). The card itself listens for `dragover`/`dragleave`/`drop` so drops still target the card. `onCmdDragStart` resolves the parent `.cmd-item` via `e.currentTarget.closest('.cmd-item')`. Drop indicators are `.cmd-drop-before` / `.cmd-drop-after` box-shadows. On drop, `_reorderCmd` mutates `_commands` in place and POSTs the new id order to `/api/commands/reorder`. `api_reorder_commands` rewrites the `commands` array in `.exptrack/config.json` in the requested order, appending any unmentioned ids defensively so a race can't drop a command. Render order is the config list order, not the previous "most recently edited" timestamp

- **"Needs naming" live count**: The `Needs naming` toggle in the Group-by bar shows `(N)` next to its label with the number of un-renamed runs in the current set, so the filter has a visible signal even when every run still happens to need naming. `updateAutoNamedCount()` recomputes from `allExperiments.filter(e => e.name_is_auto).length` on load (`loadExperiments`), on filter-control sync (`syncFilterControls`), and after each inline rename (which also clears the in-memory `name_is_auto` flag so the badge disappears without a reload)

- **Green means better on every compare surface, including the multi table**: Multi Compare tinted the row maximum green and the minimum red, so on `loss`, `latency` or any lower-is-better metric it highlighted the **worst** run in the set as the winner — contradicting the project's own rule and the pair view's Delta column one panel over. It now tints best/worst via `metricGoodDirection` (which honours the user's polarity overrides), and compares with `metricMoved`'s epsilon rather than raw floats: the cells render `.toFixed(4)`, so full-precision comparison could print two identical-looking values and tint one green and one red

- **A comparison states what it left out**: unresolvable picks, metrics logged by only one run (so not overlayable), image grids past their cap, and metric names folded together by the alias map are each reported in place. Rendering three columns for four picks — or 60 images under a heading reading `(200)` — is the same failure the matrix and branch-compare already refuse to make

- **Multi Compare shows the configuration, not only the numbers**: "what produced these" lived exclusively in the parameter matrix, a view Compare does not link to, so a cross-model comparison could not say which model each column was. The Configuration table shows the script row whenever the runs are not all the same model, and *only* the varying params — with six runs the constant ones push the differences off screen. The rank basis (final vs best) is a control and is **stated on the table**, because "0.91" means different things as a final value and as a best-ever point

- **A caller that writes a file must check the response first**: bulk Export/Copy passed `postApi`'s result straight into a Blob, so a 500 downloaded a `.csv` containing `{"error":…}` under a success toast — `api()`/`postApi()` can return `null` and the server reports errors as a payload, and neither is export content

- **A saved command is a template, and the template is never rewritten**: re-running a command differing only in `--lr` meant retyping the line, so `{{name}}` tokens in a saved command each render an editable input, the code block shows the live-substituted result and Copy copies *that*. Three rules make it survive real use. **The stored `command` keeps its `{{…}}`** — substitution happens at render, so an edit can never bake one run's values into the template. **An unfilled token stays visible** as `{{name}}` rather than collapsing to an empty string, because a command that silently lost a flag is worse than one that obviously isn't finished. **Date-like variables (`date`, `today`, `*_date`) default to today and are deliberately not persisted** — a saved date is stale by definition, and re-defaulting is what the user meant. Values are stored on the command object (`c.values`) with this-session edits layered over them in `_cmdVarEdits`, so typing is immediate and persistence is debounced. Per-keystroke updates target the individual `.cmd-fill` spans rather than rebuilding the `<code>` element, which would steal focus from the input being typed in. Commands live in `config.json`, so they are committable and travel with the project

- **A bulk action counts what it can act on, not what is selected**: `Finish` marks the *running* runs in a selection as done — the case is a launcher that died and left a batch stuck (a SLURM array, a killed sweep), which is why it is bulk at all. The button is labelled with the running count and is **absent when none is running**, so it never offers a no-op; and it posts only those ids, since posting the whole selection made the result report "7 already done" about runs the button never offered to touch. The route separates `finished` / `already_done` / `failed` rather than returning one total: a run that was already done is not a failure, and an id that resolved to nothing is the one thing the user has to be told. Finishing goes through the same `finish_experiment` the single-run route uses, so a run finished in a batch records the duration it would have recorded alone

- **Changing a selection is not changing the data, and must not repaint like it**: the Compare Within tab picks two points on a run's timeline. Every click on a checkpoint called `loadCompareWithin(expId)`, which re-requested `/api/timeline/<id>` and rewrote the tab's entire `innerHTML` — to change which two of those rows carry an `A`/`B` badge. Two scrollers paid for it, and both are load-bearing: the checkpoint list is its own `overflow-y` box, so it snapped to the top and the row just clicked left the screen; and emptying `#main-content` collapses its content, so the browser clamped the page scroll to 0 as well — the same trap the live-run refresh documents above, solved there and not here. The one control whose entire job is "click the event you mean" moved that event out from under the cursor, and the tab looked like it had reloaded the page. `_cwRepaintSelection()` is the in-place path: the two point descriptions, the Compare button's disabled state, and the badge cell plus marker classes of the rows that changed, with each row addressed by a `data-seq` attribute rather than by rebuilding the list it sits in. Both scroll offsets are captured before the writes and restored after, page and list. Three supporting rules. The checkpoints come from the cached `_withinEvents` (`_cwCheckpoints()`), because which points a run offers is a property of the run and picking one does not change it — so no request is needed and none is made. The result panel below **is** cleared, because it answered the previous pair of points and leaving it under a bar naming different ones is the one outcome worse than blanking it. And Clear takes the same path (`clearWithinSelection()`), since it is the same kind of change; leaving it on the rebuild would have kept a second, slower way to do the identical thing, which is how the first one came back

- **An artifact row is a link, and the row says so**: artifacts are tracked by reference, so a row means "this run points at this file", never "this run owns it" — and which other runs point at the same path is what decides whether a delete may take it. `get_experiment_detail` ships `linked_by` per artifact (one query for the whole list, not one per row — this is on the 5s poll), the row renders it as **also in N runs** naming them on hover, and the action is labelled **unlink**: the old *del* button asked "Delete artifact?" and removed only the record, so the wording promised a file delete it never performed. `unlinkArtifact` is the name; `deleteArtifact` stays as an alias because other call sites use it

- **A destructive choice is two named outcomes, not a tick-box**: the delete confirm first held a linked file back behind an unticked "also delete" box, which makes the safe result *the thing you did not do* — invisible in the dialog and unattributable afterwards. It now names both, headed by **⚠ Another run is linked to this file**: **Unlink and delete this experiment** (preselected) and **Delete both**, each spelling out what the other runs are left with. The radio the button handler reads is still the "delete" one, so an untouched dialog can only keep

- **Export and copy are the same answer at different distances**: the diff panels offered **Export** (a `.md` download through `exportDiff`) and nothing else, so pasting a run's code change into a lab notebook, an issue or a message meant a detour through the filesystem to find the file the browser had just saved. `copyDiff(id)` posts the same `/api/experiment/<id>/export-diff` and writes `d.markdown` to the clipboard — the same payload, rendered server-side, so the two can never disagree about what the run's code change was; a second client-side render of the diff would be a second thing to keep in step. A Copy sits beside every Export site (the merged uncommitted-changes panel, its header action, and the summary row), which is what `tests/test_dashboard_js_integrity.py` checks by counting the two call sites against each other — the failure mode here is not a broken button but a panel that quietly kept only the download

- **The same rule, and where it bit twice**: the Images tab's Compare mode is the second copy of the failure above, and the one that was actually reported. `selectImgCompare` called `loadImages(expId)` — a fresh request for `/api/images/<id>` and a full rewrite of the tab's innerHTML — in order to move an A/B badge between two cards. The gallery is the tallest thing in the detail view (`Show 200` is a real setting), so emptying it collapses `#main-content`, the browser clamps its scrollTop, and clicking a thumbnail 350 pixels down the page put the reader back at the top with the thumbnail they were aiming at somewhere else. Measured, before and after, by driving a real Chrome over CDP: pre-fix `scrollTop 349 → 0`, with a bare scroll *event* and no scrollTop *write* anywhere — a browser-side clamp, which is what makes this invisible to a grep for `scrollTop`; post-fix `349 → 349` with no scroll activity at all. `_imgCmpRepaint()` touches the badge, the card's selected class and the bar naming the two picks, addressing each card by a `data-src` attribute rather than by the text of its inline handler. `clearIntraCompare` takes the same path. Entering compare mode still rebuilds — the per-card handler switches between `selectImgCompare` and `openImageModal`, and the bar appears — so `loadImages` holds the page position across its own write instead (`_holdMainScroll`), which also covers Refresh and the filter/sort/limit selects, all of which rewrote the tab and dropped the reader at the top. **The generalization worth keeping: a handler that changes only what is *selected* must not call the function that loads the data.** Both instances were written as a call to the loader because it was the function that already knew how to draw the right thing; both produced a control that moved its own target out from under the cursor

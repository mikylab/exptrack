# Metrics at loop scale

Thinning, commit batching and chart rendering — the only things exptrack does inside the user's inner loop.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **Metric thinning (count points, never test the step value)**: Two-layer system for large metric series. Write-time: `thin_every` on `Experiment` or `metric_keep_every` in config, applied by `Experiment._keep_metric_point(key)` — **1 of every N points logged, counted per metric key on the per-instance `_metric_logged` dict, with a key's first point always kept** (count 0). Read-time: min-max bucketing downsamples for chart display (`metric_max_points`, display-only and non-destructive). The gate used to be `step % keep_every == 0`, which silently assumes the caller logs on *every* step: the common `if (i+1) % 5 == 0` cadence logs steps 5, 10, 15 …, so with `keep_every=999` the two are coprime, **no step ever satisfies the test, and the run stores zero points** — a setting reading as "thin this" acting as "discard everything", diagnosable only as an empty chart. Even a compatible factor was wrong (`1000` on a 200-step run kept step 0 alone). Counting points delivers what the setting always claimed, at any cadence, and cannot take a series to zero. Three properties are load-bearing: **(1)** the count is per key, so `log_metrics({loss, acc})` thins both identically while a key logged on only some calls still keeps every Nth of *its own* points — hence `log_metrics` calls the gate per key inside its loop rather than once for the dict; **(2)** a step-less `log_metric(k, v)` is thinned on the same rule (the old gate returned `True` for `step is None` because it had nothing to take a modulo of, so those series ignored the setting outright); **(3)** an unusable config value (`0`, `-3`, `"abc"`, `None`) degrades to keeping everything — a hand-edited config must never be why a run recorded nothing. `_metric_logged` is a class-level `None` (not a shared dict, which every run in the process would mutate) set per instance in `__init__` and in `resume`'s `object.__new__` path, and `_keep_metric_point` re-initializes it defensively. **Dropping data is never silent**: the first drop prints a one-line stderr notice naming the factor (once per run, via `_thin_notice_shown`), and the dashboard field is "Store 1 of every N points" with a `.settings-note` consequence line (`_updateKeepEveryNote`) that appears only above 1 and points at `exptrack prune` as the non-destructive alternative. Guarded by `tests/test_metric_thinning.py`

- **A divisor has to state itself in the units the user will read it in**: `metric_keep_every` *reads* like a budget ("keep 1,000 points") and *is* a divisor, and for anyone whose loop already logs every Nth step the two readings differ by orders of magnitude — a 100,000-step run logging every 5th step logs 20,000 points, and `metric_keep_every: 1000` stores 20 of them. The failure looks exactly like the coprime-step bug above (a chart with a handful of points on it) and has an entirely different cause, with no number on any surface connecting the setting to the outcome. The first-drop notice can only name the factor, because at the first drop nothing else is known yet; the counts *are* known when the run ends, so `_print_thinning_summary` states points stored out of points logged, says outright that the setting is 1-of-every-N and not a target count, and names the two non-destructive alternatives (`metric_max_points` for chart resolution, `exptrack prune` for what is already stored). It prints only when something was actually dropped — a summary on every run is noise on the default path — and goes through `safe_call`: a notice must never be the reason a finish fails. `_metric_dropped` is a class-level `0` for the same reason `_metric_logged` is a class-level `None`, the `object.__new__` resume path

- **Metric write cost at loop scale (a commit is an fsync)**: metrics are the only thing exptrack writes inside the user's *inner loop* — a 100k-iteration run calls `log_metrics` 100k times — so the per-call commit that is fine everywhere else dominates here. It was ~96% of the write cost: 100k iterations × 5 metrics took **151s**, against 8s for the same inserts committed in batches, i.e. exptrack added two and a half minutes to a run it is supposed to passively observe. `Experiment._commit_metrics` now commits at most once per `metric_commit_interval_ms` (config, default 250; `0` restores commit-per-call), and `log_metric`/`log_metrics` take the connection as `conn = get_db()` rather than `with get_db() as conn:` — **sqlite3's connection context manager commits on exit**, so the `with` form silently defeats both this and `batched_writes()` (which metrics had therefore never actually honored, despite the docstring). Three properties are load-bearing and each has a test. **(1) The window is time-based, not count-based**, because uncommitted rows are invisible to the dashboard's separate connection: a count-based batch would stall a slow run's chart for however long N iterations take, while a time window bounds the lag at the interval regardless of loop speed. **That bound only holds because a deferred write arms a trailing flush** (`Experiment._arm_trailing_flush` → `_flusher_loop` → `_commit_pending_window`): a deferred write enters the run into `_flush_due` (a `WeakKeyDictionary` of run → window deadline, so it never keeps a run alive), and **one long-lived daemon thread per process** waits on `_flush_cv` — a `Condition` over `_metric_commit_lock` — and commits whatever window reaches its deadline with no later write having closed it. Without it the window closed only when a *later* write arrived — a loop logging four metrics together every ten epochs committed the first (`loss`) and left the other three invisible to the dashboard until the next burst ten epochs later committed them, so the chart showed `loss` alone at epoch 10 and the other three, at their epoch-10 values, at epoch 20. **Every commit that closes a window goes through `_window_closed`, which removes the run from `_flush_due`** — the first version armed a `threading.Timer` per window and never cancelled it, so in a tight loop the inline commit at +250 ms was followed by the timer's own commit 5 ms later: two fsyncs per window, and a thread spawned for each (~14k an hour). The flusher commits from another thread, which is why `get_db()` opens with `check_same_thread=False`, and it commits **only a transaction it knows is all metric rows**: the deferred insert records `(conn, conn.total_changes)` as `_pending`, and the flush skips if that has moved (someone else wrote on the connection since, and committing now would split their unit of work — their own commit lands our rows) or if no transaction is open. The insert + `_commit_metrics` pair, `flush_metrics` and the flusher all hold `_metric_commit_lock` (one module-level `RLock`, so the resume path needs no per-instance setup) — `flush_metrics` holding it is what stops a flusher that already passed its check from committing `Experiment.__init__`'s `BEGIN IMMEDIATE` transaction after the flush that precedes it. The window's clock is `time.perf_counter`, not `time.monotonic`: on Windows `monotonic` advances in ~15.6 ms ticks, so two writes a few ms apart read as zero elapsed and a short window did not close on time (`test_slow_logger_is_never_a_point_behind` failed there only). **(2) The first write of a run always commits** — `_last_metric_commit` starts at `-inf`, not `now`; starting the window at creation defers the first point until the *second* write, so a run logging once per epoch would show its chart permanently one epoch behind, the exact opposite of the intent. **(3) Everything that can end a run flushes**: `finish` (before anything in it can raise), `fail`/`__exit__` via `finish`, any other logging call (committing the shared connection commits these too), and interpreter shutdown via the module-level `_live_runs` WeakSet + `atexit` hook — so a script that just falls off the end without `finish()` keeps its points. Only `kill -9` loses anything, bounded by the interval. Because `_live_runs` holds weak references, the flush cannot rely on the registry alone: a run GC'd mid-window (function scope, exception unwind) vanishes from it with rows still buffered, and the next `Experiment()`'s `BEGIN IMMEDIATE` then died on "cannot start a transaction within a transaction", destroying those points in its rollback. **`db.flush_pending(conn=None)` is the answer and it asks the connection, not a registry** — `conn.in_transaction` is maintained by sqlite3 and is True exactly when an implicit transaction is open, so it covers *every* writer rather than only the ones that remembered to set a flag. (An earlier version kept a thread-local flag beside it; that was a hand-maintained mirror which went stale against `close_db` — the flag outlived the connection it described — and reported nothing for writers that never touched it.) `_flush_live_runs` ends with a `flush_pending()`, and `close_db()` calls it before closing so a pending window is never silently rolled back. The pending window also leaves an **implicit transaction open on the shared connection**, so `Experiment.__init__` calls `_flush_live_runs()` before its `BEGIN IMMEDIATE` — otherwise creating a second run after a metrics loop dies with `cannot start a transaction within a transaction`. `Experiment.__exit__` guards both its branches with `if not self._finished:` — a script may `finish()` explicitly inside the `with` block, and an unguarded second finish raised (in the exception branch, replacing the user's real exception). A call that stores no row still ticks the window via **`_tick_commit_window()`**, so a long stretch that stores nothing can't leave an earlier kept point uncommitted indefinitely — and that helper tests the elapsed window against *instance* state before touching the DB layer, because `get_db()` re-derives the path, `mkdir`s the parent and runs a `SELECT 1` liveness probe on every call (~14 µs, ~9x the cost of the whole thinned call): calling it per dropped point put a syscall and a round trip on the one path that must stay nearly free. **Both no-store paths must tick — a thinned point and a dropped non-finite value** — on both `log_metric` and `log_metrics`: `log_metric` (singular) originally ticked on the thinned branch but `return`ed on the non-finite branch without ticking, so a non-finite single log as the last metric activity before a pause left a kept point buffered past its window (no data loss — the next kept metric or `finish()` still landed it — but a live chart lagged). The singular and plural paths now tick on every no-store exit

- **Charts must render faster than the poll that refreshes them**: `get_metrics_series` backs `/api/metrics`, which the detail view **polls every 5 seconds** while a run is live — so its cost is not a page-load nicety, it is a hard budget. It used to `SELECT` every point for the experiment and build a dict per row before handing the list to `_downsample_points`, which discarded ~99% of it: 500k rows (one 100k-iteration run × 5 metrics) took ~6s to produce 2500 chart points, of which under 1.5s was the scan. Each poll then occupied a request thread for longer than the poll interval. The bucketing now runs in SQL (`_bucketed_points`) and only surviving points are built in Python. Two aggregate passes per key — one keeping each bucket's lowest-valued point, one its highest — each relying on SQLite's **bare-columns-with-a-single-min/max** rule to get that point's own `step`/`ts` rather than just its value; that rule is *why it is two queries and not one with both aggregates*, since having both voids the guarantee and the bare columns go arbitrary. Buckets are cut on **`COALESCE(step, rowid)`**, and the result is sorted on that same value: the step for a training loop, insert order for the step-less `log_metric(k, v)` case where every step is NULL — bucketing on step alone collapses such a series into one bucket, and sorting the *output* by `step`/`ts` instead scrambles it, since `ts` resolves only to the second. First and last points get reserved buckets (`-1` and `num_buckets`) so a chart spans the run's true extent and the final value read off it is exact. A key already at or under `max_points` skips bucketing entirely and is returned exactly as stored. The bucket-local value ranking is also what **bounds** the output: filtering on `value = MIN(value) OVER …` would return every row of a flat series

- **A view of nine charts has to leave the page as nine charts**: the charts tab's `⬇ PNG` wrote one file per canvas, so taking the *Show All* grid anywhere meant nine downloads and reassembling them by hand in something else — and Show All exists precisely because "how did every metric move" is one question, not nine. `_chartsSheetCanvas` composites the visible canvases into a single image: a grid (1, 2 or 3 columns by count), each cell captioned with its metric, on an opaque theme-matched ground, because Chart.js canvases are transparent and a see-through PNG is unusable in every document it would be pasted into. The cell size comes from **the canvases' own pixel dimensions**, not from CSS pixels: Chart.js scales its backing store by the device pixel ratio, and drawing to a guessed size is what makes an exported figure blurry — the caption's font size follows the same ratio so it does not shrink to nothing on a HiDPI screen. `_visibleCharts()` is the one place that knows the `charts` map is keyed `all_<metric>` in the grid view and `_active` in the single view, so the sheet, the per-file download and the clipboard path can never disagree about what is on screen. **Copy is a first-class exit, not a follow-up to a download**: `⧉ Copy` puts the image on the clipboard directly. Several charts go as the sheet rather than one at a time, because the clipboard holds one image and copying nine would keep only the last. Writing an image needs both `ClipboardItem` and a secure context — `127.0.0.1` is one, a plain-http tunnel to the dashboard is not — so `_copyCanvasPng` checks for all three and, when they are missing, **says why and names `⬇ PNG` as the way through**; a button that silently does nothing on a tunnelled dashboard is indistinguishable from a broken one, which is the failure `_showApiError` exists to prevent elsewhere


- **Two metrics compared belong on one chart, and the x-axis is the step**: the Charts tab's **Overlay** view (`renderOverlayChart`, js/charts.js) draws any ticked subset of one run's metrics together — *Show All* answered "how did every metric move" but not "where did train and validation loss part company", because two grid cells have two y-axes and two widths and the divergence had to be eyeballed across the gap. The x-axis is **linear on the logged step** (`_overlayXY`), not the per-point label list the single chart uses: validation logged every tenth epoch and training every epoch have different label lists, and forcing them onto one would misplace one series; a step-less series falls back to its index. **One axis unless the scales force two** (`_overlayAxisGroups`): the first pick anchors the left axis and anything within 10x of its largest magnitude shares it — loss (~2) and accuracy (~0.9) read fine together — while a series past 10x (a 1e-4 learning rate) moves to a right axis, because on the left it is a flat line on the floor; two axes at most, and the right-hand series say so in the legend. The axis-range inputs bound the left axis only. It opens on **the train/val pair of the run's primary metric** (`_overlayDefaultKeys` over `_overlayBaseName`, which strips only split words — `train_`/`val_`/`valid_`/`test_`/`eval_`, prefix or suffix, `_ . / -` separators — so `val_acc` and `val_loss` stay two families); ticks are remembered per browser (`exptrack-chart-overlay`), like smoothing, and a run holding fewer than two of them falls back to its own pair. The first pick stays first so the left axis does not change owner as others are ticked. Everything a single chart does still applies: smoothing and its raw ghost per series (ghosts kept out of the legend), click-to-delete resolved against **the dataset that was hit**, PNG/Copy under the chart's `$title`, and the 5 s poll updates it in place via `_applyOverlayPoints` — which returns false, and the chart is rebuilt, only when fresh data would move a series to the other axis.

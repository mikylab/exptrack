# Storage, deletion and reclaim

Where the bytes went, refcounted blobs, pruning, exports, the Trash contract and what a permanent delete may remove.

Detail for patterns indexed in `CLAUDE.md`. Each entry states the rule and the failure it prevents — the history is the point, so it is kept verbatim rather than summarized.

- **Knowing where the bytes went (exact per table, apportioned below it)**: The storage report counted metric *rows* and never said what they cost, and nothing anywhere attributed storage to a run — so the two questions that lead to an action ("what kind of data is big" and "which run do I prune or delete") were both unanswerable. `core/storage.py` answers them, and is careful about which numbers it can stand behind. `table_byte_sizes` reads SQLite's **`dbstat`** virtual table, so per-table figures are *exact*: real pages, including each table's indexes and its free space. Nothing below a table has page-level identity, so `metric_storage` (bytes per metric key) and `experiment_storage` (bytes per run) apportion that true total across rows — accurate enough to rank, and labelled **estimated** at every surface rather than presented as measured. dbstat is a compile-time option (`SQLITE_ENABLE_DBSTAT_VTAB`), so an absent one degrades to a bytes-per-row constant instead of a confident zero, and the payload carries an `exact` flag the UI shows. Because it walks every page of the database it is a report-time call only — `exptrack storage` and the Settings panel, never a request hot path. A run's share of a `[ref:sha256:…]` git-diff body is **split across everything referencing it** (sibling runs and session nodes), since charging the full blob to each holder would over-count the database several times over. Surfaced as `exptrack storage [--by-metric] [--top N]`, and a Settings panel that leads with bytes-by-metric and the largest runs (each clickable through to the run) instead of the five row counts it used to show. **`trash_storage(conn)` covers the one place storage accumulates invisibly**: soft delete is the default everywhere, so a trashed run keeps every row *and* its output files (deliberately — Restore has to stay lossless), and nothing anywhere said what that cost. It reports three figures that are reclaimed by three different actions and must not be added into one: `db_bytes` (trashed experiments via `experiment_storage`'s own apportionment, plus trashed session nodes — counting both `session_nodes.deleted_at` **and** nodes under a `sessions.deleted_at` session, since trashing a session does not stamp its nodes), `output_bytes` (files on disk, sized through `output_dirs_owned_by` — the *same* ownership rule the permanent delete uses, so the Trash can never advertise bytes the delete refuses to take because a surviving run also claims that directory), and `local_bytes` (`.exptrack/trash/`, the OS-trash fallback, which nothing but the user removes; `db.local_trash_dir()` is the one definition, shared with `_trash_or_local`, so the report measures the directory files actually land in). Surfaced as a **Trash** section in `exptrack storage` (silent when empty), in the dashboard's storage panel, and as a one-line "Holding …" strip at the top of the Trash view — carried on `/api/trash` rather than the polled badge count, since measuring it walks the database's pages and the trashed runs' output directories

- **Reclaiming metric resolution after the fact (prune) — and reading it without changing it (smoothing)**: `thin_every`/`metric_keep_every` only ever applied at *write* time, so a run recorded at every iteration was stuck at that resolution permanently; `exptrack compact`'s modes (diff/cells/timeline/deep) never touched metrics, which are usually the largest table. `core/storage.prune_metrics` is the way back. **The first point, the last point, and the min and max of every series always survive** — so a pruned chart keeps its endpoints and its extremes, and the final value read off it stays exact. Selection runs **per `(exp_id, key)` series**, because "every Nth point" is only meaningful within one curve — striding across the interleaved rows of five metrics would thin each by a different, arbitrary amount. `preview_metric_prune` and `prune_metrics` share one selection function, so a preview provably describes the delete that follows it, and the byte figure is computed *before* the delete (afterwards the bytes-per-row is apportioned over the survivors and would understate what was freed). Deleted pages go to the database's free list, not back to the filesystem — both the CLI and the dashboard say so and point at `--vacuum` / `exptrack clean --vacuum`. Exposed as `exptrack prune [id...] --max-points N | --keep-every N [--key K] [--dry-run] [-y] [--vacuum]` and `POST /api/prune-metrics`, with the dashboard always running the dry-run first and quoting its real numbers in the confirm — and the confirmed delete removes **exactly the previewed set**: the dry-run stashes its doomed row ids server-side under a `preview_token` and the JS round-trips only the token, since the ids are millions of integers (this is why it can't use the clean-orphans shape, where the client posts back the paths it displayed); the route then passes the cached set as `doomed=`. Memory is bounded two ways because each entry is large: a TTL swept on **both** the stash and the claim path (sweeping only on stash left an abandoned dialog's set resident until the next preview, which may never come) and a hard cap on entries with oldest-first eviction, above 1 so two tabs don't invalidate each other. The stash also carries the dry-run's `table_byte_sizes` result so the confirm doesn't repeat that whole-file page walk — an unknown/expired token refuses rather than re-selecting, since points logged while the dialog was open would make a fresh selection a larger, different delete than the one confirmed. The route also runs `checkpoint_truncate` afterwards, like the delete-permanent routes. Separately and non-destructively, the Charts tab has a **smoothing slider** (`js/charts.js`): a debiased exponential moving average over the plotted points, persisted in localStorage. The debias divisor is load-bearing — without it every curve is dragged toward zero for its first points, so a loss starting at 2.0 appears to start near 0 and *climb*. The unsmoothed series stays visible as a faint ghost line behind the smoothed one, since a smoothed curve alone reads as far less noisy data than was actually recorded; both datasets exist at all times (the ghost merely `hidden` at zero) so moving the slider never changes the dataset count and the charts update **in place**, preserving the live-run refresh contract

- **Exports are summaries, and `--full` is the way back**: A checkpoint-per-epoch run registers thousands of artifacts, which buried the params, metrics and charts on the Overview and made an export unreadable. `core/queries.summarize_artifacts` is the one summariser — it caps the list *and* reports counts by type and by containing directory, so the omitted remainder is described ("4000 files — 3990 model, 10 image; `outputs/ckpts` (3990)") rather than silently dropped. Applied to every **human-readable** surface: markdown export (25), CLI `show` (15), the dashboard's plain-text export (25), each with a `… and N more` line; `--max-artifacts N` overrides, `0` lists all. **JSON used to be exempt from all of this and it was the wrong call**: a run logging every iteration made `metrics_series` tens of thousands of one-line objects and the artifact list thousands more, so the params and the final numbers — the reason anyone opens an export — were buried under raw data that the reader almost never wanted inline. So `get_export_data(conn, id, full=False, artifact_limit=ARTIFACT_LIST_LIMIT)` is a **summary by default for every format, JSON included**: `metrics` carries one `summarize_metric_series` entry per key (`count`/`first`/`last`/`min`/`max` plus the step each extreme sits at — what you'd read off the chart), the artifact list is capped, and `artifacts_summary` (`total`/`listed`/`omitted`/`by_type`/`by_dir`, dirs capped at `SUMMARY_DIR_LIMIT`) states the shape of the rest. **Round-tripping is preserved by an explicit opt-in, not by defaulting to everything**: `full=True` (`exptrack export --full`, `?full=1`, dashboard **Export → JSON (full)**, `/api/bulk-export` body `{"full": true}`) adds the raw `metrics_series` *alongside* the summary and lists every artifact; `artifact_limit=0` uncaps just the list. Truncation is never silent — `omitted` is on the payload and every renderer prints it. **`export_metric_summaries(data)` is the one reader of both shapes** (summary-only, full, or a legacy payload carrying only `metrics_series`), used by the markdown and CSV formatters and mirrored client-side by `_summarizeMetricSeries` in `js/detail.js`, so no consumer re-implements "last value of a series" and none of them break when handed either form. In the dashboard the Overview's Artifacts section **starts collapsed** past 25 with a type summary in the heading, and artifacts **group by containing directory** past 12 with each group foldable — built by `_summarizeArtifacts` in `js/detail.js`, the client-side mirror of the Python helper, shared with the plain-text export (thresholds live beside it as one group of constants). Type classification is `artifactKind(path)`, mirroring `core/queries.artifact_kind`'s vocabulary so the terminal, the export and the dashboard name the same file the same thing; `artifactTypeBadge` renders *that* rather than being the classifier, since counting by type used to mean building badge markup and regex-parsing the CSS class back out of it — which made class names a parsing contract that silently degraded every count to `file` when touched. Grouping switches the older flat 50-row cap *off* rather than stacking with it: running both meant an expanded group could still render nothing, because its rows sat past the flat cutoff

- **A delete that reclaims nothing visible is indistinguishable from a delete that failed**: `delete_experiment` has always removed every child row, but SQLite moves the freed pages to the database's **free list** rather than shrinking the file, so `ls` reports the same size afterwards and the storage report's per-table breakdown silently stops adding up to the file size (delete a run holding 120k metric points and the tables account for 8 MB of a 12 MB file, with nothing naming the other 4 MB). Three things close that gap and they are all *reporting*, not new deleting. **`core/storage.free_space(conn)`** is the measurement — `freelist_count × page_size`, two pragmas and no page walk, so it is cheap enough to call either side of a delete. **Every delete says what it freed**: `cli/mutate_cmds._print_reclaimed(conn, before)` (shared by `rm`, `clean`, `clean --older-than`, gated at `_RECLAIM_NOTE_MIN_BYTES` so a couple of pages isn't announced) and the dashboard's `freed_bytes` on both delete-permanent responses, rendered by `_reportFreedSpace` — each naming `clean --vacuum` as the one operation that hands the space back. **The storage report shows it as part of the file**, as an `of which free` line under the database size and a matching row in the Settings panel, so the breakdown reconciles. **The WAL is the other half**: a delete pushes every rewritten page through it, and the dashboard's per-request checkpoint is deliberately PASSIVE (it must never wait on a live training run), which drains the WAL but leaves the file at its high-water mark — so a dashboard delete left a same-sized database *and* a new multi-MB `-wal` beside it. **`db.checkpoint_truncate(conn, timeout_ms=250)`** is the bounded escape hatch used only by the explicitly-destructive routes: it lowers `busy_timeout` for the duration and restores it, so TRUNCATE's busy handler can wait at most that long and a blocked checkpoint returns `False` instead of stalling the request (the next PASSIVE checkpoint or process exit drains it anyway). Never call it from a hot path. The CLI needed nothing here — its process-exit `close_db` already truncates. **Orphans are the same failure one layer down**, and `core/storage.orphan_storage(conn)` is their report: rows pointing at an experiment that no longer exists are invisible in every list (nothing joins to a missing run) while still occupying the file. exptrack does not create them — `delete_experiment` removes the children first and `PRAGMA foreign_keys=ON` would refuse otherwise — but a database written by an older version, hand-edited, or left by a process killed mid-delete can carry them. `count_orphans` always found them and the CLI-exit `close_db(sweep=True)` always swept them; what was missing was any surface *saying so*, and the storage report's warning was gated on `exp_count == 0`, so a project with 5 runs and 20k orphaned metric rows reported perfect health. It now reports the count and apportioned bytes per table in **Database Health**, and `/api/storage-info` carries the same payload for an **Orphaned rows** section with a Clean button — the dashboard needs that more than the CLI does, since its per-request `close_db(sweep=False)` deliberately never sweeps (the anti-join counts are far too expensive per request), so a UI-only user would otherwise carry a legacy database's orphans forever

- **Reclaiming storage without losing data (refcounted blobs · one reset list · files are opt-in)**: Cleanup has one rule — *DB rows are bookkeeping and can be swept freely; files and content-addressed blobs are user data and need a reference check or a confirmation.* Three mechanisms in `core/db.py`, each with exactly one implementation so the CLI and dashboard can't drift. **(1) The two content-addressed blob tables are reference-counted, not exp_id-keyed.** `code_snapshots` (full script source) and `git_diffs` (whole working-tree diff body) are shared across runs by content hash, so neither can be deleted with a `WHERE exp_id=?`. `_GIT_DIFFS_ORPHAN_COND` is the pure-SQL condition for `git_diffs` (a blob is dead when no `experiments.git_diff` *or* `session_nodes.git_diff` holds its `[ref:sha256:…]` marker — session nodes matter, they reference diffs too) and `_unreferenced_snapshots` handles `code_snapshots` in Python because the reference lives inside a JSON param value SQL can't decode; `_sweep_blobs(conn)` runs both. **They are deliberately *not* in `_ORPHAN_SPECS`**: both are expensive (the SQL condition full-scans experiments ∪ session_nodes — no index serves a `LIKE` prefix across two tables — and the snapshot check reads every `_code_snapshot` param into Python) and neither can go stale without a delete, so `close_db`'s per-command-exit sweep passes `blobs=False` and pays nothing for a guaranteed-zero result. `sweep_orphans(conn, blobs=True)` (the default, used by `exptrack clean` and the dashboard) does the full set, and `count_orphans(conn)` counts the same specs without deleting so a dry-run/confirm can never describe a different set than the sweep removes. `_referenced_snapshot_hashes` scans the raw `_code_snapshot` text for hash-shaped tokens rather than replicating all three encodings that param has had (native list, double-encoded legacy, pipeline pre-encoded string): **over-retention is harmless, under-retention destroys a run's only copy of its source**, so the scan is deliberately generous. `delete_experiment` calls `_sweep_blobs` *after* deleting the run's `params` (before it, the run's own reference is still visible); pass `reclaim_blobs=False` when deleting in a loop and sweep once after — every bulk caller does, since per-run reclaim made a 200-run delete 200 full scans, and the reset paths skip it entirely because `reset_all_tables` truncates both tables wholesale. A **trashed** run still occupies `experiments`, so its blobs survive soft delete and Restore is lossless — only the permanent path drops the last reference. Before this, "permanently delete" left the run's script source and full diff (routinely including an accidentally-staged `.env`) readable forever, and `sweep_orphans` reported a clean DB while both tables grew monotonically. **(2) A reset clears one shared list.** `_RESET_TABLES` / `reset_all_tables(conn)` is used by both `exptrack clean --reset` and `api_reset_db`; the two previously kept separate hardcoded lists that each omitted `code_snapshots` + `sessions` + `session_nodes`, so "delete everything, cannot be undone" stranded every script source and every notebook cell body. Order is FK-safe (`session_nodes` before `sessions`, since `PRAGMA foreign_keys=ON`). **(3) Orphaned output paths are reported, then trashed — never `rmtree`d.** `find_orphan_output_paths` only *identifies* candidates under `outputs/` (a dir claimed by an experiment's `output_dir` or its name; a loose file claimed by living inside a claimed dir — trashed experiments still occupy the table, so their outputs never qualify); `describe_orphan_output_paths` adds file count + bytes for the confirm dialog (through **`dir_file_stats(path, max_files=None)`**, the one implementation of "how big is this tree" — the delete preview's `output_dir` and linked-dir sizing, the storage report's linked-dir and trash figures all call it, so a per-file `stat` that fails on its own is skipped identically everywhere rather than each copy inventing its own error handling. **It is capped at `DIR_STAT_MAX_FILES` (20000), does one `stat` per file rather than two (`Path.is_file()` and `Path.stat()` each issue a full `os.stat`, and it is the per-file syscall that hurts on a network filesystem, not the arithmetic), and returns `(files, bytes, truncated)`**: a checkpoint-per-epoch tree is tens of thousands of `stat`s and a bulk delete previews every run in the batch, which on a network filesystem is seconds of held request thread. Capping it is easy; capping it *honestly* is the point — a partial total is still a true lower bound, so the flag rides the preview payload (`output_dir_truncated`, `linked_dir_truncated`, `dir_stat_max_files`; the bulk totals collapse them to `dir_sizes_truncated`, since a total summed from partial figures is partial) out to both delete dialogs and the orphan-cleanup confirm, which render the affected figures as `≥ N` above a `.dc-trunc-note` naming the cap. The delete itself is unbounded and still takes the whole directory. The cap is resolved per call rather than bound as a default so it is one number the whole codebase can move); `trash_orphan_output_paths` moves them via `_trash_or_local`. Both accept an already-computed `paths` list, and callers discover once and pass it along — annotating walks every orphan tree with `rglob`+`stat` (routinely a checkpoint tree), so the delete request skips it entirely rather than computing an annotation it discards. The CLI's `--orphans` preview annotates through the same helper, so its byte total can't drift from the dashboard's dialog for the same path set. `api_clean_db(conn, body)` sweeps rows on every call but returns `orphan_files` and touches nothing on disk unless `body["delete_files"]` is set, and `settingsCleanDb()` posts twice: once to get the list, then — after an itemised `confirm()` — again with the flag. **The second post carries the paths the first one displayed** (`body["paths"]`), and the route trashes only the intersection of that list with the paths still orphaned *now*, reporting the remainder as `skipped_unconfirmed`. The confirm is built from a previous request, so re-discovering orphans at delete time meant anything written under `outputs/` in between — a run started while the dialog was open, a file dropped in by hand — was moved to the Trash having never appeared in the confirm. Omitting `paths` keeps the old discover-and-act behaviour for older callers. **Linked directories are owned by the same kind of rule** (`linked_dirs_owned_by`, shared by `_delete_experiment_files` and `get_delete_preview` exactly as `output_dirs_owned_by` is): a `[dir] …` artifact names a whole tree the run wrote *outside* `outputs/` — a TensorBoard log dir, a `link-dir` checkpoint folder — and the per-artifact delete loop skips anything that isn't a file, so before this such a directory was recorded and then never cleaned up by anything. Removing a directory is far less forgiving than removing a file, so three rules gate it: **(a)** no *other* run may link it (a shared `SummaryWriter("runs/sweep")` is normal, and trashing it on the first delete would take the survivors' logs), **(b)** it must live under the project root (a shared `~/tb-logs` belongs to the user, not the project), and **(c)** it must not *be* the project root or an ancestor of it (a stray `SummaryWriter(log_dir=".")` records the project directory, and nothing exptrack does may trash a user's whole project). The preview reports them separately from `output_dir` rather than folded into its byte total — they live outside `outputs/`, so the confirm has to name the path or a user who has never opened `runs/` cannot know what is being removed. Note the LIKE pattern for the `[dir] ` prefix takes **no** escaping: `[` is a literal in SQLite's LIKE (unlike SQL Server), and escaping it silently matches nothing. **(4) A permanent delete only removes output directories the run actually owns.** `output_dirs_owned_by(conn, exp_id, name, output_dir)` is the shared rule, used by both `_delete_experiment_files` and `get_delete_preview` so the dialog can never size a directory the delete leaves alone (or the reverse) — and the preview sizes **every** owned candidate, not just the first that exists, since the delete trashes all of them (a diverged recorded `output_dir` + name-derived `outputs/<name>` used to under-state the confirm). There are two candidates — the recorded `output_dir` and the name-derived `outputs/<name>` — and the second is only ours when no *other* experiment row claims it. **They are deduped by `_norm_path`**, because for an ordinary run they are the *same* directory: without that the preview sized it twice and the confirm reported double the files and double the bytes, while the delete correctly trashed it once. **What "claims" means is defined once, in `claimed_output_paths(conn, exclude_id=None)`, and `find_orphan_output_paths` uses the same function**: the two must never disagree, or a directory the delete protects because another run owns it gets reported as debris and trashed by the very next Clean click — the guarantee undone one button over. Comparison is lexical (`_norm_path`) on both sides rather than `resolve()`; consistency between the two consumers is the property that matters, and resolving would put a syscall on every row of a scan that runs per delete. A precomputed set is deliberately *not* threaded through the bulk-delete loops the way `reclaim_blobs=False` is: hoisting it would change the answer in exactly the collision case this exists for — bulk-deleting two runs that share a name would see each claimed by the other and leave the directory behind. **Names are not unique**: `api_rename` accepts any name and `rename_output_folder` deliberately refuses to move a folder onto an existing one, so two runs can carry the same name while only one owns the directory — trashing the name-derived path unconditionally destroyed the *other* run's outputs, with nothing in the confirm saying whose files were being counted. A **trashed** run still counts as a claimant, for the same reason its blobs survive soft delete: Restore has to stay lossless. This matters because **"orphan" is a heuristic that includes files the user explicitly kept**: the permanent-delete modal defaults `delete_files` to *false*, so deleting a run while keeping its checkpoints made those checkpoints unclaimed, and the old unconfirmed `shutil.rmtree` destroyed them on the next Clean click (along with anything hand-placed in `outputs/`). Every file-removal path in the codebase now ends at `_trash_or_local`; `rmtree`/`unlink` appear nowhere outside empty-dir `rmdir` cleanup

- **A file another run still references is not this delete's to remove**: artifacts are tracked **by reference**, never copied, so two runs that write to the same path — a `logs/<date>/` folder, a fixed `results.json`, a rerun after clearing the directory out — each hold an artifact row pointing at one file. The claim rule ("no other run may claim it") existed for directories in `output_dirs_owned_by` and `linked_dirs_owned_by` and was simply **absent from the per-file loop**, which is the one that runs for every ordinary artifact: deleting the earlier run trashed the file the later run had just written, and the survivor's outputs were gone with its artifact row left pointing at nothing. `artifact_paths_claimed_by_others(conn, exp_id)` is the file-level half — lexical (`_norm_path`) like the directory rules so the two can never disagree about one path, and counting trashed runs for the same reason `claimed_output_paths` does, because Restore has to stay lossless. The delete prints which file it left and why. **`get_delete_preview` applies the same rule**: a shared file is marked `shared`, excluded from `artifacts_existing` and `artifact_bytes`, and counted in `artifacts_shared`, so the confirm can say "3 files, 1 kept for another run" — the row stays *listed*, because "this run recorded it" is still true and a silently shortened list reads as though the run never wrote the file. In a bulk delete the last holder still takes the file: each delete removes its own rows before the next one runs, so the final holder sees no remaining claim


- **A shared file is a question, not a rule**: keeping such a file unconditionally is safe and, on its own, a dead end — the user who wants the file gone has no way to say so, and the one who does not know why a delete "freed nothing" is told only a count. The two decisions are now separate: `delete_experiment(..., delete_shared_files=…)` takes the second answer, `get_delete_preview` supplies what the question needs (`shared_with` naming every holding run, `shared_bytes` for what saying yes would free), and every surface asks it the same way — `exptrack rm` prompts (`--shared-files keep|delete` for scripts), the dashboard's three confirms show the list with an unticked box, and the route requires `delete_shared_files` alongside `delete_files`. **`--yes` is not that answer.** A scripted `rm --yes` says "delete this run"; taking another run's file off the back of it is exactly the failure the claim rule exists to prevent, so the shared question defaults to *keep* whenever it was not answered explicitly.

- **A claim can be missing as easily as it can be present**: the file-level rule reads artifact rows, so it protects nothing when the run that overwrote a file never recorded it — which is every run captured before the rule existed (the finish-time scan skipped a path another run's row already claimed; see `run-loop.md`). The second piece of evidence is the file itself: `file_modified_after_run` compares its mtime to `run_end_ts` (the run's `updated_at`, with `_STALE_CONTENT_SLACK_S = 30` for clock skew and a last flush racing the finish write, and `None` while the run is still going, so nothing a live run writes is ever called out of date underneath it). Newer bytes mean the file on disk is not this run's output any more, so it is kept and reported like a claimed one. This is a *heuristic*, and it is only ever allowed to make the delete keep more — never to remove something the claim rule would have spared.

- **The records are editable, because they are sometimes wrong**: `exptrack unlink-artifact` removes an artifact row and never the file; `exptrack log-artifact` adds one. Between them they cover both ways the claim can be wrong — a stale row protecting a file nobody needs, and a missing row leaving a live file unprotected — and they are what the delete's own output points at, since a user told "kept for another run" needs a way to disagree. Neither touches disk: the file half of this belongs to `rm`.
- **Deleted files stay restorable (OS Trash contract)**: `_trash_or_local` is the only way exptrack removes a file — OS Trash first, `<project>/.exptrack/trash/` as fallback, and the file left in place with a warning if both fail. On macOS it goes through Finder via `osascript`; on Linux it implements the XDG spec directly, and **the `.trashinfo` record is created before the file is moved**, with `O_CREAT|O_EXCL` (mode 0600, since it stores an absolute path). Both halves of that matter: a file in `Trash/files` with no matching record is a blob no file manager will restore (which is what a post-move write failure produced), and the exclusive create makes the destination-name reservation atomic so two concurrent trashes can't collide; if the move then fails, the record is unlinked so it never points at nothing. Windows and other platforms have no stdlib OS-trash path and fall through to the local fallback

- **Soft-delete (Trash) with explicit permanent path**: `experiments.deleted_at` (nullable ISO timestamp) marks a row as trashed. The dashboard's `Delete` button (per-experiment and bulk) routes through a confirm modal that defaults to **Move to Trash** — `trash_experiment(conn, id)` only sets `deleted_at` and never touches disk; `restore_experiment(conn, id)` clears it. The modal's **Permanently delete…** tab calls `delete_experiment(conn, id, delete_files=...)`; the bound checkbox "Also move files to system Trash" defaults to OFF, so file removal only runs when the user explicitly opts in. **File removal goes to the OS Trash, not `rm -rf`** — `_send_to_os_trash(path)` uses `osascript` → Finder on macOS, the XDG trash spec (`~/.local/share/Trash/{files,info}`) on Linux; if the OS-trash call fails or the platform isn't supported, `_trash_or_local` falls back to `<project>/.exptrack/trash/<timestamp>__<name>/`. Destructive `unlink`/`rmtree` is never used as a final fallback — if both OS-trash and local-fallback fail, the file is left in place with a stderr warning. `delete_experiment` returns a `{os_trash, local_trash, missing, failed}` count dict, which `api_delete_permanent` and `api_bulk_delete_permanent` surface as `file_stats` in their responses. `list_experiments`, `get_stats` (every count, plus a new `trashed` counter), `get_all_tags`, `get_all_studies`, `get_studies`, and unique-branches stats all filter `WHERE deleted_at IS NULL` by default; `list_experiments(include_trashed=True)` opts back in. Single-experiment lookups (`find_experiment`, `get_experiment_detail`) are deliberately unfiltered so the Trash view can still load detail by id. The Trash view (Settings → Database → 🗑 Open Trash, adds `body.trash-active`) lists trashed experiments with **Restore** / **Permanently delete…** actions plus bulk Restore / Permanent. Endpoints: `POST /api/experiment/<id>/{delete,restore,delete-permanent}` (delete = soft, delete-permanent body `{delete_files}`), `POST /api/{bulk-delete,bulk-restore,bulk-delete-permanent,bulk-delete-preview}`, `GET /api/trash`, `GET /api/experiment/<id>/delete-preview` (returns metric/param/timeline/artifact counts + output_dir size for the modal). Schema migration adds `deleted_at` + `idx_exp_deleted_at` via idempotent `ALTER TABLE` in `_ensure_schema`

- **The Trash is reachable from the terminal**: the dashboard has had a recoverable delete since 1.1, but from the CLI `rm` was permanent, always took the output files with it, and had no listing or restore — so a CLI-only user had no undo at all, and (because `clean --older-than` correctly skips trashed runs) no way to age out anything they *had* trashed elsewhere. `rm --trash`, `exptrack trash` and `exptrack restore-run` close that, with `--keep-files` for the delete-the-records-only case and `--yes` so bulk deletion can be scripted at all

- **An id prefix is user input, so its LIKE wildcards are escaped**: `exptrack rm %` became `LIKE '%%'` — every run in the project, offered up for a permanent delete — and `compact` had the same hole. Prefixes now go through `_like_prefix` with `ESCAPE`, and `compact` resolves ids through `find_experiment` like every other id-taking command, so a typo reports "no such experiment" (non-zero) instead of "No matching experiments." with exit 0, and an ambiguous prefix is refused instead of quietly compacting several runs

- **A destructive command must be answerable non-interactively**: a bare `input()` raises `EOFError` when stdin is not a terminal, so a delete run from cron or CI produced a raw traceback for a question the user never got to answer — and only some commands guarded it, so the same pipeline broke differently depending on which one it reached. `cli/formatting.confirm` is the one prompt: EOF and Ctrl-C both mean *no* (on a destructive action an unanswered question is a refusal), and `--yes` is the supported way to proceed without a terminal. **It returns a bool, and the call site is `if not confirm(prompt, assume_yes): abort`** — nothing else. Converting the old `input()` sites mechanically left five `exptrack session` commands still parsing the answer as raw text: two called `.strip()` on a bool and raised, and three compared it to `("y", "yes")`, which a bool never equals, so they refused every reply including `y`. Re-checking `--yes` around the call is the tell — `assume_yes` is the argument, so a guard outside it means the two disagree about who owns the decision

- **A flag that modifies an action must not replace it**: `clean` dispatched on the first matching flag, so `clean --older-than 30d --vacuum` ran *only* the VACUUM — exit 0, no warning, and the retention delete the user asked for never happened. `--vacuum` is not a selection; it runs *after* one. Two selections at once is now an error rather than a silent choice between them

- **A byte total built by adding SUMs has to COALESCE each one**: the storage report sized the timeline as `SUM(LENGTH(value)) + SUM(LENGTH(source_diff))`, and a SUM over rows that are all NULL is itself NULL in SQLite — so `value_bytes + NULL` made the whole expression NULL and the report's guard fell back to `0`. Every timeline row a materialized session node writes has no `source_diff`, so finalizing a session — the single biggest writer of timeline bytes there is — printed `Timeline: 1,137 rows (~0 B)`: the one report that answers "where did the space go?" denied the space existed. Each SUM is COALESCEd on its own now, which is the rule for every composite size in this file.

- **A command's output must survive a console that cannot spell its glyphs**: `cli/formatting.harden_stdio()` runs first thing in `main()` and reconfigures stdout/stderr with the `exptrack_ascii` error handler. On Windows the console encoding is the system ANSI codepage unless the user opted into UTF-8, and the CLI draws with characters cp1252 does not have, so `print()` raised `UnicodeEncodeError` and the command died with a traceback where its output should be — `exptrack session show` on the tree's first rail, and `exptrack notebook-guard`, the command that exists to make a notebook shareable, on its own guard cell. The stream keeps **its own** encoding (re-encoding to UTF-8 hands a cp1252 console mojibake for every accented run name); only the error handler changes, and it is deliberately not `replace`: the tree is drawn almost entirely out of unmappable characters, so `replace` turned every rail, arrow and separator into the same `?` and destroyed the shape the view exists to show. `_ASCII_FALLBACK` spells the glyphs this CLI actually uses (`+--`, `->`, `.`) and anything unknown still degrades to `?` rather than raising. A UTF-8 stream is left alone, and a stream that cannot be reconfigured (pytest's capture, any wrapper) is skipped — a hardening step must not be the thing that crashes. `NOTEBOOK_GUARD` is held to a stricter rule and is **pure ASCII**, because it is code the user pastes into their own notebook: a lossy substitution there lands in their file, not on their screen. **It lives in `exptrack/_console.py`, a stdlib-only leaf, and every entry point calls it** — `cli/main.main()`, `__main__.main()` (`python -m exptrack`), `Experiment.__init__` (a plain `python train.py`), and `exptrack.notebook` on import (a terminal IPython on Windows: `%exp_log acc` wrote the metric and then died printing the `→` in its own confirmation). It used to live in `cli/formatting.py`, which made the notebook import the whole CLI package (~15 ms per kernel) to reach two lines; `formatting` re-exports it.

- **A Python environment is never a run's output**: `_trash_or_local` refuses any path that is inside, or is, a Python environment, and any folder that directly holds one (returns `'protected'` and says why). An environment is identified by its markers, `pyvenv.cfg` (venv/virtualenv) or `conda-meta/` (conda), via `utils.python_env_containing` / `is_python_env_dir`, never by its folder name. The finish-time output scan also stops at such a folder. Before this, the only rule was the name: `_SKIP_DIRS` held `.venv` and `venv`, so an environment called `env` or `myenv` inside the project was walked, and anything a run wrote there (a mid-run `pip install`, a library writing beside itself) could become an artifact. A later delete, a `link-dir` over it, or a hand-made `log-artifact` could then remove part of the interpreter the next run needs. The guard lives in `_trash_or_local` because every removal already goes through it, and it holds even with `delete_shared_files`. The "holds one" check looks one level down only; a deeper nesting is still caught at the file level, because each file under it resolves inside the environment.
- **Prune is previewed on the chart it changes**: the Charts tab's **Prune** row (js/charts.js, `previewChartPrune`) takes any whole N of 2 or more (10/100/1000 are shortcuts, not the only choices) and a scope — the chart on screen, one named metric, or all of them (`_pruneScopeKeys`, sent as `keys`; pruning is per series, so a noisy train/loss thins without touching the val/acc beside it). It runs the same `/api/prune-metrics` dry-run with `include_points: true`, and for exactly one run the route adds `series` — `core/storage.prune_preview_points`, that run's points split into `kept` and `removed` (each strided to 3,000 for drawing; the counts are exact). The charts in scope redraw with the kept points as the metric's own line and the removed ones as hollow grey rings — shape and lightness, not a red/green hue pair, which a colour-blind reader (or anyone, on a green metric) cannot separate — and the rest of a Show All grid stays as it was; **Remove N points permanently** sends the preview's `preview_token`, so the delete is what was drawn, and **Keep everything** rebuilds the real charts. The live poll's in-place update is frozen while a preview is up (`updateChartsInPlace` returns early), since redrawing the normal chart under it would hide what the button offers to delete, and a running run cannot be pruned from here. A project-wide dry-run never returns points — its set is the whole table. The route resolves id prefixes first: the selection matches ids exactly, and a `#run=<prefix>` link reported "nothing to prune".
- **An artifact that overwrites another run's says so**: `register_artifact` → `_warn_if_overwrote_other_run` prints a one-line warning when the path is another live run's recorded artifact with a *different* content hash. A script saving `drift.png` to a fixed path rewrote it every run, so a whole sweep pointed at the last run's plot, found only when Compare showed 39 copies of one image. Nothing is refused — a shared input (a dataset, a cache) is legitimate, and the same bytes are not an overwrite.
- **Prune a selection from the list**: the selection bar's **Prune…** (js/mutations.js `openBulkPrune`) is the same controls in a panel above the bar — metric, keep 1 of every N — with a counts-only preview (many runs cannot be one picture; the panel points at a run's Charts tab for that) and a delete of the previewed set by token. A scoped dry-run carries `scope_points`, the selection's own point count, because `total_points` is the whole table and "remove 2,274 of 153,988" says nothing about the three runs picked.
- **One backup implementation, two doors**: `core/db.backup_database(conn, dest=None)` is `sqlite3.backup` into `.exptrack/backups/<UTC stamp>.db` (a second backup in the same second gets `_2`, never an overwrite), behind both `exptrack backup` and Settings → Back up database (`POST /api/backup-db`). The download is `GET /api/backup-file?name=` (handler `_serve_backup`), not `/api/file/`, because `/api/file/` refuses everything under `.exptrack/` — that is where the dashboard token lives — so this route serves only a name matching `BACKUP_NAME_RE` from the backups folder: no path, no other file. The browser fetches it with the auth header and saves the blob, since a plain link cannot carry the token.
- **CSV carries each metric's best, not only its last**: `format_export_csv` writes `metric:<key>` (the last value, unchanged), then `metric:<key>:best` (min or max by `goal_for_key`), `:min`, `:max`. The last value alone made a run that peaked and then overfit read as its worst epoch, with no way back to the number it is judged by. `script`, `command` and `output_dir` are relative to a `project_root` column, as the markdown export already states the root once.
